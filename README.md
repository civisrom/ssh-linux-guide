# SSH в Linux: подробное практическое руководство

Руководство объясняет создание программных и аппаратных SSH-ключей, подключение к Linux и GitHub, настройки клиента и сервера, передачу файлов, туннели, автоматизацию и диагностику. Основной вариант — OpenSSH, обычный пользователь Linux и Ed25519 с парольной фразой. Аппаратный FIDO2-токен, в том числе YubiKey с его режимами FIDO2, PIV и OpenPGP, рассматривается отдельно.

Все имена пользователей, комментарии, домены и адреса в примерах вымышлены. `server.example.com`, `bastion.example.com`, `alice`, `OWNER`, `REPOSITORY`, `YOUR_LOGIN` — заполнители. IPv4-адреса `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` предназначены для документации. `127.0.0.1` означает текущую машину. Настоящих ключей, паролей, токенов, адресов серверов и персональных контактов здесь нет.

Команды рассчитаны на Bash или Zsh в Linux. Они не образуют один скрипт: выбирайте нужный сценарий. Блоки с `sshconfig` — содержимое конфигурационного файла, а не команды терминала. Значения параметров и доступность новых возможностей зависят от установленной версии OpenSSH.

## 1. Термины и устройство SSH

SSH создаёт зашифрованное соединение между клиентом и сервером. Клиент обычно запускается командой `ssh`; сервер Linux принимает подключения через `sshd`. GitHub тоже принимает SSH-соединения, но предоставляет через них операции Git, а не обычную оболочку Linux.

| Термин | Значение |
| --- | --- |
| Закрытый ключ | Секретный материал, которым клиент доказывает право доступа. Программный ключ хранится в файле на вашем устройстве. |
| Открытый ключ | Часть пары, которую добавляют на сервер или в GitHub. Знание открытого ключа само по себе не позволяет войти. |
| Парольная фраза, passphrase | Защищает файл закрытого ключа на диске. Вводится локально и не является паролем сервера. |
| Пароль пользователя Linux | Проверяется сервером при парольной аутентификации. Может существовать одновременно с доступом по ключу. |
| Ключ сервера, host key | Подтверждает клиенту, к какому серверу он подключился. Это другая пара ключей. |
| Отпечаток, fingerprint | Короткое представление хеша открытого ключа для сверки. Не заменяет сам ключ при настройке доступа. |
| SSH-агент | Локальная программа, которая выполняет подписи с загруженными ключами. |
| Аппаратный токен | Физическое устройство, участвующее в создании подписи; например, FIDO2-ключ. |
| GitHub PAT | Секретная строка для API и Git через HTTPS. Не является SSH-ключом или аппаратным устройством. |
| Параметр команды | Флаг вроде `-i`, `-p`, `-a`; слово «ключ» иногда используют и в этом значении. |

При входе по ключу закрытый ключ не отправляется серверу. Клиент создаёт подпись, сервер проверяет её по разрешённому открытому ключу. Шифрование всего соединения согласовывается отдельно: выбор Ed25519 не означает, что каждый передаваемый файл шифруется алгоритмом Ed25519.

Открытые ключи не секретны, но их комментарии и повторное использование могут связывать устройства и аккаунты. В комментариях удобно писать назначение вроде `github-laptop`, без реального имени и почты.

### 1.1. Как читать команды в этом руководстве

Команда состоит из имени программы, **параметров** (их ещё называют флагами или ключами командной строки) и **аргументов**:

```text
ssh   -p 2222   -i ~/.ssh/id_ed25519_server   alice@server.example.com   'uptime'
│     │         │                             │                          └─ удалённая команда
│     │         │                             └─ назначение: пользователь@сервер
│     │         └─ параметр со значением: какой файл ключа использовать
│     └─ параметр со значением: порт
└─ программа
```

| Запись | Что означает | Пример |
| --- | --- | --- |
| `-x` | Короткий параметр из одной буквы. Регистр важен: `-p` и `-P` — разные параметры. | `ssh -v lab` |
| `-x ЗНАЧЕНИЕ` | Параметр, которому нужно значение. Значение пишут через пробел; слитная запись `-p2222` тоже допустима, но хуже читается. | `ssh -p 2222 lab` |
| `-xyz` | Несколько параметров без значений можно склеить: `-NT` равно `-N -T`. Параметр со значением ставьте последним или пишите отдельно. | `ssh -NT -L ... lab` |
| `-o Имя=Значение` | Любая директива конфигурационного файла, переданная из командной строки. | `ssh -o ConnectTimeout=10 lab` |
| `ЗАГЛАВНЫЕ_СЛОВА`, `OWNER`, `alice` | Заполнители. Замените их своими значениями. | `git@github-personal:OWNER/REPOSITORY.git` |
| `[ ... ]` в синтаксисе | Необязательная часть. Сами скобки не набирают. | `ssh [-p ПОРТ] ХОСТ` |
| `a \| b` в синтаксисе | Выбор одного из вариантов. | `-c \| -s` |
| `...` в синтаксисе | Часть можно повторить. | `ssh-keygen -k -f KRL ФАЙЛ ...` |
| `\` в конце строки | Перенос длинной команды на следующую строку; после `\` не должно быть пробела. | многострочные примеры ниже |
| `~` | Домашний каталог текущего пользователя, например `/home/alice`. | `~/.ssh/config` |

Параметры `ssh` пишите **до** имени сервера. OpenSSH разбирает параметры и сразу после имени (`ssh lab -v` включит диагностику), но с первого слова, не похожего на параметр, всё остальное становится удалённой командой: в `ssh lab ls -l` параметр `-l` получит программа `ls`, а не `ssh`. Запись `ssh lab -- -v` передаёт `-v` серверу как команду. Чтобы не гадать, держите параметры слева от имени сервера.

Где выполнять команду, всегда сказано в тексте: «на клиенте» — на компьютере, за которым вы сидите, «на сервере» — в сеансе на удалённой машине. Строки внутри блоков `sshconfig` — это содержимое файла, их не вводят в терминал.

Справка по любой программе открывается командой `man ПРОГРАММА`, краткая подсказка — запуском программы с неверным параметром, например `ssh -h`. Сведения в этом руководстве сверены со справкой OpenSSH 10.2; в старых версиях части новых параметров может не быть, а значения по умолчанию могут отличаться.

### 1.2. Быстрый старт для новичка

Если нужно просто войти на свой Linux-сервер по ключу, пройдите шаги по порядку:

1. Проверьте, что клиент установлен: `ssh -V` (раздел 2).
2. Создайте ключ с парольной фразой: `ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_server -C "laptop"` (раздел 3).
3. Узнайте у администратора или в панели провайдера отпечаток ключа сервера (раздел 7).
4. Перенесите открытый ключ на сервер: `ssh-copy-id -i ~/.ssh/id_ed25519_server.pub alice@server.example.com` (раздел 8).
5. При первом входе сравните показанный отпечаток с полученным на шаге 3 и только тогда ответьте `yes`.
6. Проверьте вход по ключу: `ssh -i ~/.ssh/id_ed25519_server -o IdentitiesOnly=yes alice@server.example.com`.
7. Запишите сервер в `~/.ssh/config`, чтобы входить короткой командой `ssh lab` (раздел 9).
8. Только после успешного входа по ключу отключайте пароли на сервере (раздел 14).

Для GitHub шаги 3–6 заменяются добавлением ключа в аккаунт и проверкой `ssh -T git@github.com` (раздел 10).

<a id="prepare"></a>
## 2. Подготовка Linux

На **клиентском компьютере** проверьте наличие OpenSSH:

```bash
ssh -V
command -v ssh ssh-keygen ssh-add
```

Для Debian/Ubuntu клиент устанавливается так:

```bash
sudo apt update
sudo apt install openssh-client
```

Чтобы только подключаться к другим машинам, устанавливать и запускать `openssh-server` на своём компьютере не требуется. Установка сервера рассмотрена отдельно.

Подготовьте каталог от имени своего пользователя, без `sudo`:

```bash
umask 077
mkdir -p ~/.ssh
chmod 700 ~/.ssh
ls -la ~/.ssh
```

`~` — домашний каталог текущего пользователя. `mkdir -p` создаёт отсутствующий каталог и не очищает существующий. `umask 077` ограничивает права новых файлов в текущей оболочке; уже существующие файлы он не исправляет. `ls` показывает имена и права, а не содержимое ключей.

Не создавайте личный ключ через `sudo ssh-keygen`: он может оказаться в домашнем каталоге root или получить неудобного владельца.

Проверьте локальную справку:

```bash
man ssh
man ssh-keygen
man ssh_config
```

Она соответствует установленной версии лучше, чем инструкция для самого нового выпуска. Установка пакетов описана в [документации Ubuntu](https://ubuntu.com/server/docs/how-to/security/openssh-server/).

<a id="software-key"></a>
## 3. Создание ключа без аппаратного токена

### 3.1. Рекомендуемый вариант для личного доступа

На компьютере, с которого будете подключаться:

```bash
ssh-keygen -t ed25519 -a 100 \
  -f ~/.ssh/id_ed25519_github \
  -C "github-laptop"
```

Обратная косая черта `\` в конце строки продолжает команду. После неё не должно быть пробелов. Та же команда одной строкой:

```bash
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_github -C "github-laptop"
```

Если программа сообщает, что файл существует, **не соглашайтесь на перезапись**. Выберите другое имя, например `id_ed25519_github_new`. Перезапись может лишить доступа к системам, где зарегистрирован старый открытый ключ.

На запрос `Enter passphrase` введите длинную уникальную парольную фразу. Затем повторите её. Символы при вводе не отображаются. Не копируйте в качестве пароля фразу из публичного руководства.

Создаются:

```text
~/.ssh/id_ed25519_github       закрытый ключ
~/.ssh/id_ed25519_github.pub   открытый ключ
```

Показать только открытую часть и её отпечаток:

```bash
cat ~/.ssh/id_ed25519_github.pub
ssh-keygen -l -E sha256 -f ~/.ssh/id_ed25519_github.pub
```

GitHub рекомендует Ed25519 для новых ключей. [Создание ключа для GitHub](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent).

### 3.2. Отдельный ключ для Linux-сервера

```bash
ssh-keygen -t ed25519 -a 100 \
  -f ~/.ssh/id_ed25519_server \
  -C "linux-admin-laptop"
```

Разделение по устройствам и назначениям упрощает отзыв: потеря ноутбука не требует менять ключ другого компьютера. Разные имена файлов сами по себе не ограничивают права — ограничения задаются на стороне принимающей системы.

### 3.3. RSA для совместимости

Если целевая система не поддерживает Ed25519 или её политика требует RSA:

```bash
ssh-keygen -t rsa -b 4096 -a 100 \
  -f ~/.ssh/id_rsa_legacy \
  -C "legacy-access"
```

Это вариант совместимости, а не автоматическое повышение защиты относительно Ed25519. Не сравнивайте числа бит у разных семейств алгоритмов напрямую. Для RSA важна также поддержка современных подписей SHA-2; не включайте устаревшие SHA-1-подписи глобально ради одного старого устройства.

Ed25519 имеет фиксированный размер. Добавление `-b 4096` не сделает его «Ed25519 на 4096 бит». DSA для нового доступа не используйте. В средах FIPS поддержка алгоритмов может ограничиваться политикой конкретной системы.

<a id="keygen-options"></a>
## 4. Что означают параметры ssh-keygen

В основной команде:

| Часть | Назначение |
| --- | --- |
| `ssh-keygen` | Создание и обслуживание ключей. |
| `-t ed25519` | Тип ключа. |
| `-a 100` | Число раундов защиты парольной фразы при сохранении. |
| `-f ПУТЬ` | Имя файла; `.pub` создаётся рядом. |
| `-C "метка"` | Комментарий, не обязательно email. |
| `-b 4096` | Размер RSA; у Ed25519 неприменим. |

Другие часто нужные режимы:

| Параметр | Назначение |
| --- | --- |
| `-p` | Изменить парольную фразу существующего ключа. |
| `-c` | Изменить комментарий. |
| `-l` | Показать отпечаток. |
| `-E sha256` | Выбрать хеш отпечатка. |
| `-y` | Получить открытую часть из закрытого ключа. |
| `-N`, `-P` | Передать новую/старую парольную фразу аргументом; для ручной работы избегайте. |
| `-O` | Дополнительная настройка выбранного режима. |
| `-Z` | Шифр хранения закрытого ключа. |
| `-m` | Формат импорта/экспорта или совместимости. |
| `-q`, `-v` | Меньше/больше диагностического вывода. |

Буквы регистрозависимы: `-C` и `-c` различаются. Подробная спецификация режимов находится в [ssh-keygen(1)](https://man.openbsd.org/ssh-keygen).

### Примеры обслуживания

Поменять парольную фразу и сохранить файл с выбранной трудоёмкостью KDF:

```bash
ssh-keygen -p -a 100 -f ~/.ssh/id_ed25519_github
```

Программа сама запросит старую и новую фразы. Публичная часть ключевой пары не меняется: повторно добавлять её в GitHub не нужно.

Изменить только поясняющую метку:

```bash
ssh-keygen -c -C "github-desktop" -f ~/.ssh/id_ed25519_github
```

Восстановить потерянный `.pub`, не выводя закрытый материал в терминал:

```bash
ssh-keygen -y -f ~/.ssh/id_ed25519_github > ~/.ssh/id_ed25519_github.recovered.pub
ssh-keygen -l -f ~/.ssh/id_ed25519_github.recovered.pub
```

Выход `-y` — открытый ключ; исходный закрытый файл обрабатывает сама программа. Новый файл специально имеет другое имя, чтобы не затереть уже существующую открытую часть.

<a id="passphrase"></a>
## 5. Парольная фраза и значение -a

У файла программного ключа есть два разных уровня защиты: права Linux ограничивают доступ к файлу, парольная фраза затрудняет использование украденной копии. Если злоумышленник уже управляет вашей разблокированной системой, одной парольной фразы недостаточно: он может перехватить ввод или воспользоваться доступным агентом.

`-a 100` задаёт 100 раундов KDF `bcrypt_pbkdf`. Это **не** размер ключа, не срок действия, не число попыток входа и не параметр сетевого шифрования. Значение применяется при защите файла парольной фразой. Без неё повышение `-a` не создаёт эквивалентной защиты.

Практическая схема выбора:

1. Создайте уникальную длинную фразу, например из нескольких независимо выбранных случайных слов, и сохраните её в надёжном менеджере паролей.
2. Начните с `-a 100`.
3. Проверьте, комфортно ли разблокировать ключ на самом медленном вашем устройстве.
4. При желании увеличьте значение до `200` или `300`, сохранив разумное время ожидания.

Зависимость времени от числа раундов следует оценивать на своей машине. Нельзя обещать одинаковые миллисекунды для ноутбука и маломощного устройства. Значение по умолчанию менялось между версиями OpenSSH — не считайте число из старой статьи универсальным. В OpenSSH 10.2 без `-a` используется 16 раундов, а сам файл шифруется алгоритмом `aes256-ctr`.

Оценить время разблокировки на своей машине можно на учебном ключе:

```bash
umask 077
mkdir -p ~/ssh-kdf-test
ssh-keygen -t ed25519 -a 100 -f ~/ssh-kdf-test/test -C "kdf-test"
time ssh-keygen -y -f ~/ssh-kdf-test/test > /dev/null
```

`time` покажет, сколько длилось чтение ключа вместе с вводом фразы; повторите с другим `-a` на новом учебном файле. Затем удалите каталог: `rm -r ~/ssh-kdf-test`.

Шифр, которым защищён файл, меняется параметром `-Z` при создании или смене фразы, например `ssh-keygen -p -Z aes256-ctr -f ПУТЬ`. Список допустимых шифров выводит `ssh -Q cipher`. Менять значение по умолчанию без конкретной причины не нужно.

Фраза не должна быть вашим паролем GitHub, паролем Linux или строкой из известной книги. Не передавайте её через `-N "секрет"`, shell history, сообщения, Git или URL. Интерактивный запрос избавляет от необходимости помещать секрет в аргументы процесса.

<a id="files"></a>
## 6. Файлы SSH и права доступа

| Путь | Где находится | Что содержит |
| --- | --- | --- |
| `~/.ssh/id_ed25519_github` | Клиент | Закрытый ключ. |
| `~/.ssh/id_ed25519_github.pub` | Клиент | Открытый ключ. |
| `~/.ssh/config` | Клиент | Псевдонимы и настройки подключений. |
| `~/.ssh/known_hosts` | Клиент | Сохранённые открытые ключи серверов. |
| `~/.ssh/authorized_keys` | Сервер, у целевого пользователя | Открытые ключи, которым разрешён вход. |
| `/etc/ssh/ssh_config` | Клиент | Общесистемные настройки клиента. |
| `/etc/ssh/sshd_config` | Сервер | Настройки демона. |
| `/etc/ssh/ssh_host_*_key` | Сервер | Закрытые ключи идентичности сервера. |

Для существующих личных файлов:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519_github
chmod 644 ~/.ssh/id_ed25519_github.pub
```

Для конфигурации:

```bash
touch ~/.ssh/config
chmod 600 ~/.ssh/config
```

На сервере, от имени пользователя, которому нужен вход:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

`700` — доступ владельцу каталога; `600` — чтение и запись владельцу файла; `644` — запись владельцу, чтение остальным. Открытый ключ допустимо хранить и с более строгими правами.

Не применяйте `chmod -R 777`, не меняйте рекурсивно весь домашний каталог. Проверьте владельца и доступность родительских каталогов; сервер может отклонять небезопасные права при `StrictModes yes`. На системах с SELinux могут дополнительно требоваться корректные метки, а на файловых системах с ACL — проверка ACL.

Проверить владельца и права всей цепочки каталогов до файла удобно командой `namei`:

```bash
namei -l ~/.ssh/authorized_keys
```

Каждая строка показывает права, владельца и группу очередного компонента пути: домашний каталог не должен быть доступен на запись группе или остальным, иначе `sshd` при `StrictModes yes` откажет во входе по ключу. На серверах с SELinux метки восстанавливает `restorecon -Rv ~/.ssh`.

### 6.1. Формат known_hosts

Каждая строка `~/.ssh/known_hosts` описывает один ключ сервера:

```text
server.example.com,192.0.2.10 ssh-ed25519 AAAAC3...КЛЮЧ
[server.example.com]:2222 ssh-ed25519 AAAAC3...КЛЮЧ
|1|СОЛЬ|ХЕШ ssh-ed25519 AAAAC3...КЛЮЧ
@cert-authority *.example.com ssh-ed25519 AAAAC3...КЛЮЧ_CA
@revoked * ssh-ed25519 AAAAC3...ОТОЗВАННЫЙ_КЛЮЧ
```

| Часть строки | Значение |
| --- | --- |
| `server.example.com,192.0.2.10` | Имена и адреса через запятую; допускаются шаблоны `*` и `?`. |
| `[server.example.com]:2222` | Запись для нестандартного порта: имя в квадратных скобках и порт через двоеточие. |
| `\|1\|СОЛЬ\|ХЕШ` | Хешированное имя (`HashKnownHosts yes` или `ssh-keygen -H`): по файлу нельзя прочитать, к каким серверам вы подключались. |
| `ssh-ed25519 AAAA...` | Тип и сам открытый ключ сервера. |
| `@cert-authority` | Строка содержит ключ центра сертификации: доверять всем серверам, чьи ключи им подписаны (раздел 22). |
| `@revoked` | Ключ отозван и никогда не принимается; `ssh` выведет предупреждение. |

Редактировать файл вручную можно, но удобнее `ssh-keygen -F` (найти) и `ssh-keygen -R` (удалить): они понимают хешированные имена и записи с портом. Системный файл с той же структурой — `/etc/ssh/ssh_known_hosts`.

### 6.2. Формат authorized_keys

На сервере каждая строка `~/.ssh/authorized_keys` — один разрешённый ключ:

```text
ssh-ed25519 AAAAC3...КЛЮЧ laptop
from="192.0.2.0/24",no-port-forwarding ssh-ed25519 AAAAC3...КЛЮЧ office-pc
```

Строка состоит из необязательного списка ограничений через запятую, типа ключа, тела ключа и комментария. Пустые строки и строки, начинающиеся с `#`, игнорируются. Перенос одной записи на несколько строк ломает ключ: вставляйте содержимое `.pub` целиком одной строкой. Полный список ограничений — в разделе 20.2.

<a id="host-verification"></a>
## 7. Отпечатки и проверка сервера

При первом подключении клиент ещё не знает host key. Отпечаток следует получить по независимому доверенному каналу: из консоли сервера, панели провайдера или от администратора. На серверной консоли показать отпечаток открытого host key можно так:

```bash
sudo ssh-keygen -l -E sha256 -f /etc/ssh/ssh_host_ed25519_key.pub
```

Сравнивайте алгоритм и полный отпечаток. Только после совпадения принимайте ключ. Для GitHub используйте [официальную страницу отпечатков](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints), а не число из случайной статьи.

Найти уже сохранённую запись:

```bash
ssh-keygen -F server.example.com
ssh-keygen -F '[server.example.com]:2222'
```

После подтверждённой переустановки сервера или согласованной ротации его host key можно удалить конкретную старую запись и заново сверить новую:

```bash
ssh-keygen -R server.example.com
ssh-keygen -R '[server.example.com]:2222'
```

Не запускайте удаление автоматически при `REMOTE HOST IDENTIFICATION HAS CHANGED`. Причиной бывает как нормальная переустановка, так и подмена подключения.

`ssh-keyscan` только получает открытый ключ из сети. Он **не подтверждает**, что отвечает правильная машина. Слепое добавление его вывода в `known_hosts` не заменяет сверку. [Описание ssh-keyscan](https://man.openbsd.org/ssh-keyscan).

Правильный порядок с `ssh-keyscan`: получить ключ, посчитать его отпечаток, сравнить с отпечатком из доверенного источника и только затем сохранить:

```bash
keys="$(mktemp)"
ssh-keyscan -t ed25519 -p 2222 server.example.com > "$keys"
ssh-keygen -l -E sha256 -f "$keys"
```

`mktemp` создаёт временный файл, доступный только вам, и печатает его имя; переменная `keys` хранит это имя до конца сеанса терминала. Если отпечаток совпал с тем, что показала консоль сервера, добавьте строку в базу доверия и удалите временный файл:

```bash
cat "$keys" >> ~/.ssh/known_hosts
rm "$keys"
```

| Параметр ssh-keyscan | Назначение |
| --- | --- |
| `-t ТИП` | Какие ключи запросить: `ed25519`, `ecdsa`, `rsa`, `ed25519-sk`, `ecdsa-sk`; несколько — через запятую. По умолчанию все. |
| `-p ПОРТ` | Порт сервера. |
| `-T СЕКУНДЫ` | Сколько ждать ответа; по умолчанию 5 секунд. |
| `-H` | Хешировать имена в выводе, как в `HashKnownHosts`. |
| `-c` | Запросить сертификаты сервера вместо обычных ключей. |
| `-D` | Вывести ключи как DNS-записи SSHFP. |
| `-O hashalg=sha256` | Для `-D`: хеш записей SSHFP (`sha1` или `sha256`; по умолчанию оба). |
| `-f ФАЙЛ` | Читать список серверов из файла, по одному в строке; `-` — со стандартного ввода. |
| `-4`, `-6` | Только IPv4 или только IPv6. |
| `-q` | Не печатать комментарии с именем сервера и баннером. |
| `-v` | Диагностика. |

Для уже настроенного соединения удобно требовать заранее известный ключ:

```bash
ssh -o StrictHostKeyChecking=yes alice@server.example.com
```

Это не подключится к новому неизвестному серверу, пока вы не установите доверие отдельно. `accept-new` автоматически доверяет первому ключу, но отказывается от изменившегося; это удобство первоначального подключения, а не независимая проверка личности сервера. Не используйте `StrictHostKeyChecking=no` и `UserKnownHostsFile=/dev/null` как универсальное исправление ошибок.

<a id="linux-login"></a>
## 8. Подключение к Linux-серверу

### 8.1. Добавление открытого ключа

Пользователь `alice` должен уже существовать на сервере. Для первоначальной установки нужен разрешённый доступ: пароль, старый ключ или серверная консоль.

На клиенте:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519_server.pub alice@server.example.com
```

Для другого порта:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519_server.pub -p 2222 alice@server.example.com
```

Укажите именно `.pub`: на сервер переносится открытый ключ. На GitHub `ssh-copy-id` не применяется — там используется интерфейс аккаунта.

Сначала можно посмотреть, что именно будет добавлено, ничего не меняя на сервере:

```bash
ssh-copy-id -n -i ~/.ssh/id_ed25519_server.pub alice@server.example.com
```

Перед добавлением `ssh-copy-id` пробует войти каждым ключом и пропускает те, что уже установлены, поэтому повторный запуск обычно не создаёт дубликатов.

| Параметр ssh-copy-id | Назначение |
| --- | --- |
| `-i [ФАЙЛ]` | Какой ключ переносить. Если имя не оканчивается на `.pub`, это окончание добавляется. Без `-i` берутся ключи из агента (`ssh-add -L`), а если их нет — самый новый `~/.ssh/id*.pub`. |
| `-n` | Пробный запуск: только показать ключи, которые были бы добавлены. |
| `-f` | Не проверять, установлен ли ключ, и не требовать закрытой части; может создать дубликат строки. |
| `-s` | Добавить ключ через SFTP: скачать `authorized_keys`, дописать и загрузить обратно. Помогает, если на сервере запрещены произвольные команды. |
| `-t ПУТЬ` | Другой файл на сервере вместо `.ssh/authorized_keys`. |
| `-p ПОРТ` | Порт сервера. |
| `-F ФАЙЛ`, `-o ОПЦИЯ` | Передать `ssh` другую конфигурацию или отдельную директиву. |
| `-x` | Показать команды самого скрипта для отладки. |

Пример с псевдонимом из `~/.ssh/config` (раздел 9) и SFTP-режимом:

```bash
ssh-copy-id -s -i ~/.ssh/id_ed25519_server.pub lab
```

Если `ssh-copy-id` отсутствует, можно передать открытую часть через уже доверенное соединение:

```bash
ssh alice@server.example.com \
  'umask 077; mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys' \
  < ~/.ssh/id_ed25519_server.pub
```

Здесь `>>` дописывает, а `>` затёр бы старые разрешённые ключи. Повтор этой ручной команды добавляет повторную строку. При последующем редактировании сохраняйте ключи других пользователей и устройств.

### 8.2. Вход по выбранному ключу

```bash
ssh -i ~/.ssh/id_ed25519_server \
  -o IdentitiesOnly=yes \
  alice@server.example.com
```

С портом:

```bash
ssh -p 2222 -i ~/.ssh/id_ed25519_server \
  -o IdentitiesOnly=yes alice@server.example.com
```

`-i` выбирает файл идентичности; `IdentitiesOnly=yes` ограничивает предложение настроенными ключами. При обычной конфигурации это предотвращает перебор всех ключей агента. Если нужно исключить дополнительные `IdentityFile` из других конфигурационных блоков, проверьте `ssh -G` либо используйте отдельную конфигурацию.

Убедиться, что вход не подменяется серверным паролем:

```bash
ssh -i ~/.ssh/id_ed25519_server \
  -o IdentitiesOnly=yes \
  -o PreferredAuthentications=publickey \
  -o PasswordAuthentication=no \
  -o KbdInteractiveAuthentication=no \
  alice@server.example.com
```

Локальная парольная фраза ключа при этом может запрашиваться. `exit` завершает удалённую оболочку. Сочетание Enter, затем `~.` аварийно разрывает интерактивное соединение при стандартном escape-символе.

<a id="client-config"></a>
## 9. Настройка клиента и псевдонимы

Откройте `~/.ssh/config` своим редактором. Добавьте блок, сохранив имеющиеся записи:

```sshconfig
Host lab
    HostName server.example.com
    User alice
    Port 2222
    IdentityFile ~/.ssh/id_ed25519_server
    IdentitiesOnly yes
    ForwardAgent no
    StrictHostKeyChecking ask
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

Теперь достаточно:

```bash
ssh lab
scp ./notes.txt lab:/home/alice/
sftp lab
```

| Настройка | Смысл |
| --- | --- |
| `Host` | Имя или шаблон, который набирают в команде. |
| `HostName` | Настоящее сетевое имя или адрес. |
| `User`, `Port` | Пользователь и порт назначения. |
| `IdentityFile` | Ключ для подключения; может повторяться. |
| `IdentitiesOnly` | Ограничение предлагаемого набора идентичностей. |
| `ForwardAgent` | Доступ удалённой машины к локальному агенту. |
| `IdentityAgent none` | Полное отключение агента для подключения. |
| `StrictHostKeyChecking` | Правила доверия host key. |
| `ServerAliveInterval`, `ServerAliveCountMax` | Проверка ответа сервера через защищённый канал. |
| `ConnectTimeout` | Ограничение ожидания подключения и начального обмена. |
| `BatchMode yes` | Запрет интерактивных запросов аутентификации. |
| `ProxyJump` | Промежуточный SSH-сервер. |
| `Include` | Подключение других файлов конфигурации. |
| `AddKeysToAgent` | Автоматическое добавление ключа в агент. |

Для большинства настроек действует **первое полученное значение**. Поэтому конкретные `Host` обычно располагают раньше общего `Host *`. Некоторые параметры накапливаются, в частности `IdentityFile`. [Правила ssh_config](https://man.openbsd.org/ssh_config).

Проверить итоговую конфигурацию без сетевого подключения:

```bash
ssh -G lab
```

Так можно обнаружить неожиданный порт, пользователя или дополнительные ключи. Вывод содержит ваши реальные адреса и пути — перед публикацией его обезличьте.

Альтернативный файл:

```bash
ssh -F ~/.ssh/config-lab lab
```

Для конкретного диагностического запуска без обычных файлов конфигурации:

```bash
ssh -F none -p 2222 -i ~/.ssh/id_ed25519_server \
  -o IdentitiesOnly=yes -o IdentityAgent=none \
  alice@server.example.com
```

`-F none` не отключает проверку host key. Не помещайте секреты в конфигурацию: она должна содержать пути к ключам, а не их содержимое и не парольные фразы.

### 9.1. Откуда берутся настройки и в каком порядке

`ssh` читает настройки из трёх мест, и для большинства директив побеждает **первое** найденное значение:

1. Параметры командной строки (`-p`, `-i`, `-o ...`).
2. Личный файл `~/.ssh/config`.
3. Общесистемный файл `/etc/ssh/ssh_config` и файлы, которые он подключает (в Debian и Ubuntu — `/etc/ssh/ssh_config.d/*.conf`).

Поэтому параметр из командной строки перекрывает файл, а блок `Host lab` выше по файлу перекрывает `Host *` ниже. Типичная структура личного файла:

```sshconfig
# 1. Подключаемые файлы — в самом начале, чтобы их Host-блоки участвовали в разборе.
Include ~/.ssh/config.d/*.conf

# 2. Конкретные серверы.
Host lab
    HostName server.example.com
    User alice

# 3. Общие значения по умолчанию — в самом конце.
Host *
    IdentitiesOnly yes
    ServerAliveInterval 30
```

`Include` можно писать и внутри блока `Host` или `Match`: тогда подключённые строки действуют только для этого блока. Относительный путь в `Include` считается от `~/.ssh`.

### 9.2. Шаблоны в Host

| Шаблон | Что совпадает | Пример |
| --- | --- | --- |
| `*` | Любая последовательность символов. | `Host *.example.com` — все поддомены. |
| `?` | Ровно один символ. | `Host web?` — `web1`, `webA`, но не `web10`. |
| `!` | Исключение из списка. | `Host *.example.com !bastion.example.com` |
| Список через пробел | Совпадение с любым элементом. | `Host lab lab-ipv4 192.0.2.10` |

`Host` сравнивается с тем именем, которое вы набрали в команде, а не с `HostName`. Исключение `!` работает только вместе с положительным шаблоном в той же строке: строка из одного `!имя` ничего не выбирает.

### 9.3. Условия Match

`Match` выбирает блок по условию, а не только по имени. Блок действует до следующего `Host` или `Match`.

| Условие | Когда истинно |
| --- | --- |
| `host ШАБЛОН` | Имя сервера после подстановки `HostName` совпадает с шаблоном. |
| `originalhost ШАБЛОН` | Имя, набранное в команде, совпадает с шаблоном. |
| `user ШАБЛОН` | Совпадает имя удалённого пользователя. |
| `localuser ШАБЛОН` | Совпадает имя локального пользователя, запустившего `ssh`. |
| `exec "КОМАНДА"` | Команда завершилась с кодом 0. Выполняется оболочкой при каждом разборе конфигурации. |
| `localnetwork СЕТЬ/МАСКА` | У одного из сетевых интерфейсов есть адрес из этой сети. |
| `tagged МЕТКА` | Метка задана директивой `Tag` или параметром `-P`. |
| `command ШАБЛОН` | Совпадает удалённая команда или имя подсистемы, например `sftp`. |
| `sessiontype ТИП` | Тип сеанса: `shell`, `exec`, `subsystem` или `none` (как при `-N`). |
| `version ШАБЛОН` | Совпадает версия самого `ssh`, например `OpenSSH_10.*`. |
| `canonical`, `final` | Только на повторном проходе после канонизации имени. |
| `all` | Всегда. |

Условия можно объединять, и тогда должны выполниться все; отрицание пишется через `!`. Примеры:

```sshconfig
# Дома — напрямую, в остальных сетях — через bastion.
Match host server.example.com !localnetwork 192.0.2.0/24
    ProxyJump bastion

# Отдельный ключ для всех серверов, когда входите пользователем deploy.
Match user deploy
    IdentityFile ~/.ssh/id_ed25519_deploy

# Набор настроек, включаемый вручную: ssh -P debug lab
Match tagged debug
    LogLevel DEBUG2
```

Условие `localnetwork` удобно для ноутбука, который бывает в разных сетях, но адрес сети не является надёжным признаком доверия: его легко получить по DHCP в чужой сети. `exec` выполняет команду при каждом подключении, поэтому вызывайте в нём только быстрые и безопасные программы.

### 9.4. Токены

В некоторых директивах можно подставлять значения текущего подключения:

| Токен | Значение |
| --- | --- |
| `%h` | Имя удалённого сервера (после `HostName`). |
| `%n` | Имя сервера в том виде, в каком его набрали в команде. |
| `%p` | Удалённый порт. |
| `%r` | Удалённый пользователь. |
| `%u` | Локальный пользователь. |
| `%d` | Домашний каталог локального пользователя. |
| `%C` | Хеш от `%l%h%p%r%j`; удобен для имён сокетов. |
| `%l`, `%L` | Локальное имя машины с доменом и без него. |
| `%i` | Числовой идентификатор локального пользователя. |
| `%j` | Содержимое `ProxyJump`. |
| `%k` | Псевдоним ключа сервера (`HostKeyAlias`) или исходное имя. |
| `%%` | Символ `%`. |

Пример: отдельный ключ на каждый сервер без перечисления их вручную.

```sshconfig
Host *.example.com
    IdentityFile ~/.ssh/id_ed25519_%h
    IdentitiesOnly yes
```

Список директив, в которых допустим каждый токен, приведён в разделе TOKENS справки `man ssh_config`.

### 9.5. Справочник часто нужных директив ssh_config

Значения по умолчанию указаны по справке OpenSSH 10.2; дистрибутив может менять их в `/etc/ssh/ssh_config` (например, Debian и Ubuntu включают там `SendEnv LANG LC_* COLORTERM NO_COLOR` и `HashKnownHosts yes`). Итоговые значения для конкретного сервера всегда показывает `ssh -G ИМЯ`.

**Куда и как подключаться**

| Директива | Значения и умолчание | Что делает |
| --- | --- | --- |
| `HostName` | имя или адрес | Настоящий адрес сервера для псевдонима `Host`. |
| `User` | имя | Удалённый пользователь; по умолчанию — ваш локальный логин. |
| `Port` | число, по умолчанию `22` | Порт сервера. |
| `AddressFamily` | `any` (умолчание), `inet`, `inet6` | Только IPv4 (`inet`) или только IPv6 (`inet6`), как `-4` / `-6`. |
| `BindAddress`, `BindInterface` | адрес / интерфейс | Исходящий адрес или интерфейс, как `-b` / `-B`. |
| `ConnectTimeout` | секунды | Сколько ждать установления соединения; без неё действует системный таймаут TCP. |
| `ConnectionAttempts` | число, по умолчанию `1` | Число попыток подключения с паузой в секунду. |
| `ProxyJump` | `[пользователь@]узел[:порт]`, список через запятую или `none` | Подключение через промежуточный сервер (раздел 17). |
| `ProxyCommand` | команда или `none` | Своя программа для соединения; её stdin/stdout становятся каналом SSH. Пример: `ProxyCommand ssh -W %h:%p bastion`. |
| `CanonicalizeHostname` | `no` (умолчание), `yes`, `always` | Дописывать к короткому имени домены из `CanonicalDomains`. |

**Аутентификация**

| Директива | Значения и умолчание | Что делает |
| --- | --- | --- |
| `IdentityFile` | путь, можно несколько | Ключ для входа; без указания пробуются `~/.ssh/id_ed25519`, `id_ecdsa`, `id_rsa` и их `-sk`-варианты. |
| `IdentitiesOnly` | `no` (умолчание), `yes` | Предлагать только ключи из `IdentityFile` и `-i`, даже если в агенте есть другие. |
| `IdentityAgent` | путь к сокету, `SSH_AUTH_SOCK` или `none` | Какой агент использовать; `none` — без агента. |
| `AddKeysToAgent` | `no` (умолчание), `yes`, `ask`, `confirm`, интервал | После разблокировки ключа добавить его в агент; интервал вроде `1h` задаёт срок жизни, `confirm` требует подтверждать каждое использование. |
| `CertificateFile` | путь | Пользовательский сертификат (раздел 22). |

| `KbdInteractiveAuthentication` | `yes` (умолчание), `no` | Интерактивные запросы сервера (одноразовые коды, PAM). |
| `NumberOfPasswordPrompts` | число, по умолчанию `3` | Сколько раз спрашивать пароль. |
| `BatchMode` | `no` (умолчание), `yes` | Никогда не задавать вопросов: ни пароля, ни фразы, ни подтверждения ключа сервера. |

**Проверка сервера**

| Директива | Значения и умолчание | Что делает |
| --- | --- | --- |
| `StrictHostKeyChecking` | `ask` (умолчание), `yes`, `accept-new`, `no` / `off` | Политика для нового или изменившегося ключа сервера (раздел 7). |
| `UserKnownHostsFile` | пути, по умолчанию `~/.ssh/known_hosts ~/.ssh/known_hosts2` | Где хранить доверенные ключи серверов. |
| `HashKnownHosts` | `no` (умолчание в OpenSSH), `yes` | Хешировать имена в новых записях. |
| `UpdateHostKeys` | `yes`, `no`, `ask` | Принимать от уже проверенного сервера его дополнительные и новые ключи. Включено, если вы не меняли `UserKnownHostsFile` и не включали `VerifyHostKeyDNS`. |
| `HostKeyAlias` | имя | Под каким именем искать ключ в `known_hosts`; полезно для одного сервера с несколькими адресами. |
| `CheckHostIP` | `no` (умолчание), `yes` | Дополнительно проверять ключ по IP-адресу. |
| `VerifyHostKeyDNS` | `no` (умолчание), `yes`, `ask` | Проверять ключ по DNS-записям SSHFP; без DNSSEC это слабая гарантия. |
| `VisualHostKey` | `no` (умолчание), `yes` | Показывать отпечаток ключа сервера картинкой из символов. |
| `RequiredRSASize` | бит, по умолчанию `1024` | Минимальный размер RSA-ключа; можно только увеличить. |

**Сеанс и терминал**

| Директива | Значения и умолчание | Что делает |
| --- | --- | --- |

| `RemoteCommand` | команда | Команда на сервере вместо оболочки, например `tmux new -A -s main`. |

**Алгоритмы**

| Директива | Что задаёт |
| --- | --- |
| `KexAlgorithms` | Обмен ключами сеанса. |
| `Ciphers` | Шифры канала. |
| `MACs` | Контроль целостности. |
| `HostKeyAlgorithms` | Типы ключей сервера, которые клиент готов принять. |
| `PubkeyAcceptedAlgorithms` | Типы подписей пользовательских ключей. |
| `WarnWeakCrypto` | Предупреждения о слабых алгоритмах; `no-pq-kex` отключает только предупреждение о непостквантовом обмене. |

Списки алгоритмов принимают префиксы: `+` добавляет к списку по умолчанию, `-` убирает из него, `^` ставит в начало. Например, `HostKeyAlgorithms +ssh-rsa` временно добавит устаревший алгоритм для одного старого устройства, не заменяя остальной список. Такие исключения пишите только в блок этого устройства, а не в `Host *`.

`IgnoreUnknown` перечисляет директивы, которые старая версия `ssh` должна пропустить без ошибки `Bad configuration option`; это удобно, если один файл используется на машинах с разными версиями OpenSSH.

### 9.6. Постквантовый обмен ключами

В OpenSSH 10 первым в списке `KexAlgorithms` стоит гибридный постквантовый алгоритм `mlkem768x25519-sha256`. Он защищает записанный сегодня трафик от расшифровки будущими квантовыми компьютерами. Начиная с 10.1 клиент предупреждает, если сервер не поддерживает постквантовый обмен. Это повод обновить сервер, а не отключать предупреждение.

Проверить, какой алгоритм выбран:

```bash
ssh -v lab exit 2>&1 | grep 'kex: algorithm'
```

Строка вида `kex: algorithm: mlkem768x25519-sha256` означает постквантовый обмен. На старом сервере будет, например, `curve25519-sha256`.

<a id="github"></a>
## 10. GitHub и несколько аккаунтов

### 10.1. Добавление открытого ключа

Покажите открытую часть:

```bash
cat ~/.ssh/id_ed25519_github.pub
```

На GitHub откройте **Settings → SSH and GPG keys → New SSH key**. Укажите понятное название устройства, тип **Authentication Key**, вставьте одну полную строку `.pub`. Комментарий после ключа не обязан совпадать с email аккаунта. [Добавление ключа](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/adding-a-new-ssh-key-to-your-github-account).

### 10.2. Псевдоним для аккаунта

```sshconfig
Host github-personal
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_github
    IdentitiesOnly yes
    ForwardAgent no
```

Проверка:

```bash
ssh -T git@github-personal
```

У GitHub SSH-пользователь — всегда `git`; аккаунт определяется предъявленным ключом. Успешный ответ приветствует ваш логин и сообщает об отсутствии shell-доступа. При таком успешном тесте GitHub использует код завершения `1`, что не следует путать с отказом аутентификации. [Проверка соединения](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/testing-your-ssh-connection).

Клонирование и настройка уже существующего репозитория:

```bash
git clone git@github-personal:OWNER/REPOSITORY.git
```

```bash
git remote set-url origin git@github-personal:OWNER/REPOSITORY.git
git ls-remote --heads origin
```

Последние команды выполняются внутри нужного локального репозитория. В SSH URL нет токена. `OWNER` может быть владельцем другого аккаунта или организацией: право доступа определяется настройками репозитория.

### 10.3. Два аккаунта

Создайте второй ключ с другим именем и добавьте его во второй аккаунт:

```bash
ssh-keygen -t ed25519 -a 100 \
  -f ~/.ssh/id_ed25519_github_work \
  -C "github-work-laptop"
```

```sshconfig
Host github-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_github_work
    IdentitiesOnly yes
    ForwardAgent no
```

```bash
ssh -T git@github-personal
ssh -T git@github-work
git clone git@github-work:WORK_OWNER/REPOSITORY.git
```

Проверьте логин в каждом приветствии. Не пытайтесь прикрепить одну и ту же личную SSH-пару к двум разным GitHub-аккаунтам — используйте независимые пары.

### 10.4. Автор коммита — отдельная настройка

SSH определяет доступ к репозиторию, но не автора коммита. Внутри каждого клона задайте имя и **свой точный GitHub noreply-адрес из Settings → Emails**:

```bash
git config user.name "YOUR_LOGIN"
git config user.email "YOUR_GITHUB_NOREPLY_ADDRESS"
```

Вторая строка содержит заполнитель: замените его настоящим noreply-адресом перед выполнением. Не подставляйте личную почту в публичные примеры. Обычно современный адрес имеет форму `ID+LOGIN@users.noreply.github.com`; его следует скопировать из настроек, а не угадывать. [Справка GitHub об email](https://docs.github.com/en/account-and-profile/reference/email-addresses-reference).

### 10.5. Если сеть блокирует порт 22

Для GitHub.com доступен специальный SSH endpoint на TCP 443:

```sshconfig
Host github-personal-443
    HostName ssh.github.com
    Port 443
    User git
    IdentityFile ~/.ssh/id_ed25519_github
    IdentitiesOnly yes
    ForwardAgent no
```

```bash
ssh -T git@github-personal-443
git clone git@github-personal-443:OWNER/REPOSITORY.git
```

Это SSH на порту 443, а не превращение протокола в HTTPS. HTTPS-прокси может его блокировать. Используется `ssh.github.com`, а не `github.com:443`; для Enterprise действуют отдельные ограничения. [Официальная инструкция](https://docs.github.com/en/authentication/troubleshooting-ssh/using-ssh-over-the-https-port).

## 11. SSH-агент

Агент позволяет разблокировать программный ключ один раз и затем выполнять подписи без повторного ввода фразы. Он хранит доступную для использования идентичность, а не превращает серверный вход в парольный.

Проверить, доступен ли агент, и увидеть только отпечатки:

```bash
ssh-add -l
```

Если агента нет и его не предоставляет графическая сессия, запустите его для текущей оболочки:

```bash
eval "$(ssh-agent -s)"
```

Не добавляйте безусловный запуск в каждый shell startup-файл: иначе можно создавать множество ненужных агентов.

Загрузить ключ на один час:

```bash
ssh-add -t 1h ~/.ssh/id_ed25519_github
```

Показать открытые части, удалить одну идентичность или все загруженные идентичности:

```bash
ssh-add -L
ssh-add -d ~/.ssh/id_ed25519_github.pub
ssh-add -D
```

Удаление из агента не удаляет файлы и не отзывает ключ на GitHub. `-t` ограничивает доступность загруженного ключа, но не завершает уже открытые SSH-сессии. При необходимости используйте `ssh-add -c` для подтверждения операций: это требует работоспособного механизма `ssh-askpass`. [ssh-add](https://man.openbsd.org/ssh-add), [ssh-agent](https://man.openbsd.org/ssh-agent).

Чтобы запросить парольную фразу напрямую и обойти агент:

```bash
ssh -o IdentityAgent=none -i ~/.ssh/id_ed25519_github \
  -o IdentitiesOnly=yes -T git@github.com
```

`ForwardAgent no` и `IdentityAgent none` различаются: первое запрещает прокидывать агент на удалённую машину, второе отключает его использование самим клиентом. `ssh -A` не копирует закрытый ключ на сервер, но предоставляет возможность просить локальный агент выполнить подпись. Для доступа через промежуточную машину обычно достаточно `ProxyJump`.

### 11.1. Все параметры ssh-add

| Параметр | Что делает | Пример |
| --- | --- | --- |
| без параметров | Добавить ключи по умолчанию (`~/.ssh/id_ed25519`, `id_ecdsa`, `id_rsa` и `-sk`-варианты). | `ssh-add` |
| `ФАЙЛ ...` | Добавить указанные закрытые ключи. | `ssh-add ~/.ssh/id_ed25519_github` |
| `-t ВРЕМЯ` | Срок жизни ключа в агенте: секунды или формат `30m`, `1h`, `1d`. | `ssh-add -t 30m ~/.ssh/id_ed25519_server` |
| `-c` | Требовать подтверждения каждого использования через окно `ssh-askpass`. | `ssh-add -c ~/.ssh/id_ed25519_server` |
| `-l` | Показать отпечатки загруженных ключей. | `ssh-add -l` |
| `-L` | Показать загруженные открытые ключи целиком. | `ssh-add -L` |
| `-E md5` / `-E sha256` | Хеш для отпечатков в `-l`; по умолчанию `sha256`. | `ssh-add -l -E md5` |
| `-d ФАЙЛ` | Удалить один ключ; указывается файл `.pub` или закрытый файл рядом с ним. | `ssh-add -d ~/.ssh/id_ed25519_github.pub` |
| `-D` | Удалить из агента все ключи. | `ssh-add -D` |
| `-x` / `-X` | Запереть агент паролем / отпереть. Запертый агент не подписывает и не показывает ключи. | `ssh-add -x` |
| `-T ФАЙЛ.pub` | Проверить, что ключ из агента действительно подписывает: агент делает пробную подпись. | `ssh-add -T ~/.ssh/id_ed25519_github.pub` |
| `-h ОГРАНИЧЕНИЕ` | Разрешить ключу работу только с указанными серверами (OpenSSH 8.9+). | см. ниже |
| `-H ФАЙЛ` | Файл `known_hosts`, по которому проверяются серверы в `-h`. | `ssh-add -H ~/.ssh/known_hosts -h ...` |
| `-K` | Загрузить резидентные ключи с FIDO2-токена. | `ssh-add -K` |
| `-S БИБЛИОТЕКА` | Другая библиотека для FIDO-токена вместо встроенной поддержки USB. | редко нужно |
| `-s БИБЛИОТЕКА` / `-e БИБЛИОТЕКА` | Загрузить / выгрузить ключи смарт-карты PKCS#11. | раздел 12.7 |
| `-C` / `-k` | Обрабатывать только сертификаты / только обычные ключи. | `ssh-add -k ~/.ssh/id_ed25519_server` |
| `-N` | Не удалять сертификат из агента автоматически после окончания его срока. | редко нужно |
| `-q` | Не печатать сообщение об успехе. | в скриптах |
| `-v` | Диагностика; до трёх раз. | `ssh-add -vvv` |

Ограничение по назначению защищает пересланный агент. Ключ ниже можно использовать только для входа с вашей машины на `bastion.example.com`, а через него — только на `internal.example.com`:

```bash
ssh-add -t 1h \
  -h bastion.example.com \
  -h 'bastion.example.com>internal.example.com' \
  ~/.ssh/id_ed25519_internal
```

Серверы опознаются по их ключам из `known_hosts`, поэтому обе машины должны быть уже проверены. Для серверов, которые предъявляют сертификат хоста (раздел 22.1.1), проверьте ограничение заранее: при проверке этого руководства на OpenSSH 10.2 такая связка ключ отклонила. Поддержка нужна и на промежуточном сервере. Даже с ограничениями пересылку агента включайте только на доверенные машины: администратор промежуточного сервера всё равно сможет воспользоваться ключом в разрешённых пределах, пока вы подключены.

Запереть агент на время отлучки и отпереть по возвращении:

```bash
ssh-add -x
ssh-add -X
```

### 11.2. Все параметры ssh-agent

Обычно агент запускает графическая сессия или systemd, и вручную он нужен редко.

| Параметр | Что делает |
| --- | --- |
| `-s` / `-c` | Вывести команды настройки переменных для sh/bash/zsh или для csh; обычно выбирается автоматически. |
| `-t ВРЕМЯ` | Срок жизни ключей по умолчанию; `ssh-add -t` для отдельного ключа важнее. Без параметра — бессрочно. |
| `-a ПУТЬ` | Явный путь к сокету агента. |
| `-T` | Создать сокет во временном каталоге `$TMPDIR/ssh-XXXXXXXXXX/` вместо каталога по умолчанию. |
| `-k` | Завершить агент, указанный в `SSH_AGENT_PID`. |
| `-D` | Работать на переднем плане, не уходя в фон. |
| `-d` | Режим отладки: на переднем плане с подробным выводом. |
| `-E md5` / `-E sha256` | Хеш отпечатков в сообщениях. |
| `-P СПИСОК` | Из каких каталогов разрешено загружать библиотеки PKCS#11 и FIDO; по умолчанию `/usr/lib*/*,/usr/local/lib*/*`. |
| `-O allow-remote-pkcs11` | Разрешить загрузку библиотек через пересланный агент; по умолчанию только локально. |
| `-O no-restrict-websafe` | Разрешить подписи FIDO-ключами, которые похожи на вход на сайт. По умолчанию запрещено: пересланный агент не должен давать доступ к вашим веб-аккаунтам. |
| `-U` / `-u` | Не убирать / только убрать старые сокеты в `~/.ssh/agent/`. |
| `КОМАНДА` | Запустить команду под агентом; агент завершится вместе с ней. |

Примеры:

```bash
eval "$(ssh-agent -s -t 1h)"
ssh-agent bash
eval "$(ssh-agent -k)"
```

Первая команда запускает агент с часовым сроком для ключей, вторая открывает новую оболочку со своим агентом (он закроется при `exit`), третья завершает агент текущей оболочки и очищает переменные. В OpenSSH 10.1 и новее сокет агента по умолчанию создаётся в `~/.ssh/agent/`, а не в `/tmp`.

## 12. Аппаратный FIDO2-токен и YubiKey

### 12.1. Что требуется

Нужен аппаратный аутентификатор, поддерживающий используемый OpenSSH механизм FIDO и выбранный алгоритм. Наличие USB-разъёма или поддержки входа на сайты само по себе не гарантирует поддержку `ed25519-sk`. Клиентская сборка OpenSSH должна включать соответствующую поддержку; аппаратные SSH-ключи появились в OpenSSH 8.2.

Проверьте версию и доступные типы:

```bash
ssh -V
ssh -Q key
```

В списке ищите типы с `sk-`, например `sk-ssh-ed25519@openssh.com`. Это показывает возможности программы, но не подтверждает возможности конкретного токена.

Токен содержит неэкспортируемый секрет устройства; локальный файл содержит материал, необходимый для обращения к ключу. Для обычного, нерезидентного варианта нужны **и токен, и локальный файл**. Парольная фраза файла, PIN токена и касание выполняют разные задачи. [Поддержка аппаратных ключей GitHub](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent).

### 12.2. Создание с PIN и касанием

Сначала настройте FIDO2 PIN в официальной программе производителя. Если токен уже используется, учитывайте действующие настройки; сброс FIDO может удалить зарегистрированные учётные данные. Не выполняйте reset ради обычной смены PIN.

Подключите токен и выполните:

```bash
ssh-keygen -t ed25519-sk -a 100 -O verify-required \
  -f ~/.ssh/id_ed25519_sk_github \
  -C "github-fido-laptop"
```

Подтвердите операцию на токене и задайте парольную фразу локального файла. `verify-required` запрашивает проверку пользователя токеном, обычно PIN. Касание требуется по умолчанию. Поддержка конкретной проверки зависит от токена и программного обеспечения.

Если токен не поддерживает Ed25519-SK, совместимый вариант:

```bash
ssh-keygen -t ecdsa-sk -a 100 -O verify-required \
  -f ~/.ssh/id_ecdsa_sk_github \
  -C "github-fido-laptop"
```

Добавьте соответствующий `.pub` в GitHub как **Authentication Key**, как и для программного ключа.

```sshconfig
Host github-fido
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_sk_github
    IdentitiesOnly yes
    ForwardAgent no
    IdentityAgent none
```

Если создали `ecdsa-sk`, измените `IdentityFile`. Проверка и использование:

```bash
ssh -T git@github-fido
git clone git@github-fido:OWNER/REPOSITORY.git
```

Установка `IdentityAgent none` — строгий вариант без агента. При обычном агенте требования токена к пользовательскому подтверждению не следует считать отключёнными: агент не превращает аппаратный ключ в экспортируемый программный.

### 12.3. Резидентный ключ

Это отдельный вариант для переноса доступа между компьютерами. Дескриптор ключа хранится на самом токене:

```bash
ssh-keygen -t ed25519-sk -O resident -O verify-required \
  -O application=ssh:github-guide -O user=portable-key \
  -a 100 -f ~/.ssh/id_ed25519_sk_portable \
  -C "github-fido-portable"
```

Устройство должно поддерживать resident credentials. `application` начинается с `ssh:` и различает назначение, `user` задаёт метку резидентной записи. Эти строки не должны содержать личные данные.

На другом доверенном компьютере получить локальные файлы можно в **новом пустом защищённом каталоге**:

```bash
umask 077
mkdir ~/ssh-fido-import
cd ~/ssh-fido-import
ssh-keygen -K
```

Посмотрите созданные имена через `ls -la`, назначьте парольную фразу нужному файлу через `ssh-keygen -p -a 100 -f ПУТЬ` и аккуратно разместите его в `~/.ssh`. Не импортируйте поверх существующих файлов. `ssh-add -K` загружает резидентные ключи в агент; на системах с другим вариантом `ssh-add` сначала проверьте локальную справку.

Нерезидентный вариант лучше разделяет устройство и локальный файл. Резидентный удобнее переносить, но украденный токен содержит больше необходимой для доступа информации. PIN и правила подтверждения остаются важны. [Модель FIDO в OpenSSH](https://man.openbsd.org/ssh-keygen#FIDO_AUTHENTICATOR).

### 12.4. Дополнительные параметры FIDO

| Настройка | Применение |
| --- | --- |
| `-O verify-required` | Проверка пользователя при подписи. |
| `-O resident` | Хранение дескриптора на токене. |
| `-O application=ssh:...` | Разделение назначений. |
| `-O user=...` | Метка резидентной записи. |
| `-O device=...` | Выбор устройства; синтаксис зависит от платформы. |
| `-w ПУТЬ` | Внешний FIDO provider при специальной интеграции. |
| `-O no-touch-required` | Снятие требования касания; не включайте ради удобства личного доступа. |
| `-O write-attestation=ПУТЬ` | Сохранение аттестации; может раскрывать сведения об устройстве. |
| `-O challenge=ПУТЬ` | Свой challenge для регистрации вместо случайного; нужен только для проверки аттестации. |

Не каждый параметр поддерживается каждой версией: `verify-required` появился в OpenSSH 8.4, загрузка резидентных ключей `ssh-keygen -K` — в 8.3. Пример `verify-required` относится к FIDO; добавление его к обычному `ed25519` не создаёт аппаратной защиты.

### 12.5. Резервный доступ

Создайте независимый ключ на втором токене и добавьте его в аккаунт заранее. Скопировать неэкспортируемый секрет первого токена на второй обычной командой нельзя. Для нерезидентного ключа защищённая копия локального файла также нужна; сам файл без рабочего токена не восстановит доступ.

Отдельно настройте восстановление веб-доступа к GitHub. Потеря SSH-токена не должна одновременно лишать вас всех способов войти в настройки аккаунта. Регистрация токена как passkey/2FA для сайта и создание SSH-SK ключа — разные операции.

### 12.6. YubiKey: модели, подготовка и обслуживание

YubiKey — распространённый аппаратный токен компании Yubico. Для SSH у него есть три независимых механизма: **FIDO2** (ключи `-sk`, описанные выше), **PIV** (смарт-карта, работа через PKCS#11) и **OpenPGP** (через `gpg-agent`). Для нового доступа к Linux и GitHub проще и надёжнее всего FIDO2.

**Какая модель подходит**

| Модель | FIDO2 для SSH | PIV и OpenPGP |
| --- | --- | --- |
| YubiKey 5 Series (5 NFC, 5C NFC, 5Ci, 5 Nano и др.) | да | да |
| Security Key Series | да | нет: только FIDO |
| YubiKey Bio Series | да; PIN заменяется отпечатком пальца | нет |
| YubiKey 5 FIPS Series | да, с ограничениями режима FIPS | да |

**Что зависит от прошивки**

| Версия прошивки | Что важно для SSH |
| --- | --- |
| ниже 5.2.3 | Только `ecdsa-sk`; резидентные ключи недоступны. |
| 5.2.3 и выше | `ed25519-sk` и резидентные ключи (`-O resident`), которым нужен FIDO2 PIN. |
| ниже 5.7 | До 25 резидентных учётных записей FIDO2. Уязвимость YSA-2024-03 в ECDSA (см. ниже). |
| 5.7 и выше | До 100 резидентных учётных записей; PIV с RSA 3072 и 4096; уязвимость YSA-2024-03 исправлена. |

Прошивку YubiKey **нельзя обновить**: она записывается на заводе. Новые возможности или исправления требуют нового ключа. Узнать модель и версию:

```bash
ykman info
```

**Установка программ в Debian и Ubuntu**

```bash
sudo apt install yubikey-manager
ykman --version
```

`ykman` — официальная консольная утилита Yubico. Для FIDO2-ключей SSH она не обязательна, но нужна для настройки PIN, просмотра и удаления учётных записей. Для PIV и OpenPGP дополнительно нужен сервис смарт-карт `pcscd`: `sudo apt install pcscd`.

**Доступ к устройству в Linux**

В современных Debian и Ubuntu локальный пользователь графической сессии получает доступ к FIDO-устройству автоматически. Если `ssh-keygen` пишет, что устройство не найдено, проверьте по шагам:

```bash
lsusb | grep -i yubico
ls -l /dev/hidraw*
ykman fido info
```

Первая команда должна показать устройство Yubico, вторая — файлы `hidraw`. Если устройство видно, но доступа нет, установите пакет правил `libfido2-1` (или `libu2f-udev` в старых выпусках), отключите и снова подключите ключ. Не меняйте права на `/dev/hidraw*` вручную через `chmod 666`: так доступ получат все пользователи машины.

**FIDO2 PIN**

У нового YubiKey PIN для FIDO2 не задан. Задайте его до создания ключей с `verify-required` и резидентных ключей:

```bash
ykman fido access change-pin
```

Программа сама спросит текущий PIN (если он есть) и новый. Не передавайте PIN параметрами `--pin` и `--new-pin` в командной строке: он останется в истории оболочки и будет виден в списке процессов. PIN FIDO2 — от 4 символов (у части моделей минимум больше), до 63 байт.

| Ошибочных вводов PIN подряд | Что происходит |
| --- | --- |
| 3 | Ключ перестаёт принимать PIN, пока его не отключат и не подключат снова. |
| 8 | Функция FIDO2 блокируется; вернуть её можно только сбросом, который удаляет все учётные записи FIDO. |

Правильный ввод снова возвращает счётчик к 8. Сколько попыток осталось, показывает `ykman fido info`.

**Создание SSH-ключа на YubiKey**

Команды те же, что в разделах 12.2 и 12.3:

```bash
ssh-keygen -t ed25519-sk -O resident -O verify-required \
  -O application=ssh:github -f ~/.ssh/id_ed25519_sk_github -C "yubikey-github"
```

Во время создания YubiKey попросит PIN и касание: металлический контакт или кнопка мигает — коснитесь его. У YubiKey Bio вместо PIN приложите зарегистрированный палец. Для прошивки ниже 5.2.3 замените `ed25519-sk` на `ecdsa-sk` и уберите `-O resident`. Разные значения `application=ssh:...` позволяют хранить на одном ключе несколько резидентных SSH-ключей: одинаковое значение перезапишет прежнюю запись.

**Просмотр и удаление учётных записей**

```bash
ykman fido credentials list
ykman fido credentials delete ЧАСТЬ_ИДЕНТИФИКАТОРА
```

`list` показывает резидентные учётные записи, в том числе SSH-ключи с `application=ssh:...` и passkey сайтов. `delete` принимает уникальную часть идентификатора из списка и удаляет одну запись; перед этим уберите соответствующий открытый ключ из GitHub и `authorized_keys`. Обычные нерезидентные ключи на YubiKey не хранятся и в этом списке не видны: для отказа от них достаточно отозвать открытую часть и удалить локальный файл.

**Сброс FIDO**

```bash
ykman fido reset
```

Сброс удаляет **все** учётные записи FIDO2 и U2F на ключе, включая входы на сайты, и снимает PIN. Его выполняют в первые секунды после подключения ключа и подтверждают касанием. PIV и OpenPGP при этом не затрагиваются. Используйте сброс, только если PIN заблокирован или ключ передаётся другому человеку.

**Если YubiKey потерян**

1. С другого устройства или резервным YubiKey удалите открытые SSH-ключи потерянного токена из GitHub и всех `authorized_keys`.
2. Удалите потерянный ключ из списка ключей безопасности и passkey в аккаунтах сайтов.
3. Проверьте журналы входа.

Именно поэтому заранее держите второй YubiKey с независимыми ключами, зарегистрированными везде.

**Уязвимость YSA-2024-03**

В прошивках YubiKey 5 и Security Key ниже 5.7 найдена уязвимость по побочному каналу в реализации ECDSA. Для атаки нужен физический доступ к самому ключу, специальное оборудование и значительные ресурсы, поэтому Yubico оценивает её как умеренную. Для SSH на таких ключах предпочитайте `ed25519-sk` вместо `ecdsa-sk` и не оставляйте ключ без присмотра. Ключи с прошивкой 5.7 и новее не затронуты. [Бюллетень Yubico](https://www.yubico.com/support/security-advisories/ysa-2024-03/).

### 12.7. YubiKey через PIV и PKCS#11

PIV подходит для систем, где нет поддержки `-sk`-ключей, например для старых серверов и сетевого оборудования. Ключ генерируется внутри YubiKey, а `ssh` обращается к нему через библиотеку `libykcs11`.

Сначала смените заводские PIN (`123456`), PUK (`12345678`) и ключ управления. Оставлять их по умолчанию Yubico не рекомендует:

```bash
ykman piv access change-pin
ykman piv access change-puk
ykman piv access change-management-key --generate --protect
```

PIN и PUK для PIV — от 6 до 8 символов; Yubico советует цифровые значения ради совместимости. По умолчанию три неверных PIN подряд блокируют PIN, разблокировать его можно PUK; после трёх неверных PUK остаётся только сброс PIV (`ykman piv reset`), удаляющий ключи и сертификаты PIV.

Создайте ключ в слоте `9a` с запросом PIN и касания и сохраните открытую часть:

```bash
ykman piv keys generate --algorithm ECCP256 \
  --pin-policy ONCE --touch-policy ALWAYS 9a public.pem
ykman piv certificates generate --subject "CN=SSH key" 9a public.pem
```

`--pin-policy ONCE` спрашивает PIN один раз за сеанс, `--touch-policy ALWAYS` требует касания при каждой подписи. Сертификат нужен библиотеке PKCS#11, чтобы найти ключ; сервер SSH его не проверяет. На прошивке ниже 5.7 вместо `ECCP256` используйте `RSA2048` (см. YSA-2024-03). На 5.7 и выше `ykman` умеет создавать также `RSA3072`, `RSA4096` и `ED25519`, но работу Ed25519 через PKCS#11 проверьте со своими версиями OpenSSH и `libykcs11`, прежде чем полагаться на неё.

Найти библиотеку и получить открытый ключ в формате SSH:

```bash
ls /usr/lib/*/libykcs11.so* /usr/local/lib/libykcs11.so* 2>/dev/null
ssh-keygen -D /usr/lib/x86_64-linux-gnu/libykcs11.so -e
```

Путь к библиотеке зависит от дистрибутива и архитектуры; подставьте найденный. Вторая команда печатает открытые ключи всех занятых слотов, по одному в строке. Нужную строку добавьте в `authorized_keys` или в GitHub. Вход:

```bash
ssh -I /usr/lib/x86_64-linux-gnu/libykcs11.so alice@server.example.com
```

То же в конфигурации и через агент:

```sshconfig
Host lab-piv
    HostName server.example.com
    User alice
    PKCS11Provider /usr/lib/x86_64-linux-gnu/libykcs11.so
```

```bash
ssh-add -s /usr/lib/x86_64-linux-gnu/libykcs11.so
ssh-add -L
ssh-add -e /usr/lib/x86_64-linux-gnu/libykcs11.so
```

`ssh-add -s` загружает ключи токена в агент и спрашивает PIN, `-e` выгружает их. Агент принимает библиотеки только из разрешённых каталогов; другой путь нужно явно разрешить параметром `ssh-agent -P`.

### 12.8. YubiKey через OpenPGP

Если YubiKey уже используется для GnuPG, ключ аутентификации OpenPGP можно применять для SSH через `gpg-agent`: в `~/.gnupg/gpg-agent.conf` добавляется `enable-ssh-support`, а `SSH_AUTH_SOCK` указывает на сокет `gpg-agent` (`gpgconf --list-dirs agent-ssh-socket`). Это отдельная экосистема со своими PIN и правилами; если GnuPG вам не нужен по другим причинам, выбирайте FIDO2. [Руководство Yubico по OpenPGP](https://developers.yubico.com/PGP/).

Официальные инструкции Yubico: [SSH с FIDO2](https://developers.yubico.com/SSH/Securing_SSH_with_FIDO2.html), [команды ykman fido](https://docs.yubico.com/software/yubikey/tools/ykman/FIDO_Commands.html), [SSH через PIV](https://developers.yubico.com/PIV/Guides/SSH_with_PIV_and_PKCS11.html), [обзор прошивок](https://docs.yubico.com/hardware/yubikey/yk-tech-manual/yk5-firmware-overview.html).

## 13. GitHub PAT: отдельный способ доступа

PAT нужен для определённых операций API или Git по HTTPS. Он **не передаётся** в `ssh -i`, не добавляется в `authorized_keys` и не заменяет PIN аппаратного токена. Успешный `git push` через SSH также не авторизует автоматически отдельный запрос к REST API.

Если нужен PAT, в GitHub откройте **Settings → Developer settings → Personal access tokens**. Предпочитайте fine-grained token с выбранным владельцем ресурсов, конкретными репозиториями, минимальными разрешениями и сроком действия. Для чтения содержимого нужен соответствующий доступ на чтение; для записи — на запись. Организация может требовать одобрения. Не выдавайте полномочия администратора ради обычного клонирования. [Управление PAT](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

Пример HTTPS URL без секрета:

```bash
git clone https://github.com/OWNER/REPOSITORY.git
```

При прямом интерактивном запросе Git для приватного репозитория имя пользователя — логин GitHub, а в поле пароля используется PAT. Если уже настроен credential manager, он может провести вход по собственному сценарию и не показывать этот запрос.

Для повседневной работы используйте Git Credential Manager с поддерживаемым защищённым хранилищем вашей Linux-сессии. Не считайте `credential.helper store` шифрованным хранилищем: он записывает секрет на диск открытым текстом. Не вставляйте PAT в URL, команды, `.git/config`, логи и README. [Хранение учётных данных GitHub](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git).

Для автоматизации секрет обычно передают процессу через предусмотренное защищённое хранилище CI. Переменная окружения не является абсолютной защитой: секрет нельзя печатать, сериализовать в отчёт, включать в отладочный `set -x` или передавать недоверенному процессу. Не используйте личный PAT с широкими правами, если задачу решает более узкий механизм.

| Задача | Подходящий способ |
| --- | --- |
| Личный Git через SSH | Обычный SSH-ключ или FIDO2 SSH-ключ. |
| Git через HTTPS | Credential manager или PAT с нужными правами. |
| REST API GitHub | Разрешённый API credential, например PAT или GitHub App. |
| Чтение одного репозитория сервером | Отдельный read-only deploy key либо иной узкий сервисный доступ. |
| Вход на сайт | Пароль/passkey и настроенная защита аккаунта; SSH-ключ не заменяет веб-вход. |

<a id="server"></a>
## 14. Настройка SSH-сервера Linux

### 14.1. Установка и проверка

Следующие команды выполняются **на сервере**, а не на компьютере-клиенте. Пример для Debian/Ubuntu с systemd:

```bash
sudo apt update
sudo apt install openssh-server
sudo systemctl status ssh.service
sudo ss -ltnp
```

В других дистрибутивах служба часто называется `sshd.service`; названия пакетов и средства управления firewall отличаются. Проверьте документацию своей системы. Некоторые Ubuntu используют `ssh.socket` для активации; при изменении порта нужно учитывать сокет, а не только конфигурацию демона.

```bash
systemctl status ssh.socket
systemctl cat ssh.service ssh.socket
```

Отсутствие socket unit в другой системе само по себе не ошибка. Открывать SSH всему интернету для использования GitHub не требуется.

### 14.2. Сначала обеспечить второй проверенный вход

Перед отключением паролей:

1. Убедитесь, что есть консоль провайдера или другой способ восстановить доступ.
2. Создайте обычного пользователя с нужными административными правами либо используйте существующего.
3. Добавьте его открытый ключ и проверьте `sudo` при необходимости.
4. Оставьте текущую SSH-сессию открытой.
5. Откройте **новое** соединение с принудительной аутентификацией по ключу из раздела 8.
6. Сохраните резервные копии изменяемых файлов конфигурации, включая используемые snippets.

Успешный вход root не доказывает, что после `PermitRootLogin no` получится войти обычным пользователем. Существующая сессия также не доказывает, что новая конфигурация разрешает новые подключения.

Если на новом Debian/Ubuntu-сервере ещё нет нужного пользователя, пример создания из административной сессии:

```bash
sudo adduser alice
sudo usermod -aG sudo alice
```

Замените `alice` выбранным именем; не создавайте повторно существующего пользователя. Вторая команда добавляет административные полномочия и нужна только тому, кто действительно должен администрировать сервер. Не убирайте `-a`: без него изменение дополнительных групп может лишить пользователя прежних членств. Затем войдите как новый пользователь, добавьте его `.pub` и проверьте необходимые действия через `sudo`.

### 14.3. Пример конфигурации только для ключей

После проверки доступа можно применить следующие настройки:

```sshconfig
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
AuthenticationMethods publickey
PermitRootLogin no
X11Forwarding no
AllowAgentForwarding no
```

| Настройка | Назначение |
| --- | --- |
| `PubkeyAuthentication` | Вход по открытым ключам. |
| `PasswordAuthentication` | Метод серверного пароля. |
| `KbdInteractiveAuthentication` | Интерактивные механизмы, включая некоторые PAM/MFA-сценарии. |
| `AuthenticationMethods` | Требуемый набор методов. |
| `PermitRootLogin` | Возможность прямого входа root. |
| `X11Forwarding` | Перенаправление X11. |
| `AllowAgentForwarding` | Перенаправление SSH-агента. |

Это профиль **только для publickey**, не шаблон для сервера с PAM/TOTP: отключение keyboard-interactive может нарушить нужную MFA-схему. Не отключайте `UsePAM` без понимания зависимых механизмов учётных записей и сессий.

Для ограничения списка пользователей существует `AllowUsers`, например `AllowUsers alice deploy`. Добавляйте его только после учёта всех законных пользователей и сервисов. Не копируйте вымышленные имена в рабочую конфигурацию.

Где разместить настройки, зависит от реального `Include`. В стандартной Ubuntu обычно используются `/etc/ssh/sshd_config.d/*.conf`, подключённые в начале основного файла. Имена файлов сортируются, а для большинства директив важно первое значение. Поэтому файл `99-hardening.conf` **не гарантирует**, что перекроет более ранние настройки. Проверьте существующий порядок и итог через `sshd -T`. [Ubuntu: конфигурация OpenSSH](https://ubuntu.com/server/docs/how-to/security/openssh-server/), [sshd_config](https://man.openbsd.org/sshd_config).

### 14.4. Проверка и применение

Сначала проверить синтаксис:

```bash
sudo sshd -t
```

Без ошибок команда обычно не выводит ничего. Проверить эффективные параметры:

```bash
sudo sshd -T
```

При использовании блоков `Match` проверяйте конкретный контекст входа, заменив заполнители:

```bash
sudo sshd -T -C user=alice,host=client.example.com,addr=192.0.2.50
```

`-t` проверяет конфигурацию и необходимые серверные файлы; `-T` показывает рассчитанные настройки; `-C` задаёт условия подключения для проверки `Match`. Дополнительные условия вроде локального адреса и порта также задаются при необходимости. [sshd(8)](https://man.openbsd.org/sshd).

Только после успешной проверки перечитайте конфигурацию соответствующей службы:

```bash
sudo sshd -t && sudo systemctl reload ssh.service
```

Если unit называется иначе, используйте его действительное имя. Не заменяйте ошибку проверки безусловным restart. После применения откройте новое соединение и подтвердите ожидаемый способ входа, прежде чем закрывать старое.

### 14.5. Сеть и порт

Доступ зависит одновременно от слушающего сокета, локального firewall, облачных правил и NAT. Замена порта с 22 на 2222 уменьшает часть шума сканирования, но не заменяет ключи, обновления и проверку host key.

Для системы, где **уже используется UFW**, можно посмотреть действующие правила:

```bash
sudo ufw status verbose
```

Пример разрешения SSH только с документального клиентского адреса:

```bash
sudo ufw allow from 192.0.2.50 to any port 22 proto tcp
```

Перед выполнением замените адрес своим доверенным источником и учтите IPv6. Это добавляет правило, но не удаляет ранее существовавшее более широкое разрешение. Не включайте и не сбрасывайте firewall удалённо без проверки всей политики и резервного доступа.

### 14.6. Смена порта на Ubuntu с ssh.socket

В Ubuntu 24.04 и новее SSH по умолчанию запускается через `ssh.socket`: порт слушает systemd, а `sshd` стартует при подключении. Генератор `sshd-socket-generator` читает `Port` и `ListenAddress` из `sshd_config` и сам настраивает сокет. Поэтому порт меняется так:

1. Откройте новый порт в firewall и облачных правилах, **не закрывая** старый.
2. Укажите порт в файле из `/etc/ssh/sshd_config.d/`, например `Port 2222` в `/etc/ssh/sshd_config.d/10-port.conf`.
3. Проверьте и примените:

```bash
sudo sshd -t
sudo systemctl daemon-reload
sudo systemctl restart ssh.socket
sudo ss -ltnp | grep -E ':22|:2222'
```

4. В **новом** терминале проверьте вход: `ssh -p 2222 alice@server.example.com`.
5. Только после этого закройте старый порт в firewall.

Узнать, как запускается SSH на вашей системе:

```bash
systemctl is-enabled ssh.socket ssh.service
```

Если включён `ssh.service`, а `ssh.socket` выключен или отсутствует, используется обычная служба: после `sshd -t` достаточно `sudo systemctl restart ssh.service`. В Ubuntu 22.10–23.04 генератора ещё не было, и порт задавался переопределением `ListenStream` в `systemctl edit ssh.socket`.

### 14.7. Параметры командной строки sshd

Обычно `sshd` запускает systemd. Вручную эти параметры нужны для проверки и отладки:

| Параметр | Что делает |
| --- | --- |
| `-t` | Проверить синтаксис конфигурации и наличие ключей сервера, затем выйти. |
| `-T` | Проверить конфигурацию и напечатать итоговые значения всех директив. |
| `-G` | Разобрать и напечатать конфигурацию без расширенных проверок ключей. |
| `-C СПЕЦИФИКАЦИЯ` | Условия подключения для `-T` или `-G`: `user=`, `host=`, `addr=`, `laddr=`, `lport=`, `rdomain=`. |
| `-f ФАЙЛ` | Другой конфигурационный файл вместо `/etc/ssh/sshd_config`. |
| `-o Директива=значение` | Задать директиву из командной строки. |
| `-p ПОРТ` | Слушать этот порт; можно несколько раз. |
| `-d` | Отладка: не уходить в фон, обработать одно подключение, печатать подробности; `-dd`, `-ddd` — подробнее. |
| `-D` | Не уходить в фон, но работать как обычно. |
| `-e` | Писать журнал в stderr вместо системного журнала. |
| `-E ФАЙЛ` | Дописывать журнал в файл. |
| `-q` | Ничего не писать в журнал. |
| `-h ФАЙЛ`, `-c ФАЙЛ` | Ключ или сертификат сервера; нужны при запуске не от root. |
| `-g СЕКУНДЫ` | Время на аутентификацию, как `LoginGraceTime`. |
| `-4`, `-6` | Только IPv4 или только IPv6. |
| `-V` | Версия. |

Отладочный экземпляр на отдельном порту, не мешающий основной службе:

```bash
sudo /usr/sbin/sshd -d -p 2299 -o PasswordAuthentication=no
```

Подключитесь из другого терминала через `ssh -p 2299 ...` и читайте, почему сервер принял или отклонил ключ. Экземпляр в режиме `-d` обслуживает **одно** подключение и завершается: если первым к нему обратится `ssh-keyscan` или сканер, ваш вход уже не пройдёт, и экземпляр нужно запустить снова. Клиент спросит подтверждение ключа сервера для `[server.example.com]:2299` — это тот же ключ, что и на основном порту. Если порт закрыт firewall, проверяйте с самого сервера: `ssh -p 2299 alice@127.0.0.1`.

### 14.8. Справочник директив sshd_config

Значения по умолчанию указаны по справке OpenSSH 10.2. В Debian и Ubuntu стандартный `/etc/ssh/sshd_config` переопределяет часть из них: `KbdInteractiveAuthentication no`, `UsePAM yes`, `X11Forwarding yes`, `PrintMotd no`, `AcceptEnv LANG LC_* COLORTERM NO_COLOR`, а облачные образы часто добавляют файл в `sshd_config.d/`. Итоговое значение показывает `sudo sshd -T | grep -i ИМЯ` (имена в выводе строчными буквами).

**Сеть**

| Директива | Значения и умолчание | Что делает |
| --- | --- | --- |
| `Port` | `22` | Порт; можно указать несколько строк. |
| `ListenAddress` | все адреса | Адрес, на котором слушать, например `192.0.2.10` или `[2001:db8::10]:2222`. |
| `AddressFamily` | `any`, `inet`, `inet6` | Только IPv4 или только IPv6. |
| `UseDNS` | `no` | Проверять имя клиента по DNS; при `no` в `from=` и `Match Host` используйте адреса. |

**Вход и аутентификация**

| Директива | Значения и умолчание | Что делает |
| --- | --- | --- |
| `PermitRootLogin` | `prohibit-password` (умолчание), `yes`, `forced-commands-only`, `no` | Вход root: `prohibit-password` — только по ключу, `forced-commands-only` — только ключом с `command=`. |
| `PubkeyAuthentication` | `yes` | Вход по ключу. |
| `PasswordAuthentication` | `yes` | Вход по паролю пользователя. |
| `KbdInteractiveAuthentication` | `yes` (в Debian/Ubuntu `no`) | Интерактивные запросы, через которые работают PAM и одноразовые коды. |
| `AuthenticationMethods` | `any` | Набор обязательных методов. `publickey,keyboard-interactive` — сначала ключ, затем код; несколько наборов через пробел — любой из них. |
| `PermitEmptyPasswords` | `no` | Разрешить вход с пустым паролем. Не включайте. |
| `MaxAuthTries` | `6` | Попыток аутентификации за одно подключение; после половины неудач они попадают в журнал. |
| `LoginGraceTime` | `120` секунд | Сколько ждать завершения входа. |
| `MaxStartups` | `10:30:100` | Ограничение одновременных неаутентифицированных подключений: с 10 начинать отбрасывать 30 % новых, с 100 — все. |
| `MaxSessions` | `10` | Сеансов в одном соединении (важно для multiplexing). |
| `AuthorizedKeysFile` | `.ssh/authorized_keys .ssh/authorized_keys2` | Где искать разрешённые ключи; путь от домашнего каталога или абсолютный, токены `%h`, `%u`. |
| `StrictModes` | `yes` | Проверять владельца и права файлов пользователя перед входом. |
| `UsePAM` | `no` (в Debian/Ubuntu `yes`) | Использовать PAM для учётных записей и сеансов. Не отключайте без понимания последствий. |
| `TrustedUserCAKeys` | путь | Открытые ключи CA для пользовательских сертификатов (раздел 22). |
| `RevokedKeys` | путь | Список отозванных ключей или KRL. |

**Кто может войти**

| Директива | Что делает |
| --- | --- |
| `AllowUsers alice deploy@192.0.2.*` | Только перечисленные пользователи; форма `пользователь@адрес` ограничивает и источник. |
| `AllowGroups ssh-users` | Только члены групп. |
| `DenyUsers`, `DenyGroups` | Запретить перечисленным. Сначала проверяются запреты, затем разрешения. |

Если указан любой `Allow*`, все остальные пользователи входить не смогут. Перед включением проверьте, что в список попали вы сами и служебные учётные записи.

**Сеанс и перенаправления**

| Директива | Значения и умолчание | Что делает |
| --- | --- | --- |
| `AllowTcpForwarding` | `yes` (умолчание), `all`, `no`, `local`, `remote` | Перенаправление TCP-портов. |
| `AllowStreamLocalForwarding` | `yes`, `all`, `no`, `local`, `remote` | Перенаправление Unix-сокетов. |
| `AllowAgentForwarding` | `yes` | Пересылка агента. |
| `GatewayPorts` | `no` (умолчание), `yes`, `clientspecified` | Доступность портов `-R` для других машин: `no` — только loopback сервера, `clientspecified` — адрес выбирает клиент. |
| `PermitOpen` | `any` | Куда разрешено подключаться через `-L`, например `PermitOpen 127.0.0.1:5432`. |
| `PermitListen` | `any` | Какие порты разрешено открывать через `-R`. |
| `PermitTunnel` | `no` | Устройства `tun` через `-w`. |
| `X11Forwarding` | `no` (в Debian/Ubuntu `yes`) | Пересылка X11. |
| `ClientAliveInterval` | `0` | Как часто проверять клиента; `0` — не проверять. |
| `ClientAliveCountMax` | `3` | Сколько проверок без ответа допустимо. При интервале 15 клиент отключится примерно через 45 секунд тишины. |
| `ChannelTimeout` | нет | Закрывать неактивные каналы, например `session=1h`. |
| `UnusedConnectionTimeout` | нет | Закрывать соединения без открытых каналов. |
| `AcceptEnv` | нет | Какие переменные клиента принимать (`SendEnv`/`SetEnv`). |
| `PermitUserEnvironment` | `no` | Разрешить `environment=` в `authorized_keys` и файл `~/.ssh/environment`. |
| `ForceCommand` | нет | Выполнять только эту команду, что бы ни запросил клиент; `internal-sftp` — только SFTP. |
| `ChrootDirectory` | нет | Запереть пользователя в каталоге после входа. |
| `Subsystem sftp ...` | в Debian/Ubuntu `/usr/lib/openssh/sftp-server` | Программа для SFTP; `internal-sftp` — встроенная. |
| `Banner` | `none` | Текстовый файл, который показывается до входа. |
| `PrintMotd` | `yes` (в Debian/Ubuntu `no`, сообщение выводит PAM) | Показывать `/etc/motd`. |

**Журнал и защита от перебора**

| Директива | Значения и умолчание | Что делает |
| --- | --- | --- |
| `LogLevel` | `INFO` | `VERBOSE` дополнительно записывает отпечаток ключа, которым вошёл пользователь, — удобно для аудита. |
| `SyslogFacility` | `AUTH` | Категория системного журнала. |
| `PerSourcePenalties` | включено | Временно отказывать адресам, с которых были неудачные входы (`authfail`, по умолчанию 5 с), обрывы без входа (`noauth`, 1 с), сбои `sshd` (`crash`, 90 с) и другие нарушения. `no` — выключить. |
| `PerSourcePenaltyExemptList` | нет | Адреса, на которые штрафы не распространяются, например сеть мониторинга. |
| `RefuseConnection` | `no` | В блоке `Match` — немедленно разорвать подключение. |

`PerSourcePenalties` появились в OpenSSH 9.8 и уже снижают эффект перебора паролей. Они не заменяют вход только по ключам и не являются полноценной заменой `fail2ban` для других служб.

### 14.9. Блоки Match на сервере

`Match` применяет директивы только к подходящим подключениям. Блок действует до следующего `Match` или до конца файла, поэтому блоки пишут **в конце** конфигурации. Если директива встречается в нескольких подходящих блоках, действует первая.

| Условие | Пример |
| --- | --- |
| `User` | `Match User deploy` |
| `Group` | `Match Group sftponly` |
| `Address` | `Match Address 192.0.2.0/24,2001:db8::/32` |
| `Host` | `Match Host *.example.com` (нужен `UseDNS yes`) |
| `LocalAddress`, `LocalPort` | `Match LocalPort 2222` |
| `Version` | Совпадение с версией клиента. |
| `Invalid-User` | Имя пользователя не существует. |
| `All` | Все подключения; удобно, чтобы закрыть блок. |

Вход по паролю только из внутренней сети, извне — только по ключу:

```sshconfig
PasswordAuthentication no

Match Address 192.0.2.0/24
    PasswordAuthentication yes
```

Пользователь только для SFTP, запертый в своём каталоге:

```sshconfig
Match Group sftponly
    ChrootDirectory /srv/sftp/%u
    ForceCommand internal-sftp
    AuthorizedKeysFile /etc/ssh/authorized_keys/%u
    AllowTcpForwarding no
    AllowAgentForwarding no
    X11Forwarding no
    PermitTunnel no
```

Подготовка на сервере для пользователя `bob`:

```bash
sudo groupadd sftponly
sudo useradd -M -d /upload -s /usr/sbin/nologin -G sftponly bob
sudo mkdir -p /srv/sftp/bob/upload /etc/ssh/authorized_keys
sudo chown root:root /srv/sftp/bob
sudo chmod 755 /srv/sftp/bob
sudo chown bob:bob /srv/sftp/bob/upload
sudo install -m 644 -o root -g root bob.pub /etc/ssh/authorized_keys/bob
sudo sshd -t
```

Каталог из `ChrootDirectory` и все его родители должны принадлежать root и не быть доступны на запись другим, иначе вход завершится ошибкой. Поэтому писать пользователь может только во вложенный каталог `upload`. Домашний каталог `/upload` указан уже внутри chroot. Ключ хранится вне домашнего каталога: `sshd` ищет его до перехода в chroot. Оболочка `/usr/sbin/nologin` запрещает обычный вход в терминал. Пользователь подключается командой `sftp bob@server.example.com`; `ssh` и туннели для него недоступны.

Проверить, какие настройки получит конкретное подключение:

```bash
sudo sshd -T -C user=bob,host=client.example.com,addr=198.51.100.7 | grep -E 'chrootdirectory|forcecommand|passwordauthentication'
```

## 15. Передача файлов

### 15.1. scp

Отправить файл, получить файл и отправить каталог:

```bash
scp ./notes.txt lab:/home/alice/notes.txt
scp lab:/home/alice/report.txt ./report.txt
scp -r ./documents lab:/home/alice/incoming/
```

Если псевдоним не настроен:

```bash
scp -P 2222 -i ~/.ssh/id_ed25519_server -o IdentitiesOnly=yes \
  ./notes.txt alice@server.example.com:/home/alice/notes.txt
```

| Параметр scp | Что делает | Пример |
| --- | --- | --- |
| `-P ПОРТ` | Порт сервера. Буква **заглавная**: строчная `-p` занята. | `scp -P 2222 file lab:` |
| `-p` | Сохранить время изменения, доступа и права файла. | `scp -p ./script.sh lab:` |
| `-r` | Копировать каталог целиком. Символические ссылки при этом раскрываются. | `scp -r ./site lab:/srv/` |
| `-i ФАЙЛ` | Ключ для входа. | `scp -i ~/.ssh/id_ed25519_server ...` |
| `-F ФАЙЛ` | Другая конфигурация `ssh`. | `scp -F ~/.ssh/config-lab ...` |
| `-o ДИРЕКТИВА` | Любая директива `ssh_config`. | `scp -o ConnectTimeout=10 ...` |
| `-J УЗЕЛ` | Через промежуточный сервер. | `scp -J bastion file internal:` |
| `-3` | Копирование между двумя серверами идёт через ваш компьютер; так по умолчанию. | `scp -3 a:/f b:/f` |
| `-R` | Копирование между двумя серверами напрямую: первый сервер сам подключается ко второму. | `scp -R a:/f b:/f` |
| `-C` | Сжатие; помогает на медленном канале с несжатыми данными. | `scp -C log.txt lab:` |
| `-l КБИТ/С` | Ограничение скорости в килобитах в секунду: `8000` — около 1 МБ/с. | `scp -l 8000 big.iso lab:` |
| `-c ШИФР` | Шифр соединения; обычно не нужен. | `scp -c aes256-gcm@openssh.com ...` |
| `-4`, `-6` | Только IPv4 / только IPv6. | `scp -4 file lab:` |
| `-A` | Переслать агент на сервер; нужно для `-R`, если второй сервер принимает тот же ключ. | `scp -A -R a:/f b:/f` |
| `-B` | Пакетный режим: не спрашивать пароль и фразу. | в скриптах |
| `-q` | Без индикатора хода и предупреждений. | в скриптах |
| `-v` | Подробная диагностика `scp` и `ssh`. | `scp -v file lab:` |
| `-O` | Старый протокол SCP вместо SFTP. Нужен только для серверов без SFTP. | `scp -O file old-router:` |
| `-s` | Явно использовать SFTP (так по умолчанию с OpenSSH 9.0). | `scp -s file lab:` |
| `-T` | Отключить проверку имён файлов, присланных сервером. Небезопасно: используйте только с доверенным сервером. | редко нужно |
| `-X nrequests=N`, `-X buffer=Б` | Число параллельных запросов SFTP (по умолчанию 64) и размер буфера (32 КБ). | `scp -X nrequests=128 ...` |
| `-S ПРОГРАММА` | Другая программа вместо `ssh`. | редко нужно |
| `-D ПУТЬ` | Подключиться к локальному SFTP-серверу; для отладки. | редко нужно |

Современный OpenSSH `scp` по умолчанию использует SFTP. Старый режим имеет другие правила обработки путей и шаблонов. Не переключайте протокол без причины. [scp(1)](https://man.openbsd.org/scp).

Команда может перезаписать существующий файл назначения. Для больших деревьев и предварительного просмотра изменений удобнее `rsync`.

**Пути с пробелами и шаблонами.** Путь на сервере берите в кавычки целиком вместе с именем сервера:

```bash
scp 'lab:/home/alice/Мои документы/отчёт.pdf' ./
scp ./'план работ.txt' 'lab:/home/alice/Мои документы/'
scp 'lab:/var/log/app/*.log' ./logs/
```

Кавычки не дают локальной оболочке разбить имя на части или раскрыть `*` у себя; шаблон `*.log` раскрывается на сервере. Если путь на сервере не начинается с `/`, он считается от домашнего каталога: `lab:notes.txt` — это `/home/alice/notes.txt`, а `lab:` — сам домашний каталог.

**Копирование между двумя серверами.** По умолчанию данные идут через ваш компьютер, и для обоих серверов используются ваши ключи:

```bash
scp lab:/home/alice/backup.tar.gz internal:/home/alice/
```

### 15.2. sftp

```bash
sftp lab
```

Внутри интерактивного клиента:

```text
pwd
lpwd
ls
lls
cd /home/alice/incoming
lcd ./documents
put notes.txt
get report.txt
bye
```

Команды с начальным `l` относятся к локальной машине. `put` отправляет, `get` скачивает. Для явного порта используется `sftp -P 2222`; параметры ключа и SSH-настроек доступны через `-i` и `-o`. Пакетный файл команд задаётся `-b`, но его операции могут менять и удалять данные — просмотрите содержимое заранее. [sftp(1)](https://man.openbsd.org/sftp).

**Команды внутри sftp**

| Команда | Что делает |
| --- | --- |
| `pwd` / `lpwd` | Текущий каталог на сервере / на своём компьютере. |
| `ls [-1afhlnrSt] [ПУТЬ]` / `lls` | Список файлов на сервере / локально; `-l` — подробно, `-h` — размеры в КБ/МБ, `-t` — по времени, `-S` — по размеру, `-a` — со скрытыми. |
| `cd ПУТЬ` / `lcd ПУТЬ` | Перейти в каталог на сервере / локально. |
| `get [-afpR] УДАЛЁННЫЙ [ЛОКАЛЬНЫЙ]` | Скачать; `-R` — каталог целиком, `-p` — сохранить время и права, `-a` — продолжить прерванное. |
| `put [-afpR] ЛОКАЛЬНЫЙ [УДАЛЁННЫЙ]` | Загрузить; ключи те же. |
| `reget`, `reput` | Продолжить прерванную загрузку, как `get -a` / `put -a`. |
| `mkdir ПУТЬ` / `lmkdir ПУТЬ` | Создать каталог на сервере / локально. |
| `rm ПУТЬ`, `rmdir ПУТЬ` | Удалить файл / пустой каталог на сервере. |
| `rename СТАРОЕ НОВОЕ` | Переименовать или переместить на сервере. |
| `cp СТАРОЕ НОВОЕ` (`copy`) | Копировать на стороне сервера, без передачи по сети; сервер должен поддерживать это расширение. |
| `ln [-s] СТАРОЕ НОВОЕ`, `symlink` | Создать ссылку на сервере. |
| `chmod [-h] РЕЖИМ ПУТЬ` | Права файла, например `chmod 640 report.txt`. |
| `chown [-h] UID ПУТЬ`, `chgrp [-h] GID ПУТЬ` | Владелец и группа; принимаются числовые идентификаторы. |
| `df [-hi] [ПУТЬ]` | Свободное место на сервере. |
| `lumask МАСКА` | Маска прав для скачиваемых файлов. |
| `progress` | Включить или выключить индикатор хода. |
| `!КОМАНДА` / `!` | Выполнить локальную команду / открыть локальную оболочку. |
| `help`, `?` | Справка. |
| `version` | Версия протокола SFTP. |
| `bye`, `exit`, `quit` | Выход. |

Имена с пробелами берите в кавычки: `get "отчёт за май.pdf"`. Символы `*` и `?` в именах работают как шаблоны: `get *.log` скачает все журналы текущего каталога.

**Параметры командной строки sftp**

| Параметр | Что делает |
| --- | --- |
| `-P ПОРТ` | Порт сервера (заглавная буква, как у `scp`). |
| `-i ФАЙЛ`, `-F ФАЙЛ`, `-o ДИРЕКТИВА`, `-J УЗЕЛ` | Ключ, конфигурация, директива `ssh_config`, промежуточный сервер. |
| `-b ФАЙЛ` | Выполнить команды из файла; `-` — со стандартного ввода. Без `-` перед командой ошибка любой команды прерывает выполнение. |
| `-r` | Рекурсивные `get` и `put` по умолчанию. |
| `-p` | Сохранять время и права. |
| `-a` | Продолжать прерванные передачи вместо перезаписи. |
| `-f` | После передачи просить сервер сразу записать файл на диск (`fsync`). |
| `-l КБИТ/С` | Ограничение скорости. |
| `-C` | Сжатие. |
| `-B БАЙТ` | Размер буфера передачи; по умолчанию 32768. |
| `-R ЧИСЛО` | Сколько запросов держать одновременно; по умолчанию 64. |
| `-q` | Без индикатора хода и предупреждений. |
| `-N` | Отменить тихий режим, который включается вместе с `-b`. |
| `-v` | Диагностика. |
| `-4`, `-6` | Только IPv4 / IPv6. |
| `-A` | Переслать агент. |
| `-s ПОДСИСТЕМА` | Другая подсистема или путь к программе SFTP-сервера. |

Пакетный режим для автоматической выгрузки:

```bash
cat > ./upload.sftp <<'EOF'
cd /home/alice/incoming
-mkdir reports
put -p ./reports/*.csv reports/
ls -l reports
EOF
sftp -b ./upload.sftp lab
```

Знак `-` перед `mkdir` означает «продолжить, даже если команда не удалась» — каталог может уже существовать. Для неинтерактивного режима ключ должен быть доступен без вопросов: через агент или отдельный сервисный ключ (раздел 20).

### 15.3. rsync поверх SSH

Сначала просмотр без изменений:

```bash
rsync -av --dry-run ./documents/ lab:/home/alice/documents/
```

Затем выполнение:

```bash
rsync -av --progress ./documents/ lab:/home/alice/documents/
```

С явными SSH-параметрами:

```bash
rsync -av --dry-run \
  -e 'ssh -p 2222 -i ~/.ssh/id_ed25519_server -o IdentitiesOnly=yes' \
  ./documents/ alice@server.example.com:/home/alice/documents/
```

`-a` включает архивный режим, `-v` выводит ход работы, `--dry-run` показывает план, `-e` выбирает транспорт. Завершающий `/` у исходного каталога означает передачу **содержимого**. Без него структура назначения может отличаться. `--delete` удаляет лишние файлы на стороне назначения; в базовые примеры он намеренно не добавлен. Для стандартного rsync через SSH программа должна быть доступна на обеих машинах. [Руководство rsync](https://download.samba.org/pub/rsync/rsync.1).

<a id="commands"></a>
## 16. Команды, кавычки и интерактивный терминал

Одноразовая команда:

```bash
ssh lab 'uname -sr'
ssh lab 'df -h /'
```

Команда выполняется на сервере, а вывод возвращается в локальный терминал. Обычный `ssh` возвращает код удалённой команды; ошибка самого подключения часто обозначается кодом `255`. GitHub имеет отдельное поведение тестового `ssh -T`, описанное выше.

### Где раскрываются переменные

```bash
ssh lab 'printf "%s\n" "$HOME"'
```

Одинарные кавычки сохраняют `$HOME` до обработки на сервере. Вариант с двойными внешними кавычками может раскрыть переменную локально ещё до запуска SSH.

SSH передаёт удалённую команду для обработки удалённой оболочкой. Нельзя считать, что произвольные аргументы автоматически сохранят границы и будут безопасны. Не подставляйте в командную строку непроверенные имена файлов или пользовательский текст. Для файлов используйте SFTP; для сложной автоматизации — проверенный скрипт с определённым форматом входных данных.

Передать простой скрипт через stdin без локального раскрытия переменных:

```bash
ssh -T lab 'bash -s' <<'REMOTE_SCRIPT'
set -eu
printf 'Удалённый пользователь: %s\n' "$(id -un)"
uname -sr
REMOTE_SCRIPT
```

Кавычки вокруг `REMOTE_SCRIPT` важны: содержимое раскрывается удалённой Bash. Завершающая метка должна стоять отдельно. На сервере должен быть `bash`.

### Когда нужны -t и -T

Для интерактивного редактора или команды, которой нужен терминал:

```bash
ssh -t lab 'top'
```

`-t` запрашивает псевдотерминал; `-tt` принудительно запрашивает его даже без локального терминала. `-T` запрещает псевдотерминал и подходит для машинного вывода или потока данных. Не добавляйте `-t` к бинарной передаче: терминал может преобразовывать поток.

### Долгая работа

Для интерактивного задания используйте установленный на сервере `tmux`:

```bash
ssh lab
tmux new -s maintenance
```

Отсоединение: Ctrl+B, затем D. После повторного входа:

```bash
tmux attach -t maintenance
```

SSH keepalive помогает обнаруживать оборванное соединение, но не гарантирует сохранение процесса. `ssh -f` также не является менеджером удалённых задач. Для фонового сервиса используйте штатный менеджер служб и журналирование.

### 16.4. Escape-последовательности

В интерактивном сеансе с терминалом `ssh` понимает команды, которые начинаются с символа `~`. Их набирают **в начале строки**: сначала Enter, затем `~` и следующий символ. Нажатые клавиши не отправляются на сервер.

| Последовательность | Что делает |
| --- | --- |
| `~.` | Разорвать соединение. Помогает, когда сеанс «завис» и не реагирует на клавиши. |
| `~^Z` (тильда, затем Ctrl+Z) | Приостановить `ssh` и вернуться в локальную оболочку; назад — командой `fg`. |
| `~&` | Уйти в фон при выходе, пока закрываются туннели и X11. |
| `~#` | Показать открытые через соединение перенаправления. |
| `~?` | Показать список последовательностей. |
| `~C` | Командная строка для добавления (`-L`, `-R`, `-D`) и отмены (`-KL`, `-KR`, `-KD`) туннелей без переподключения. |
| `~R` | Попросить сервер заново согласовать ключи сеанса. |
| `~B` | Отправить сигнал BREAK (полезно для консолей сетевого оборудования). |
| `~v`, `~V` | Повысить / понизить подробность диагностики. |
| `~~` | Отправить сам символ `~`. |

Начиная с OpenSSH 9.2 командная строка `~C` **по умолчанию отключена**. Включить её для отдельного сервера:

```sshconfig
Host lab
    EnableEscapeCommandline yes
```

После этого в сеансе: Enter, `~C`, затем, например, `-L 127.0.0.1:18080:127.0.0.1:8080` и Enter — туннель появится без нового входа.

Если символ `~` мешает (например, при передаче двоичных данных через терминал или во вложенных сеансах), смените его параметром `-e` или отключите: `ssh -e none lab`. Во вложенном сеансе `ssh` внутри `ssh` команда `~~.` разорвёт внутреннее соединение, а `~.` — внешнее.

<a id="jump"></a>
## 17. Промежуточный сервер ProxyJump

Сценарий: внутренний сервер доступен только через bastion. Ключи остаются на клиентском компьютере; пересылка агента для обычного `ProxyJump` не требуется.

```sshconfig
Host bastion
    HostName bastion.example.com
    User gateway
    IdentityFile ~/.ssh/id_ed25519_bastion
    IdentitiesOnly yes
    ForwardAgent no

Host internal
    HostName internal.example.com
    User alice
    IdentityFile ~/.ssh/id_ed25519_internal
    IdentitiesOnly yes
    ForwardAgent no
    ProxyJump bastion
```

Для этих двух назначений предварительно создайте отдельные ключи и зарегистрируйте их на соответствующих серверах.

```bash
ssh internal
scp ./notes.txt internal:/home/alice/
```

Одноразовая запись:

```bash
ssh -J gateway@bastion.example.com alice@internal.example.com
```

С портом bastion:

```bash
ssh -J gateway@bastion.example.com:2222 alice@internal.example.com
```

Для двух переходов можно использовать `-J first-hop,second-hop`, если оба псевдонима настроены. Командный `-i` относится к целевому подключению и не является универсальной настройкой ключа каждого перехода: для разных ключей удобнее отдельные блоки `Host`.

Проверяются host keys и bastion, и конечного сервера. Посредник должен разрешать нужное TCP-перенаправление. `ProxyJump` и `ProxyCommand` не следует одновременно задавать для одного подключения без понимания порядка выбора.

<a id="tunnels"></a>
## 18. Туннели: -L, -R и -D

SSH-перенаправление используется только там, где у вас есть право доступа к обоим концам. Оно не отменяет аутентификацию приложения и правила firewall. Базовые примеры слушают только loopback, чтобы не открыть сервис всей сети.

### 18.1. Локальный туннель -L

Сценарий: на сервере веб-приложение слушает `127.0.0.1:8080`, нужно открыть его в локальном браузере:

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18080:127.0.0.1:8080 lab
```

Теперь на **своём компьютере** откройте `http://127.0.0.1:18080`.

```text
локальный браузер → локальный 127.0.0.1:18080
                 → SSH → сервер → серверный 127.0.0.1:8080
```

В `-L АДРЕС:ПОРТ:ЦЕЛЬ:ПОРТ_ЦЕЛИ` первая пара относится к клиенту; соединение с целью открывает сервер. Поэтому последние `127.0.0.1` здесь означают **сервер**, а не ноутбук.

Для базы данных, доступной серверу по имени:

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:15432:db.internal.example.com:5432 lab
```

Имя базы разрешается и соединение устанавливается с удалённой стороны. Шифрован участок клиент ↔ SSH-сервер; дальнейший участок до базы требует собственной защиты, если проходит по недоверенной сети.

### 18.2. Обратный туннель -R

Сценарий: на ноутбуке есть приложение `127.0.0.1:3000`; нужно временно сделать его доступным **на loopback сервера**:

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -R 127.0.0.1:13000:127.0.0.1:3000 lab
```

На сервере обращайтесь к `http://127.0.0.1:13000`. Здесь последняя пара `127.0.0.1:3000` относится к **клиентскому компьютеру**.

Поведение адреса прослушивания `-R` ограничивает серверная настройка `GatewayPorts`. Профиль `GatewayPorts no` сохраняет доступ через loopback. Не заменяйте адрес на `0.0.0.0` и не включайте `GatewayPorts yes`, если не планируете осознанно публиковать сервис и проверять его аутентификацию.

### 18.3. SOCKS-прокси -D

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -D 127.0.0.1:1080 lab
```

Приложение должно использовать SOCKS-прокси `127.0.0.1:1080`. Пример для установленного `curl`:

```bash
curl --socks5-hostname 127.0.0.1:1080 https://example.com/
```

`--socks5-hostname` передаёт разрешение имени через прокси. Настройка браузера, выполняющего DNS локально, может вести себя иначе. Этот прокси не перенаправляет автоматически весь трафик Linux и не является универсальным VPN для UDP.

### 18.4. Несколько туннелей в одном соединении

```bash
ssh -N -T \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 \
  -o ServerAliveCountMax=3 \
  -L 127.0.0.1:18080:127.0.0.1:8080 \
  -L 127.0.0.1:15432:db.internal.example.com:5432 \
  -D 127.0.0.1:1080 \
  lab
```

`-N` убирает удалённую команду, `-T` — терминал. `ExitOnForwardFailure` позволяет заметить невозможность **создать перенаправление**, но не доказывает, что конечный HTTP-сервис или база здоровы. Проверяйте приложение отдельным запросом. Ctrl+C закрывает foreground-туннель.

В конфигурации аналогичные настройки:

```sshconfig
Host lab-web
    HostName server.example.com
    User alice
    Port 2222
    IdentityFile ~/.ssh/id_ed25519_server
    IdentitiesOnly yes
    ForwardAgent no
    LocalForward 127.0.0.1:18080 127.0.0.1:8080
    ExitOnForwardFailure yes
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

```bash
ssh -N -T lab-web
```

Не путайте `LocalForward`/`RemoteForward` клиента с разрешениями `AllowTcpForwarding`, `PermitOpen`, `PermitListen` на сервере. Полный синтаксис TCP и Unix-сокетов описан в [ssh(1)](https://man.openbsd.org/ssh).

<a id="multiplexing"></a>
## 19. Повторное использование соединения

Multiplexing позволяет новым сеансам использовать уже открытое SSH-соединение. Это ускоряет серии команд, но новый сеанс может не выполнять новую аутентификацию и не просить парольную фразу или касание токена.

Создайте закрытый каталог сокетов:

```bash
mkdir -p ~/.ssh/control
chmod 700 ~/.ssh/control
```

В нужный существующий блок `Host` можно добавить:

```sshconfig
ControlMaster auto
ControlPath ~/.ssh/control/%C
ControlPersist 5m
```

`%C` формирует сокращённое имя на основе параметров соединения. Сокет нельзя размещать в каталоге, доступном другим пользователям для записи. `ControlPersist` оставляет master-соединение на заданное время после завершения последнего клиентского сеанса.

```bash
ssh lab 'uname -sr'
ssh -O check lab
ssh -O exit lab
```

`exit` завершает master и может оборвать использующие его сеансы. `stop` прекращает принимать новые multiplexed-сеансы, сохраняя существующие.

| Команда `ssh -O` | Что делает |
| --- | --- |
| `check` | Проверить, работает ли master для этого сервера. |
| `forward` | Добавить перенаправление в работающий master, не открывая сеанс: `ssh -O forward -L 127.0.0.1:18080:127.0.0.1:8080 lab`. |
| `cancel` | Отменить такое перенаправление: `ssh -O cancel -L 127.0.0.1:18080:127.0.0.1:8080 lab`. |
| `stop` | Перестать принимать новые сеансы, не трогая текущие. |
| `exit` | Завершить master. |
| `proxy` | Подключиться к master в режиме прокси; используется внутри `ProxyCommand`. |

`ControlMaster` принимает значения `no` (по умолчанию), `yes`, `ask`, `auto` и `autoask`: `auto` создаёт master, если его ещё нет, и использует существующий в остальных случаях. `ControlPersist` принимает `no`, `yes` (держать бессрочно) или время, например `5m`.

Для диагностики **новой аутентификации** отключите повторное использование:

```bash
ssh -S none -o ControlMaster=no lab
```

Для строгой проверки аппаратного токена дополнительно можно использовать `-o IdentityAgent=none`. Удаление ключа из агента само по себе не разрывает существующий master.

<a id="automation"></a>
## 20. Автоматизация и ограниченный доступ

### 20.1. Команда без интерактивных вопросов

Когда нужный host key уже проверен и сохранён, а ключ доступен процессу:

```bash
ssh -T -o BatchMode=yes \
  -o StrictHostKeyChecking=yes \
  -o ConnectTimeout=10 \
  lab 'uname -sr'
```

`BatchMode=yes` не разблокирует ключ и не обходит пароль. Если для ключа требуется интерактивная парольная фраза, команда завершится ошибкой. Ограничение `ConnectTimeout` не задаёт максимальное время выполнения удалённой команды. Для общего таймаута на Linux можно обернуть вызов в `timeout`, понимая, что разрыв клиента не гарантирует остановку всех удалённых процессов.

```bash
timeout 30s ssh -T -o BatchMode=yes -o ConnectTimeout=10 lab 'uname -sr'
```

Для заданий по расписанию нужны абсолютные пути, явно доступный агент или отдельный сервисный ключ, заранее проверенный `known_hosts` и минимальные права. Не делайте копию личного административного ключа на каждом CI runner. FIDO2 с обязательным касанием плохо подходит для полностью автоматического unattended-задания.

### 20.2. Ограничения одного ключа на Linux

В `authorized_keys` перед открытым ключом можно указать ограничения. Следующая строка — **шаблон**, а не готовый действительный ключ:

```text
from="192.0.2.50",restrict,command="/usr/bin/id" ssh-ed25519 PUBLIC_KEY_BODY monitoring-key
```

Вместо `PUBLIC_KEY_BODY` используется настоящая открытая часть, а документальный адрес заменяется разрешённым источником. `from` ограничивает адрес входа, `restrict` отключает ряд дополнительных возможностей, `command` заставляет выполнять фиксированную команду. Один `restrict` не равнозначен ограничению произвольных shell-команд: для этого нужен `command` или профиль сервиса. [Формат authorized_keys](https://man.openbsd.org/sshd#AUTHORIZED_KEYS_FILE_FORMAT).

Для ограниченного туннельного сервиса могут понадобиться `permitopen`, `permitlisten`, соответствующие настройки `AllowTcpForwarding` и отсутствие произвольной оболочки. Ограничение пересылки портов само по себе не изолирует пользователя, которому разрешено запускать любые программы на сервере.

**Все ограничения строки authorized_keys**

| Ограничение | Что делает |
| --- | --- |
| `restrict` | Включить все ограничения: запретить туннели, пересылку агента и X11, терминал и `~/.ssh/rc`. Нужные возможности затем включают по одной. |
| `command="КОМАНДА"` | Выполнять только эту команду; запрошенная клиентом команда доступна ей в переменной `SSH_ORIGINAL_COMMAND`. |
| `from="ШАБЛОНЫ"` | Принимать ключ только с этих адресов или имён: `from="192.0.2.0/24,!192.0.2.13"`. |
| `expiry-time="ДАТА"` | Ключ действует до даты: `expiry-time="20271231"` или `"202712312359"`. |
| `environment="ИМЯ=значение"` | Задать переменную окружения; работает только при `PermitUserEnvironment yes` на сервере. |
| `no-port-forwarding` / `port-forwarding` | Запретить / разрешить туннели `-L`, `-R`, `-D`. |
| `permitopen="узел:порт"` | Разрешить `-L` только к этому назначению; можно указать несколько раз. |
| `permitlisten="[узел:]порт"` | Разрешить `-R` только на этом порту. |
| `no-agent-forwarding` / `agent-forwarding` | Запретить / разрешить пересылку агента. |
| `no-X11-forwarding` / `X11-forwarding` | Запретить / разрешить X11. |
| `no-pty` / `pty` | Запретить / разрешить терминал. |
| `no-user-rc` / `user-rc` | Не выполнять / выполнять `~/.ssh/rc`. |
| `tunnel="N"` | Номер устройства `tun` для `-w`. |
| `cert-authority` | Строка содержит ключ CA: принимать сертификаты, подписанные им. |
| `principals="имя1,имя2"` | Вместе с `cert-authority`: допустимые principals сертификата. |
| `no-touch-required` | Для FIDO-ключа: не требовать касания (ключ должен быть создан с тем же параметром). |
| `verify-required` | Для FIDO-ключа: требовать PIN или биометрию при каждом входе. |

Примеры строк (вместо `AAAA...` — настоящая открытая часть):

```text
# Резервное копирование: только rsync в режиме приёма, без терминала и туннелей.
restrict,command="/usr/bin/rrsync -wo /srv/backup" ssh-ed25519 AAAA... backup-host

# Только туннель к базе: команды заменяются на /bin/false, подключаться с ssh -N.
restrict,port-forwarding,permitopen="127.0.0.1:5432",command="/bin/false" ssh-ed25519 AAAA... db-tunnel

# Временный ключ подрядчика с ограничением по адресу и сроку.
from="198.51.100.0/24",expiry-time="20270131" ssh-ed25519 AAAA... contractor

# FIDO-ключ, для которого сервер требует PIN при каждом входе.
verify-required sk-ssh-ed25519@openssh.com AAAA... yubikey-laptop
```

`rrsync` — сценарий из пакета `rsync`, который разрешает только rsync-операции внутри указанного каталога; `-wo` разрешает только запись, `-ro` — только чтение. В Debian и Ubuntu он лежит в `/usr/bin/rrsync`. Ограничение `command=` работает и без `restrict`, но тогда клиент сможет открыть туннели и получить терминал.

`restrict` **не запрещает** выполнять команды: без `command=` ключ из примера с туннелем мог бы запустить любую программу на сервере. Поэтому для ключа «только туннель» добавлен `command="/bin/false"`: при `ssh -N` команда не запускается вовсе и туннель работает, а любая попытка выполнить команду получит `/bin/false`. Все примеры этого раздела проверены на OpenSSH 10.2.

### 20.3. Deploy key GitHub

Для одного репозитория можно создать отдельную SSH-пару и добавить её открытую часть в **Repository → Settings → Deploy keys**. По умолчанию сохраняйте доступ только для чтения; запись включайте только при необходимости. Такой ключ привязан к репозиторию и управляется отдельно от личных ключей аккаунта. [Deploy keys](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys).

SSH-ключ без парольной фразы иногда используется в изолированной автоматизации, но тогда защита файла и ограничение его прав становятся особенно важны. Это не рекомендуемый вариант для универсального личного ключа. Сам секрет выдаётся заданию через механизм CI, не через Git, Dockerfile или артефакт сборки.

<a id="rotation"></a>
## 21. Замена, резервирование и отзыв ключей

### 21.1. Плановая замена

1. Создайте новую пару с новым именем файла.
2. Добавьте новый `.pub` в GitHub и на нужные серверы.
3. Проверьте **новое соединение** с явно указанным новым ключом, без multiplexing.
4. Обновите `IdentityFile` и необходимые задания.
5. Удалите старую открытую часть из GitHub и каждого `authorized_keys`.
6. Уберите старую идентичность из агента и закройте старые master-соединения.
7. По принятой политике удалите ненужные локальные копии старого закрытого ключа.

Пример проверки нового ключа на Linux:

```bash
ssh -S none -F none -p 2222 \
  -i ~/.ssh/id_ed25519_server_new \
  -o IdentitiesOnly=yes -o IdentityAgent=none \
  -o PreferredAuthentications=publickey \
  alice@server.example.com
```

Удаление закрытого файла **не отзывает** украденные копии. Отзыв выполняется на стороне всех принимающих систем. Изменение парольной фразы вашего экземпляра также не меняет старую копию, уже оказавшуюся у другого человека.

### 21.2. Потеря или компрометация

При подтверждённой компрометации сначала отключайте подозрительный доступ, используя доверенное устройство и резервный канал. Проверьте журнал входов и действия аккаунта. Создайте новую пару, а не только новую фразу старого файла. Если украден FIDO2-токен, удалите соответствующие SSH-ключи и отдельно связанные веб-credentials; это разные регистрации.

Удаление ключа обычно запрещает **новую** аутентификацию. Оно не гарантирует остановку уже открытых сессий, токенов приложений или выполненных злоумышленником изменений — это нужно проверять отдельно.

### 21.3. Резервные копии

Для программного ключа резервируйте зашифрованный закрытый файл и сведения о его назначении в защищённом хранилище. Храните парольную фразу так, чтобы восстановление не зависело от одного потерянного устройства. Практически проверьте процедуру восстановления на доверенной машине, не публикуя закрытый материал.

Для нерезидентного FIDO2 нужны рабочий токен и локальный файл-дескриптор; резерв второго токена создаётся как независимый ключ. Не кладите архив `~/.ssh` в Git даже приватного репозитория. Удаление секретов следующим коммитом не удаляет их из истории.

Не обещайте себе «безвозвратное стирание» простым `rm` или `shred` на SSD, snapshot-файловой системе и облачном диске. Отзыв доступа важнее предположений об очистке каждой старой копии.

<a id="certificates"></a>
## 22. Сертификаты и подпись файлов

Эти примеры относятся к отдельной учебной Linux-инфраструктуре. Для обычного личного GitHub-доступа достаточно добавления открытого ключа; SSH-сертификат не следует считать автоматически принимаемым любым аккаунтом GitHub.

### 22.1. SSH CA и временный пользовательский сертификат

В новой учебной директории создайте CA и пользовательский ключ. Для обоих задайте парольные фразы:

```bash
umask 077
mkdir ~/ssh-ca-demo
ssh-keygen -t ed25519 -a 100 -f ~/ssh-ca-demo/ca -C "lab-ca"
ssh-keygen -t ed25519 -a 100 -f ~/ssh-ca-demo/user -C "lab-user"
```

Подписать открытую часть пользователя:

```bash
ssh-keygen -s ~/ssh-ca-demo/ca \
  -I demo-session-001 -n alice -V -5m:+8h -z 1 \
  ~/ssh-ca-demo/user.pub
```

Появится `user-cert.pub`. `-s` выбирает CA, `-I` — идентификатор сертификата, `-n` — разрешённый principal, `-V` — интервал действия, `-z` — серийный номер. В этом примере начало сдвинуто на пять минут назад, окончание — через восемь часов от текущего времени, чтобы небольшой рассинхрон часов не мешал входу.

Проверить содержимое сертификата:

```bash
ssh-keygen -L -f ~/ssh-ca-demo/user-cert.pub
```

Чтобы сервер принимал сертификат, администратор отдельно устанавливает **открытый** ключ CA и настраивает `TrustedUserCAKeys`, допустимые principals и правила входа. Закрытый CA-ключ на сервер не переносится. Без этого подпись файла сертификата сама по себе не даёт доступ.

После настройки доверия можно использовать пару ключ/сертификат:

```bash
ssh -i ~/ssh-ca-demo/user \
  -o CertificateFile=~/ssh-ca-demo/user-cert.pub \
  alice@server.example.com
```

Файл сертификата может автоматически подбираться по стандартному суффиксу `-cert.pub`. Разделение CA и пользовательских ключей удобно для большого числа серверов, но требует управления сроками, отзывом и защитой CA.

Параметры подписи, которые чаще всего нужны:

| Параметр | Что делает |
| --- | --- |
| `-I ИДЕНТИФИКАТОР` | Метка сертификата для журналов сервера, например имя сотрудника и номер заявки. |
| `-n ИМЕНА` | Principals через запятую: для пользователя — имена входа, для сервера — его имена. |
| `-V ИНТЕРВАЛ` | Срок действия: `+8h` (с этого момента на 8 часов), `-5m:+1d`, `20270101:20270201`, `always:forever`. |
| `-z ЧИСЛО` | Серийный номер для отзыва через KRL. |
| `-h` | Подписать ключ **сервера**, а не пользователя. |
| `-U` | Закрытый ключ CA находится в агенте; `-s` тогда указывает на его открытую часть. |
| `-O clear` | Снять все разрешения, затем включить нужные по одному. |
| `-O force-command=КОМАНДА` | Сертификат позволяет выполнить только эту команду. |
| `-O source-address=СЕТИ` | Принимать сертификат только с этих адресов. |
| `-O no-port-forwarding`, `-O no-agent-forwarding`, `-O no-x11-forwarding`, `-O no-pty`, `-O no-user-rc` | Запретить отдельные возможности. |
| `-O permit-port-forwarding`, `-O permit-agent-forwarding`, `-O permit-X11-forwarding`, `-O permit-pty`, `-O permit-user-rc` | Разрешить их после `clear`. |
| `-O verify-required`, `-O no-touch-required` | Для FIDO-ключей: требовать PIN / не требовать касания. |

Пример сертификата только для чтения журналов, без терминала и туннелей, на один рабочий день:

```bash
ssh-keygen -s ~/ssh-ca-demo/ca -I audit-2027-01-15 -n alice -V +9h \
  -O clear -O force-command="journalctl -n 200 --no-pager" \
  ~/ssh-ca-demo/user.pub
```

### 22.1.1. Сертификат сервера вместо сверки отпечатков

CA может подписать и ключ сервера. Тогда клиентам достаточно один раз доверять открытому ключу CA, и вопрос о неизвестном сервере не появится для всех подписанных машин.

Закрытый ключ CA на сервер не переносят. Скопируйте с сервера **открытый** ключ `/etc/ssh/ssh_host_ed25519_key.pub` (он не секретный) на машину с CA и подпишите там:

```bash
ssh-keygen -s ~/ssh-ca-demo/ca -h -I server-example -n server.example.com \
  -V +52w ./ssh_host_ed25519_key.pub
```

Получится `./ssh_host_ed25519_key-cert.pub`. Перенесите его на сервер в `/etc/ssh/` и объявите в файле из `/etc/ssh/sshd_config.d/`:

```sshconfig
HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub
```

Затем `sudo sshd -t` и перезагрузка службы, как в разделе 14.4.

На клиенте в `~/.ssh/known_hosts` добавляется одна строка с открытым ключом CA:

```text
@cert-authority *.example.com ssh-ed25519 AAAA...ОТКРЫТЫЙ_КЛЮЧ_CA lab-ca
```

Principal `-n` должен совпадать с именем, по которому вы подключаетесь. Срок сертификата сервера нужно отслеживать: по истечении клиенты снова увидят вопрос о неизвестном ключе.

### 22.2. Список отзыва KRL

В новом файле можно создать список отзыва учебного открытого ключа:

```bash
ssh-keygen -k -f ~/ssh-ca-demo/revoked.krl ~/ssh-ca-demo/user.pub
ssh-keygen -Q -f ~/ssh-ca-demo/revoked.krl ~/ssh-ca-demo/user.pub
```

Для отозванного ключа проверка вернёт ненулевой статус. Чтобы отзыв реально применялся сервером, KRL нужно безопасно установить и подключить через `RevokedKeys`. Создание локального файла не уведомляет серверы автоматически. Для крупных инфраструктур существуют также отзыв сертификатов по серийным номерам и идентификаторам; см. [KRL в OpenSSH](https://man.openbsd.org/ssh-keygen#KEY_REVOCATION_LISTS).

### 22.3. Подпись файла

SSH-ключом можно подписать обычный файл без подключения к серверу:

```bash
ssh-keygen -Y sign -f ~/ssh-ca-demo/user -n file ./document.txt
```

Файл должен существовать; рядом создаётся `.sig`. `-n file` здесь задаёт пространство имён подписи, **не** пользователя сертификата. Для проверки нужны доверенный список подписантов, исходный файл и подпись:

```bash
ssh-keygen -Y verify -f ./allowed_signers \
  -I demo -n file -s ./document.txt.sig < ./document.txt
```

Пример формата `allowed_signers` с заполнителем:

```text
demo namespaces="file" ssh-ed25519 PUBLIC_KEY_BODY
```

Открытый ключ в этом файле должен быть получен по доверенному каналу. Подпись не шифрует документ.

### 22.4. Подпись Git-коммитов

Git может использовать SSH-ключ для подписания коммитов. В репозитории настройте отдельный ключ подписи или осознанно выбранную существующую пару:

```bash
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_signing -C "git-signing"
ssh-add -t 1h ~/.ssh/id_ed25519_signing
git config gpg.format ssh
git config user.signingkey ~/.ssh/id_ed25519_signing.pub
git config commit.gpgsign true
```

Агент должен быть запущен, как описано в разделе 11. Если ключ уже существует, не выполняйте его создание повторно. При использовании пути `.pub` закрытая часть доступна для подписи через агент. Открытую часть добавляют в GitHub как **Signing Key**; роль Authentication Key сама по себе не означает регистрацию для проверки подписей. Адрес автора коммита остаётся отдельной настройкой. [GitHub: настройка SSH-подписи](https://docs.github.com/en/authentication/managing-commit-signature-verification/telling-git-about-your-signing-key).

<a id="ssh-options"></a>
## 23. Справочник параметров ssh

Общая форма:

```text
ssh [ПАРАМЕТРЫ] [ПОЛЬЗОВАТЕЛЬ@]ХОСТ [УДАЛЁННАЯ_КОМАНДА]
```

Ниже перечислены короткие параметры современного OpenSSH `ssh`. Некоторые новые флаги могут отсутствовать в вашей сборке. Это справочник выбора, а не рекомендация включить всё одновременно.

**Куда подключаться**

| Параметр | Что делает | Пример |
| --- | --- | --- |
| `-p ПОРТ` | Порт сервера; по умолчанию 22. | `ssh -p 2222 alice@server.example.com` |
| `-l ПОЛЬЗОВАТЕЛЬ` | Имя на сервере; то же, что `пользователь@` перед именем. | `ssh -l alice server.example.com` |
| `-4` / `-6` | Только IPv4 / только IPv6. | `ssh -6 lab` |
| `-b АДРЕС` | С какого из своих адресов подключаться. | `ssh -b 192.0.2.50 lab` |
| `-B ИНТЕРФЕЙС` | Через какой сетевой интерфейс подключаться. | `ssh -B wg0 lab` |
| `-J УЗЕЛ[,УЗЕЛ]` | Через промежуточный сервер (раздел 17). | `ssh -J bastion internal` |
| `-W УЗЕЛ:ПОРТ` | Передать stdin/stdout на указанный адрес за сервером; используется в `ProxyCommand`. | `ssh -W internal.example.com:22 bastion` |

**Чем подтверждать доступ**

| Параметр | Что делает | Пример |
| --- | --- | --- |
| `-i ФАЙЛ` | Файл закрытого ключа; можно повторять. Рядом подхватывается сертификат `ФАЙЛ-cert.pub`. | `ssh -i ~/.ssh/id_ed25519_server lab` |
| `-I БИБЛИОТЕКА` | Ключи смарт-карты через PKCS#11 (раздел 12.7). | `ssh -I /usr/lib/x86_64-linux-gnu/libykcs11.so lab` |
| `-A` / `-a` | Включить / выключить пересылку агента на сервер. | `ssh -a lab` |
| `-K` / `-k` | Включить / выключить вход и делегирование по GSSAPI (Kerberos). | `ssh -K host.corp.example.com` |

**Какую конфигурацию использовать**

| Параметр | Что делает | Пример |
| --- | --- | --- |
| `-F ФАЙЛ` | Другой файл конфигурации; `none` — никакого. | `ssh -F ~/.ssh/config-lab lab` |
| `-o ДИРЕКТИВА=ЗНАЧЕНИЕ` | Любая директива `ssh_config` (раздел 9.5). | `ssh -o ConnectTimeout=10 lab` |
| `-G` | Не подключаться, а напечатать итоговую конфигурацию. | `ssh -G lab \| grep -E '^(hostname\|port\|user) '` |
| `-P МЕТКА` | Задать метку для блоков `Match tagged` (раздел 9.3). | `ssh -P debug lab` |
| `-Q ЧТО` | Показать поддерживаемые алгоритмы: `cipher`, `mac`, `kex`, `key`, `sig`, `help` и другие. | `ssh -Q kex` |
| `-V` | Версия OpenSSH. | `ssh -V` |

**Какой нужен сеанс**

| Параметр | Что делает | Пример |
| --- | --- | --- |
| `-t` / `-tt` | Выделить терминал / выделить даже без локального терминала. | `ssh -t lab 'sudo systemctl status ssh'` |
| `-T` | Не выделять терминал: для команд и передачи данных. | `ssh -T git@github.com` |
| `-N` | Не запускать команду: только туннели. | `ssh -N -L 127.0.0.1:18080:127.0.0.1:8080 lab` |
| `-n` | Не читать stdin (подставить `/dev/null`); нужен при запуске `ssh` в фоне или в цикле по строкам. | `ssh -n lab 'uptime' &` |
| `-f` | Уйти в фон после входа; обычно вместе с `-N`. | `ssh -f -N -L 127.0.0.1:15432:127.0.0.1:5432 lab` |
| `-s` | Запустить подсистему сервера вместо команды. | `ssh -s lab sftp` |
| `-e СИМВОЛ` | Escape-символ вместо `~`; `none` — без него (раздел 16.4). | `ssh -e none lab` |
| `-C` | Сжатие данных. | `ssh -C lab 'cat /var/log/app.log'` |
| `-c ШИФРЫ` / `-m MAC` | Явный выбор шифров / алгоритмов целостности; обычно не нужен. | `ssh -c aes256-gcm@openssh.com lab` |

**Перенаправления**

| Параметр | Что делает | Пример |
| --- | --- | --- |
| `-L [АДРЕС:]ПОРТ:ЦЕЛЬ:ПОРТ` | Локальный туннель (раздел 18.1). | `ssh -L 127.0.0.1:18080:127.0.0.1:8080 lab` |
| `-R [АДРЕС:]ПОРТ:ЦЕЛЬ:ПОРТ` | Обратный туннель (раздел 18.2). | `ssh -R 127.0.0.1:13000:127.0.0.1:3000 lab` |
| `-D [АДРЕС:]ПОРТ` | SOCKS-прокси (раздел 18.3). | `ssh -D 127.0.0.1:1080 lab` |
| `-g` | Пускать к локальным туннелям другие машины сети. | `ssh -g -L 18080:127.0.0.1:8080 lab` |
| `-w ЛОКАЛЬНЫЙ[:УДАЛЁННЫЙ]` | Туннель на уровне сети через устройства `tun`; нужен `PermitTunnel` на сервере и права root. | `sudo ssh -w 0:0 root@lab` |
| `-X` / `-Y` / `-x` | Пересылка X11 / доверенная пересылка X11 / запрет X11. | `ssh -X lab xclock` |

**Повторное использование соединения**

| Параметр | Что делает | Пример |
| --- | --- | --- |
| `-M` | Сделать это соединение master для multiplexing (раздел 19). | `ssh -M -S ~/.ssh/control/lab -f -N lab` |
| `-S ПУТЬ` | Путь к управляющему сокету; `none` — не использовать. | `ssh -S none lab` |
| `-O КОМАНДА` | Управлять master: `check`, `forward`, `cancel`, `stop`, `exit`, `proxy`. | `ssh -O check lab` |

**Диагностика**

| Параметр | Что делает | Пример |
| --- | --- | --- |
| `-v`, `-vv`, `-vvv` | Подробный журнал подключения; чем больше `v`, тем подробнее. | `ssh -vvv lab` |
| `-q` | Не печатать предупреждения и диагностику. | `ssh -q lab 'uptime'` |
| `-E ФАЙЛ` | Писать диагностику в файл, а не на экран. | `ssh -vvv -E ./ssh-debug.log lab` |
| `-y` | Писать журнал в системный журнал (syslog). | `ssh -y -f -N lab-web` |

Точный синтаксис, поддерживаемые значения и ограничения: [ssh(1)](https://man.openbsd.org/ssh). Проверьте `man ssh` на своей машине: метки конфигурации (`Tag`, `Match tagged`, `-P`) и условие `localnetwork` появились в OpenSSH 9.4 и новее, а в старых версиях части параметров может не быть.

### Примеры менее частых параметров

Версия, категории запросов и поддерживаемые алгоритмы:

```bash
ssh -V
ssh -Q help
ssh -Q key
ssh -Q kex
ssh -Q cipher
ssh -Q mac
```

Поддержка алгоритма в `-Q` не означает, что он включён по умолчанию или разрешён удалённым сервером. Не заменяйте обновляемые безопасные настройки длинным устаревающим списком из интернета.

Проверка IPv4 и IPv6 — независимые варианты:

```bash
ssh -4 lab
ssh -6 lab
```

Исходящий адрес выбирают только из уже назначенных клиентской машине:

```bash
ssh -b 192.0.2.50 alice@server.example.com
```

Это не подмена сетевого адреса и не обход маршрутизации. `-B` требует реального имени локального интерфейса.

Порт в URI и обычной форме:

```bash
ssh ssh://alice@server.example.com:2222
ssh -p 2222 alice@server.example.com
```

Прямой поток через bastion, используемый в специальных транспортных схемах:

```bash
ssh -W internal.example.com:22 bastion
```

Этот вызов сам не открывает обычную оболочку конечной машины; в повседневной работе понятнее `ProxyJump`.

`-X` и особенно `-Y` требуют доверия удалённой стороне, могут давать доступ к возможностям локального X-сервера и не равнозначны безопасному полному удалённому рабочему столу. `-w` требует настройки TUN, прав и серверного разрешения; это не сокращённая замена обычному `-L`.

### Настройки через -o

Коротких флагов недостаточно для всех режимов. Через `-o` доступны директивы `ssh_config`:

```bash
ssh -o ConnectTimeout=10 \
  -o ConnectionAttempts=1 \
  -o ServerAliveInterval=30 \
  -o ServerAliveCountMax=3 \
  lab
```

Настройки, которые часто встречаются дополнительно:

| Директива | Когда нужна |
| --- | --- |
| `PreferredAuthentications` | Порядок допустимых методов клиента. |
| `PasswordAuthentication` | Разрешение клиенту попробовать серверный пароль. |
| `KbdInteractiveAuthentication` | Интерактивные запросы сервера. |
| `CertificateFile` | Пользовательский SSH-сертификат. |
| `UserKnownHostsFile` | Отдельная база доверенных host keys. |
| `HashKnownHosts` | Скрытие имён узлов в новых записях known_hosts. |
| `UpdateHostKeys` | Согласованное обновление доверенных host keys. |
| `HostKeyAlias` | Отдельное имя для проверки host key. |
| `HostKeyAlgorithms` | Алгоритмы идентичности сервера. |
| `PubkeyAcceptedAlgorithms` | Алгоритмы пользовательской подписи. |
| `KexAlgorithms` | Алгоритмы обмена ключами сеанса. |
| `Ciphers`, `MACs` | Шифры и контроль целостности транспорта. |
| `LocalForward`, `RemoteForward`, `DynamicForward` | Настройки туннелей. |
| `ExitOnForwardFailure` | Ошибка при невозможности создать forwarding. |
| `ControlMaster`, `ControlPath`, `ControlPersist` | Повторное использование соединения. |
| `RequestTTY` | Политика выделения терминала. |
| `LogLevel` | Подробность диагностики. |
| `SendEnv`, `SetEnv` | Передача переменных, если разрешена сервером. |

Полный набор директив существенно шире таблицы и меняется с версиями; официальная спецификация — [ssh_config(5)](https://man.openbsd.org/ssh_config). Передача `-o` клиенту не изменяет `sshd_config` сервера. Например, клиентское `PasswordAuthentication=no` защищает конкретное подключение от fallback, но не отключает парольные входы остальных клиентов.

| `-A` | Создание отсутствующих host keys. |
| `-D` | Открытые ключи PKCS#11. |
| `-K` | Импорт резидентных FIDO credentials. |

### Примеры режимов ssh-keygen

Отпечаток вместе с «картинкой» из символов: её проще сравнить на глаз, чем строку.

```bash
ssh-keygen -l -v -f ~/.ssh/id_ed25519_github.pub
```

Отпечаток в старом формате MD5 для систем, которые показывают только его, и в виде Bubble Babble:

```bash
ssh-keygen -l -E md5 -f ~/.ssh/id_ed25519_github.pub
ssh-keygen -B -f ~/.ssh/id_ed25519_github.pub
```

Преобразовать открытый ключ OpenSSH в формат RFC 4716 (нужен некоторым коммерческим SSH-серверам и сетевому оборудованию) и обратно:

```bash
ssh-keygen -e -m RFC4716 -f ~/.ssh/id_ed25519_github.pub > ./key-rfc4716.pub
ssh-keygen -i -m RFC4716 -f ./key-rfc4716.pub
```

`-m` принимает `RFC4716`, `PKCS8` и `PEM`. Импорт `-i` печатает ключ в формате OpenSSH на экран. Перевести **закрытый** ключ в старый формат PEM для программы, которая не понимает новый, можно сменой фразы с `-m PEM`; делайте это на копии файла и только при реальной необходимости:

```bash
cp ~/.ssh/id_rsa_legacy ./id_rsa_legacy.pem
ssh-keygen -p -m PEM -f ./id_rsa_legacy.pem
```

DNS-записи SSHFP для ключей сервера (выполняется на сервере):

```bash
ssh-keygen -r server.example.com -f /etc/ssh/ssh_host_ed25519_key.pub
```

Захешировать имена в существующем `known_hosts` (старая копия останется в `known_hosts.old`):

```bash
ssh-keygen -H -f ~/.ssh/known_hosts
```

Подписи данных и список доверенных подписантов:

```bash
ssh-keygen -Y sign -f ~/.ssh/id_ed25519_signing -n file ./release.tar.gz
ssh-keygen -Y find-principals -s ./release.tar.gz.sig -f ./allowed_signers
ssh-keygen -Y check-novalidate -n file -s ./release.tar.gz.sig < ./release.tar.gz
```

`find-principals` подскажет, какой записи из `allowed_signers` соответствует подпись, `check-novalidate` проверяет только целостность подписи без доверия к подписанту — для настоящей проверки нужен `-Y verify` (раздел 22.3).

Спецификация: [ssh-keygen(1)](https://man.openbsd.org/ssh-keygen). Справочник новых версий может перечислять алгоритмы, которых ещё нет в вашем Linux или GitHub. Не выбирайте экспериментально новый тип только из-за его присутствия на странице документации — нужна совместимость обеих сторон.

`ssh-keygen -A` создаёт **серверные** host keys, а не универсальный личный ключ. Удалять существующие host keys ради их обновления без плана ротации нельзя: клиенты увидят смену идентичности.

При `ssh-keygen -H` рядом может остаться `.old` с нехешированными именами серверов. Хеширование не превращает весь файл в зашифрованный секрет и не отменяет необходимость защиты резервных копий.

При импорте/экспорте некоторые режимы способны вывести закрытый материал. Не запускайте неизвестную комбинацию над личным ключом ради просмотра формата. Не используйте старый PEM-формат без требования конкретной системы.

Исторический параметр `ssh-keygen -o` встречается в старых инструкциях: он выбирал новый формат OpenSSH. В современных версиях этот формат используется по умолчанию, а наличие самого флага следует сверять с локальной справкой.

<a id="combinations"></a>
## 25. Сочетания параметров и типичные ошибки

### 25.1. Как собирать команду

Разделяйте задачу на четыре части:

1. Куда подключаться: пользователь, хост, `-p`, при необходимости `-J`.
2. Чем подтверждать доступ: `-i`, `IdentitiesOnly`, агент или FIDO2.
3. Какой сеанс нужен: оболочка, команда, `-t`, `-T` либо `-N`.
4. Как контролировать работу: проверка host key, таймаут, диагностика, forwarding.

Пример чтения состояния сервера через нестандартный порт:

```bash
ssh -p 2222 \
  -i ~/.ssh/id_ed25519_server \
  -o IdentitiesOnly=yes \
  -o StrictHostKeyChecking=yes \
  -o ConnectTimeout=10 \
  -T alice@server.example.com 'uptime'
```

Настроенные `Host` заменяют повторяющиеся параметры. Для сложных команд оставляйте флаги раздельными: `-N -T -v` читается понятнее, чем слитная запись.

### 25.2. Одинаковые буквы у разных программ

| Буква | ssh | ssh-keygen | scp / sftp |
| --- | --- | --- | --- |
| `-a` | Запрет forwarding агента. | Раунды KDF. | У sftp — попытка продолжить передачу. |
| `-C` | Сжатие. | Комментарий. | Сжатие. |
| `-f` | Фоновый режим. | Файл выбранной операции. | У sftp — запрос fsync после передачи. |
| `-i` | Файл идентичности. | Импорт. | Файл идентичности. |
| `-l` | Пользователь. | Отпечаток. | Лимит скорости. |
| `-N` | Без удалённой команды. | Новая парольная фраза. | У sftp — отменить тихий режим, включаемый `-b`; у scp нет. |
| `-p` | Порт. | Изменение парольной фразы. | Сохранение атрибутов. |
| `-P` | Метка конфигурации в новых версиях. | Старая парольная фраза. | Порт. |
| `-t` | Псевдотерминал. | Тип ключа. | Нет. |
| `-T` | Без терминала. | — | У scp — отключить проверку имён файлов от сервера. |
| `-R` | Обратный туннель. | Удалить запись known_hosts. | У scp — копировать между серверами напрямую; у sftp — число одновременных запросов. |
| `-A` | Пересылка агента. | Создать недостающие ключи сервера. | Пересылка агента. |
| `-D` | SOCKS-прокси. | Ключи PKCS#11. | Путь к локальному SFTP-серверу для отладки. |
| `-v` | Диагностика. | Диагностика / визуальный отпечаток с `-l`. | Диагностика. |

### 25.3. Комбинации, требующие внимания

| Комбинация | Что учитывать |
| --- | --- |
| `-N` и удалённая команда | Выберите туннель без команды либо выполнение команды. |
| `-T` и `-t` | Противоположные цели; задавайте одну политику явно. |
| `-n` и скрипт через stdin | `-n` лишает скрипт входных данных. |
| `-f` и stdin | Фоновый режим подразумевает прекращение чтения stdin. |
| `BatchMode=yes` и заблокированный ключ | Не будет интерактивного запроса фразы. |
| `IdentityAgent=none` и `ssh-add` | Для этого подключения загруженный агент не используется. |
| `IdentitiesOnly=yes` и несколько `IdentityFile` | Несколько настроенных ключей всё ещё могут предлагаться. |
| `-J` и `-A` | Forwarding агента обычно не нужен для перехода. |
| `-g` или bind `0.0.0.0` | Может открыть локальный туннель другим узлам сети. |
| `-R` и серверный `GatewayPorts` | Сервер ограничивает адрес прослушивания. |
| `-a 100` без passphrase | Нет ожидаемой защиты закрытого файла фразой. |
| FIDO2 и `ControlMaster` | Повторный сеанс может использовать уже авторизованный канал. |
| `-C` и уже сжатые данные | Дополнительное сжатие может только увеличить нагрузку. |

Параметры размещайте до имени узла. Текст после узла обычно относится к удалённой команде, а не является продолжением настройки клиента.

<a id="troubleshooting"></a>
## 26. Диагностика

### 26.1. Начинайте с фактов

```bash
ssh -V
ssh -G lab
ssh-add -l
ssh -vvv lab
```

Если необходимо исключить уже открытый master:

```bash
ssh -S none -o ControlMaster=no -vvv lab
```

В журнале последовательно проверяйте сетевой адрес, порт, host key, предлагаемый пользовательский ключ, ответ сервера и выбранный метод аутентификации.

Записать диагностику в отдельный файл:

```bash
umask 077
ssh -vvv -E ./ssh-debug.log lab
```

Лог может содержать реальные имена, IP, пути, отпечатки и команды. Перед передачей третьим лицам обезличьте его. Не прикладывайте закрытые ключи, файлы секретов и целиком каталог `~/.ssh`.

На сервере Debian/Ubuntu с соответствующей службой:

```bash
sudo journalctl -u ssh.service --since '15 minutes ago'
sudo sshd -t
sudo ss -ltnp
```

### 26.2. Таблица ошибок

| Сообщение / симптом | Проверка |
| --- | --- |
| `Could not resolve hostname` | Опечатка в имени, DNS, правильный `Host`/`HostName`, доступность сети. |
| `Connection timed out` | Маршрут, firewall, NAT, адрес и порт; это ещё не ошибка ключа. |
| `Connection refused` | Доступность слушателя, служба, порт, явный reject firewall. |
| `Permission denied (publickey)` | Пользователь, файл ключа, запись `.pub`, права, серверная политика. |
| `Too many authentication failures` | Лишние ключи агента; проверьте `IdentityFile` и `IdentitiesOnly`. |
| `UNPROTECTED PRIVATE KEY FILE` | Права и владелец закрытого файла; для личного ключа обычно `600`. |
| `Host key verification failed` | База доверия, непроверенный новый сервер или изменившийся ключ. |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | Сначала независимая сверка причины; не удаляйте запись автоматически. |
| `Could not open a connection to your authentication agent` | Доступен ли агент и корректен ли `SSH_AUTH_SOCK`. |
| `The agent has no identities` | Агент работает, но нужный ключ не загружен. |
| `sign_and_send_pubkey: signing failed` | Агент, доступ к токену, PIN, касание и выбранный ключ. |
| `No such file or directory` для `IdentityFile` | Путь, имя, домашний каталог и пользователь, от которого запускается SSH. |
| `invalid format` | Выбран не тот файл, повреждение переноса или неподдерживаемый формат. |
| `no matching host key type` | Совместимость host key; обновление старой стороны предпочтительнее глобального ослабления. |
| `no matching key exchange method` | Совместимость KEX; это не парольная фраза пользовательского ключа. |
| `Bad configuration option` | Опечатка или опция более новой/другой реализации OpenSSH. |
| `Address already in use` | Локальный порт туннеля занят; выберите другой или разберите владельца сокета. |
| `administratively prohibited` | Сервер запрещает forwarding или конкретное назначение. |
| Туннель поднялся, приложение не отвечает | Доступность цели с нужной стороны, адрес, DNS, порт и собственная авторизация приложения. |
| GitHub приветствует другой аккаунт | Предложен другой ключ; проверьте alias, агент и конфигурацию. |
| `Repository not found` после SSH-входа | Путь репозитория, права аккаунта, ограничения организации/SSO. |
| Git просит HTTPS credential | В репозитории настроен HTTPS transport; SSH-проверка к нему не относится. |
| `Permission denied (publickey,password)` | Сервер предлагает эти методы, но ни один не подошёл: проверьте пользователя, ключ и пароль. Список в скобках — методы, которые разрешает сервер. |
| `no mutual signature algorithm` | Старый сервер или ключ RSA с подписями SHA-1; обновите сервер или используйте Ed25519. Временное исключение — `PubkeyAcceptedAlgorithms +ssh-rsa` только для этого сервера. |
| `Unable to negotiate with ... no matching cipher found` | Сервер поддерживает только устаревшие шифры; ориентир — раздел 9.5, исключение только для конкретного устройства. |
| `kex_exchange_identification: read: Connection reset by peer` | Соединение оборвали до обмена версиями: firewall, `MaxStartups`, штраф `PerSourcePenalties`, ограничения провайдера. |
| `Connection closed by ... port 22` сразу после входа | `AllowUsers`/`DenyUsers`, `ForceCommand`, `ChrootDirectory` с неверными правами, оболочка `nologin`; см. журнал сервера. |
| `WARNING: connection is not using a post-quantum key exchange algorithm` | Сервер старше OpenSSH 9.0 и не поддерживает постквантовый обмен; обновите сервер (раздел 9.6). |
| `channel 0: open failed: connect failed` | Туннель создан, но сервер не может подключиться к цели `-L`: неверный адрес, порт или служба не запущена. |
| `remote port forwarding failed for listen port` | Порт `-R` на сервере занят или запрещён `PermitListen`/`AllowTcpForwarding`. |
| `Bad owner or permissions on ~/.ssh/config` | Файл конфигурации доступен на запись другим; выполните `chmod 600 ~/.ssh/config`. |
| `sign_and_send_pubkey: no mutual signature supported` | То же, что `no mutual signature algorithm`: сервер не принимает тип подписи ключа. |
| `Load key ...: incorrect passphrase supplied to decrypt private key` | Неверная парольная фраза или выбран не тот файл. |
| `agent refused operation` | Агент не смог подписать: ключ заперт (`ssh-add -X`), требует подтверждения, токен отключён или не получен PIN/касание. |

### 26.3. Аппаратный токен не работает

Проверьте по порядку:

1. Поддерживает ли клиент SK-типы (`ssh -Q key`).
2. Поддерживает ли сам токен выбранный алгоритм и `verify-required`.
3. Доступно ли устройство текущему пользователю Linux; нужны ли пакетные udev-правила производителя.
4. Не выполняется ли команда внутри контейнера или удалённой сессии без доступа к USB.
5. Выбран ли соответствующий локальный файл и добавлен ли именно его `.pub`.
6. Получено ли касание и корректно ли введён PIN.
7. Не перепутаны ли FIDO2 SSH, PIV/PKCS#11 и регистрация токена для веб-входа.

Не запускайте всё через root для обхода доступа к устройству и не делайте полный reset токена без понимания потери credentials. При неудачном PIN учитывайте ограничение попыток конкретного устройства.

### 26.4. Частые неверные выводы

- Отсутствие запроса парольной фразы может объясняться агентом или существующим master, а не отсутствием защиты файла.
- Успех `ssh -T` к GitHub подтверждает аккаунт, но не право записи в любой репозиторий.
- `chmod 600` не защищает украденную копию и не заменяет парольную фразу.
- Смена комментария `-C` не меняет владельца доступа на сервере.
- `-a 100` у `ssh-keygen` не задаёт серверный лимит попыток входа.
- Работа HTTPS на порту 443 не гарантирует, что сеть пропускает SSH на этом порту.
- Отпечаток пользовательского ключа и отпечаток сервера решают разные задачи.

## 27. Короткие рецепты

### Личный GitHub без аппаратного токена

```bash
umask 077
mkdir -p ~/.ssh
chmod 700 ~/.ssh
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_github -C "github-laptop"
cat ~/.ssh/id_ed25519_github.pub
```

Задать парольную фразу, добавить `.pub` как Authentication Key, настроить `github-personal`, сверить host fingerprint и проверить:

```bash
ssh -T git@github-personal
```

### GitHub с аппаратным FIDO2

Сначала задать PIN токена и проверить поддержку алгоритма:

```bash
ssh-keygen -t ed25519-sk -a 100 -O verify-required \
  -f ~/.ssh/id_ed25519_sk_github -C "github-fido-laptop"
```

Добавить `.pub`, настроить `github-fido`, подключить токен:

```bash
ssh -S none -o IdentityAgent=none -T git@github-fido
```

### Проверка Linux-входа по конкретному ключу

```bash
ssh -S none -F none -p 2222 \
  -i ~/.ssh/id_ed25519_server \
  -o IdentitiesOnly=yes \
  -o IdentityAgent=none \
  -o PreferredAuthentications=publickey \
  alice@server.example.com
```

### Локальный доступ к веб-сервису сервера

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18080:127.0.0.1:8080 lab
```

### Просмотр плана передачи каталога

```bash
rsync -av --dry-run ./documents/ lab:/home/alice/documents/
```

### Сменить парольную фразу, сохранив пару

```bash
ssh-keygen -p -a 100 -f ~/.ssh/id_ed25519_github
```

Эти рецепты предполагают подготовку, описанную в соответствующих разделах. Не создавайте повторно ключ поверх уже используемого файла.

## 28. Документация и границы применимости

Сведения сверены со справкой OpenSSH 10.2 (Ubuntu 26.04) и документацией Yubico в октябре 2026 года. Руководство содержит практические сценарии, справочник коротких параметров `ssh`, основные и специальные режимы `ssh-keygen`, а также объяснение всех настроек, использованных в примерах. У OpenSSH есть дополнительные директивы, платформенные возможности и параметры отдельных режимов; полный нормативный справочник следует читать для **своей версии**, а не предполагать одинаковое поведение всех выпусков.

Для поиска в Linux:

```bash
man ssh
man ssh-keygen
man ssh_config
man sshd
man sshd_config
man ssh-agent
man ssh-add
man scp
man sftp
```

В `man` клавиша `/` начинает поиск, `n` переходит к следующему совпадению, `q` выходит.

Основные первичные источники приведены рядом с соответствующими разделами. Дополнительно доступны [сайт OpenSSH](https://www.openssh.com/), [справочник OpenBSD](https://man.openbsd.org/) и [раздел GitHub об SSH](https://docs.github.com/en/authentication/connecting-to-github-with-ssh).

Конфигурации сервера, firewall, CA и ограничений доступа нужно адаптировать к существующей системе. Все перечисленные варианты не следует включать одновременно. Проверка синтаксиса примера не доказывает наличие вашего токена, сетевую доступность, работу конкретной версии ОС или правильность выбранных прав доступа.

Не сохраняйте в этом репозитории реальные SSH-ключи, токены, парольные фразы, резервные копии `~/.ssh`, сведения о личной инфраструктуре и необезличенные диагностические журналы.
