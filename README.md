# SSH в Linux: подробное практическое руководство

Руководство объясняет создание программных и аппаратных SSH-ключей, подключение к Linux и GitHub, настройки клиента и сервера, передачу файлов, туннели, автоматизацию и диагностику. Основной вариант — OpenSSH, обычный пользователь Linux и Ed25519 с парольной фразой. Аппаратный FIDO2-токен рассматривается отдельно.

Все имена пользователей, комментарии, домены и адреса в примерах вымышлены. `server.example.com`, `bastion.example.com`, `alice`, `OWNER`, `REPOSITORY`, `YOUR_LOGIN` — заполнители. IPv4-адреса `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` предназначены для документации. `127.0.0.1` означает текущую машину. Настоящих ключей, паролей, токенов, адресов серверов и персональных контактов здесь нет.

Команды рассчитаны на Bash или Zsh в Linux. Они не образуют один скрипт: выбирайте нужный сценарий. Блоки с `sshconfig` — содержимое конфигурационного файла, а не команды терминала. Значения параметров и доступность новых возможностей зависят от установленной версии OpenSSH.

## 1. Термины и устройство SSH

SSH создаёт зашифрованное соединение между клиентом и сервером. Клиент обычно запускается командой `ssh`; сервер Linux принимает подключения через `sshd`. GitHub тоже принимает SSH-соединения, но предоставляет через них операции Git, а не обычную оболочку Linux.

| Термин | Значение |
| --- | --- |
| Закрытый ключ | Секретный материал, которым клиент доказывает право доступа. Программный ключ хранится в файле на вашем устройстве. |
| Открытый ключ | Часть пары, которую добавляют на сервер или в GitHub. Знание открытого ключа само по себе не позволяет войти. |
| Парольная фраза, passphrase | Защищает файл закрытого ключа на диске. Вводится локально и не является паролем сервера. |
| Пароль пользователя Linux | Проверяется сервером при парольной аутентификации. Может существовать одновременно с доступом по ключу. |
| Ключ сервера, host key | Подтверждает клиенту, к какому серверу он подключился. Это другая пара ключей. |
| Отпечаток, fingerprint | Короткое представление хеша открытого ключа для сверки. Не заменяет сам ключ при настройке доступа. |
| SSH-агент | Локальная программа, которая выполняет подписи с загруженными ключами. |
| Аппаратный токен | Физическое устройство, участвующее в создании подписи; например, FIDO2-ключ. |
| GitHub PAT | Секретная строка для API и Git через HTTPS. Не является SSH-ключом или аппаратным устройством. |
| Параметр команды | Флаг вроде `-i`, `-p`, `-a`; слово «ключ» иногда используют и в этом значении. |

При входе по ключу закрытый ключ не отправляется серверу. Клиент создаёт подпись, сервер проверяет её по разрешённому открытому ключу. Шифрование всего соединения согласовывается отдельно: выбор Ed25519 не означает, что каждый передаваемый файл шифруется алгоритмом Ed25519.

Открытые ключи не секретны, но их комментарии и повторное использование могут связывать устройства и аккаунты. В комментариях удобно писать назначение вроде `github-laptop`, без реального имени и почты.

<a id="prepare"></a>
## 2. Подготовка Linux

На **клиентском компьютере** проверьте наличие OpenSSH:

```bash
ssh -V
command -v ssh ssh-keygen ssh-add
```

Для Debian/Ubuntu клиент устанавливается так:

```bash
sudo apt update
sudo apt install openssh-client
```

Чтобы только подключаться к другим машинам, устанавливать и запускать `openssh-server` на своём компьютере не требуется. Установка сервера рассмотрена отдельно.

Подготовьте каталог от имени своего пользователя, без `sudo`:

```bash
umask 077
mkdir -p ~/.ssh
chmod 700 ~/.ssh
ls -la ~/.ssh
```

`~` — домашний каталог текущего пользователя. `mkdir -p` создаёт отсутствующий каталог и не очищает существующий. `umask 077` ограничивает права новых файлов в текущей оболочке; уже существующие файлы он не исправляет. `ls` показывает имена и права, а не содержимое ключей.

Не создавайте личный ключ через `sudo ssh-keygen`: он может оказаться в домашнем каталоге root или получить неудобного владельца.

Проверьте локальную справку:

```bash
man ssh
man ssh-keygen
man ssh_config
```

Она соответствует установленной версии лучше, чем инструкция для самого нового выпуска. Установка пакетов описана в [документации Ubuntu](https://ubuntu.com/server/docs/how-to/security/openssh-server/).

<a id="software-key"></a>
## 3. Создание ключа без аппаратного токена

### 3.1. Рекомендуемый вариант для личного доступа

На компьютере, с которого будете подключаться:

```bash
ssh-keygen -t ed25519 -a 100 \
  -f ~/.ssh/id_ed25519_github \
  -C "github-laptop"
```

Обратная косая черта `\` в конце строки продолжает команду. После неё не должно быть пробелов. Та же команда одной строкой:

```bash
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_github -C "github-laptop"
```

Если программа сообщает, что файл существует, **не соглашайтесь на перезапись**. Выберите другое имя, например `id_ed25519_github_new`. Перезапись может лишить доступа к системам, где зарегистрирован старый открытый ключ.

На запрос `Enter passphrase` введите длинную уникальную парольную фразу. Затем повторите её. Символы при вводе не отображаются. Не копируйте в качестве пароля фразу из публичного руководства.

Создаются:

```text
~/.ssh/id_ed25519_github       закрытый ключ
~/.ssh/id_ed25519_github.pub   открытый ключ
```

Показать только открытую часть и её отпечаток:

```bash
cat ~/.ssh/id_ed25519_github.pub
ssh-keygen -l -E sha256 -f ~/.ssh/id_ed25519_github.pub
```

GitHub рекомендует Ed25519 для новых ключей. [Создание ключа для GitHub](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent).

### 3.2. Отдельный ключ для Linux-сервера

```bash
ssh-keygen -t ed25519 -a 100 \
  -f ~/.ssh/id_ed25519_server \
  -C "linux-admin-laptop"
```

Разделение по устройствам и назначениям упрощает отзыв: потеря ноутбука не требует менять ключ другого компьютера. Разные имена файлов сами по себе не ограничивают права — ограничения задаются на стороне принимающей системы.

### 3.3. RSA для совместимости

Если целевая система не поддерживает Ed25519 или её политика требует RSA:

```bash
ssh-keygen -t rsa -b 4096 -a 100 \
  -f ~/.ssh/id_rsa_legacy \
  -C "legacy-access"
```

Это вариант совместимости, а не автоматическое повышение защиты относительно Ed25519. Не сравнивайте числа бит у разных семейств алгоритмов напрямую. Для RSA важна также поддержка современных подписей SHA-2; не включайте устаревшие SHA-1-подписи глобально ради одного старого устройства.

Ed25519 имеет фиксированный размер. Добавление `-b 4096` не сделает его «Ed25519 на 4096 бит». DSA для нового доступа не используйте. В средах FIPS поддержка алгоритмов может ограничиваться политикой конкретной системы.

<a id="keygen-options"></a>
## 4. Что означают параметры ssh-keygen

В основной команде:

| Часть | Назначение |
| --- | --- |
| `ssh-keygen` | Создание и обслуживание ключей. |
| `-t ed25519` | Тип ключа. |
| `-a 100` | Число раундов защиты парольной фразы при сохранении. |
| `-f ПУТЬ` | Имя файла; `.pub` создаётся рядом. |
| `-C "метка"` | Комментарий, не обязательно email. |
| `-b 4096` | Размер RSA; у Ed25519 неприменим. |

Другие часто нужные режимы:

| Параметр | Назначение |
| --- | --- |
| `-p` | Изменить парольную фразу существующего ключа. |
| `-c` | Изменить комментарий. |
| `-l` | Показать отпечаток. |
| `-E sha256` | Выбрать хеш отпечатка. |
| `-y` | Получить открытую часть из закрытого ключа. |
| `-N`, `-P` | Передать новую/старую парольную фразу аргументом; для ручной работы избегайте. |
| `-O` | Дополнительная настройка выбранного режима. |
| `-Z` | Шифр хранения закрытого ключа. |
| `-m` | Формат импорта/экспорта или совместимости. |
| `-q`, `-v` | Меньше/больше диагностического вывода. |

Буквы регистрозависимы: `-C` и `-c` различаются. Подробная спецификация режимов находится в [ssh-keygen(1)](https://man.openbsd.org/ssh-keygen).

### Примеры обслуживания

Поменять парольную фразу и сохранить файл с выбранной трудоёмкостью KDF:

```bash
ssh-keygen -p -a 100 -f ~/.ssh/id_ed25519_github
```

Программа сама запросит старую и новую фразы. Публичная часть ключевой пары не меняется: повторно добавлять её в GitHub не нужно.

Изменить только поясняющую метку:

```bash
ssh-keygen -c -C "github-desktop" -f ~/.ssh/id_ed25519_github
```

Восстановить потерянный `.pub`, не выводя закрытый материал в терминал:

```bash
ssh-keygen -y -f ~/.ssh/id_ed25519_github > ~/.ssh/id_ed25519_github.recovered.pub
ssh-keygen -l -f ~/.ssh/id_ed25519_github.recovered.pub
```

Выход `-y` — открытый ключ; исходный закрытый файл обрабатывает сама программа. Новый файл специально имеет другое имя, чтобы не затереть уже существующую открытую часть.

<a id="passphrase"></a>
## 5. Парольная фраза и значение -a

У файла программного ключа есть два разных уровня защиты: права Linux ограничивают доступ к файлу, парольная фраза затрудняет использование украденной копии. Если злоумышленник уже управляет вашей разблокированной системой, одной парольной фразы недостаточно: он может перехватить ввод или воспользоваться доступным агентом.

`-a 100` задаёт 100 раундов KDF `bcrypt_pbkdf`. Это **не** размер ключа, не срок действия, не число попыток входа и не параметр сетевого шифрования. Значение применяется при защите файла парольной фразой. Без неё повышение `-a` не создаёт эквивалентной защиты.

Практическая схема выбора:

1. Создайте уникальную длинную фразу, например из нескольких независимо выбранных случайных слов, и сохраните её в надёжном менеджере паролей.
2. Начните с `-a 100`.
3. Проверьте, комфортно ли разблокировать ключ на самом медленном вашем устройстве.
4. При желании увеличьте значение до `200` или `300`, сохранив разумное время ожидания.

Зависимость времени от числа раундов следует оценивать на своей машине. Нельзя обещать одинаковые миллисекунды для ноутбука и маломощного устройства. Значение по умолчанию менялось между версиями OpenSSH — не считайте число из старой статьи универсальным.

Фраза не должна быть вашим паролем GitHub, паролем Linux или строкой из известной книги. Не передавайте её через `-N "секрет"`, shell history, сообщения, Git или URL. Интерактивный запрос избавляет от необходимости помещать секрет в аргументы процесса.

<a id="files"></a>
## 6. Файлы SSH и права доступа

| Путь | Где находится | Что содержит |
| --- | --- | --- |
| `~/.ssh/id_ed25519_github` | Клиент | Закрытый ключ. |
| `~/.ssh/id_ed25519_github.pub` | Клиент | Открытый ключ. |
| `~/.ssh/config` | Клиент | Псевдонимы и настройки подключений. |
| `~/.ssh/known_hosts` | Клиент | Сохранённые открытые ключи серверов. |
| `~/.ssh/authorized_keys` | Сервер, у целевого пользователя | Открытые ключи, которым разрешён вход. |
| `/etc/ssh/ssh_config` | Клиент | Общесистемные настройки клиента. |
| `/etc/ssh/sshd_config` | Сервер | Настройки демона. |
| `/etc/ssh/ssh_host_*_key` | Сервер | Закрытые ключи идентичности сервера. |

Для существующих личных файлов:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519_github
chmod 644 ~/.ssh/id_ed25519_github.pub
```

Для конфигурации:

```bash
touch ~/.ssh/config
chmod 600 ~/.ssh/config
```

На сервере, от имени пользователя, которому нужен вход:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

`700` — доступ владельцу каталога; `600` — чтение и запись владельцу файла; `644` — запись владельцу, чтение остальным. Открытый ключ допустимо хранить и с более строгими правами.

Не применяйте `chmod -R 777`, не меняйте рекурсивно весь домашний каталог. Проверьте владельца и доступность родительских каталогов; сервер может отклонять небезопасные права при `StrictModes yes`. На системах с SELinux могут дополнительно требоваться корректные метки, а на файловых системах с ACL — проверка ACL.

<a id="host-verification"></a>
## 7. Отпечатки и проверка сервера

При первом подключении клиент ещё не знает host key. Отпечаток следует получить по независимому доверенному каналу: из консоли сервера, панели провайдера или от администратора. На серверной консоли показать отпечаток открытого host key можно так:

```bash
sudo ssh-keygen -l -E sha256 -f /etc/ssh/ssh_host_ed25519_key.pub
```

Сравнивайте алгоритм и полный отпечаток. Только после совпадения принимайте ключ. Для GitHub используйте [официальную страницу отпечатков](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints), а не число из случайной статьи.

Найти уже сохранённую запись:

```bash
ssh-keygen -F server.example.com
ssh-keygen -F '[server.example.com]:2222'
```

После подтверждённой переустановки сервера или согласованной ротации его host key можно удалить конкретную старую запись и заново сверить новую:

```bash
ssh-keygen -R server.example.com
ssh-keygen -R '[server.example.com]:2222'
```

Не запускайте удаление автоматически при `REMOTE HOST IDENTIFICATION HAS CHANGED`. Причиной бывает как нормальная переустановка, так и подмена подключения.

`ssh-keyscan` только получает открытый ключ из сети. Он **не подтверждает**, что отвечает правильная машина. Слепое добавление его вывода в `known_hosts` не заменяет сверку. [Описание ssh-keyscan](https://man.openbsd.org/ssh-keyscan).

Для уже настроенного соединения удобно требовать заранее известный ключ:

```bash
ssh -o StrictHostKeyChecking=yes alice@server.example.com
```

Это не подключится к новому неизвестному серверу, пока вы не установите доверие отдельно. `accept-new` автоматически доверяет первому ключу, но отказывается от изменившегося; это удобство первоначального подключения, а не независимая проверка личности сервера. Не используйте `StrictHostKeyChecking=no` и `UserKnownHostsFile=/dev/null` как универсальное исправление ошибок.

<a id="linux-login"></a>
## 8. Подключение к Linux-серверу

### 8.1. Добавление открытого ключа

Пользователь `alice` должен уже существовать на сервере. Для первоначальной установки нужен разрешённый доступ: пароль, старый ключ или серверная консоль.

На клиенте:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519_server.pub alice@server.example.com
```

Для другого порта:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519_server.pub -p 2222 alice@server.example.com
```

Укажите именно `.pub`: на сервер переносится открытый ключ. На GitHub `ssh-copy-id` не применяется — там используется интерфейс аккаунта.

Если `ssh-copy-id` отсутствует, можно передать открытую часть через уже доверенное соединение:

```bash
ssh alice@server.example.com \
  'umask 077; mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys' \
  < ~/.ssh/id_ed25519_server.pub
```

Здесь `>>` дописывает, а `>` затёр бы старые разрешённые ключи. Повтор этой ручной команды добавляет повторную строку. При последующем редактировании сохраняйте ключи других пользователей и устройств.

### 8.2. Вход по выбранному ключу

```bash
ssh -i ~/.ssh/id_ed25519_server \
  -o IdentitiesOnly=yes \
  alice@server.example.com
```

С портом:

```bash
ssh -p 2222 -i ~/.ssh/id_ed25519_server \
  -o IdentitiesOnly=yes alice@server.example.com
```

`-i` выбирает файл идентичности; `IdentitiesOnly=yes` ограничивает предложение настроенными ключами. При обычной конфигурации это предотвращает перебор всех ключей агента. Если нужно исключить дополнительные `IdentityFile` из других конфигурационных блоков, проверьте `ssh -G` либо используйте отдельную конфигурацию.

Убедиться, что вход не подменяется серверным паролем:

```bash
ssh -i ~/.ssh/id_ed25519_server \
  -o IdentitiesOnly=yes \
  -o PreferredAuthentications=publickey \
  -o PasswordAuthentication=no \
  -o KbdInteractiveAuthentication=no \
  alice@server.example.com
```

Локальная парольная фраза ключа при этом может запрашиваться. `exit` завершает удалённую оболочку. Сочетание Enter, затем `~.` аварийно разрывает интерактивное соединение при стандартном escape-символе.

<a id="client-config"></a>
## 9. Настройка клиента и псевдонимы

Откройте `~/.ssh/config` своим редактором. Добавьте блок, сохранив имеющиеся записи:

```sshconfig
Host lab
    HostName server.example.com
    User alice
    Port 2222
    IdentityFile ~/.ssh/id_ed25519_server
    IdentitiesOnly yes
    ForwardAgent no
    StrictHostKeyChecking ask
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

Теперь достаточно:

```bash
ssh lab
scp ./notes.txt lab:/home/alice/
sftp lab
```

| Настройка | Смысл |
| --- | --- |
| `Host` | Имя или шаблон, который набирают в команде. |
| `HostName` | Настоящее сетевое имя или адрес. |
| `User`, `Port` | Пользователь и порт назначения. |
| `IdentityFile` | Ключ для подключения; может повторяться. |
| `IdentitiesOnly` | Ограничение предлагаемого набора идентичностей. |
| `ForwardAgent` | Доступ удалённой машины к локальному агенту. |
| `IdentityAgent none` | Полное отключение агента для подключения. |
| `StrictHostKeyChecking` | Правила доверия host key. |
| `ServerAliveInterval`, `ServerAliveCountMax` | Проверка ответа сервера через защищённый канал. |
| `ConnectTimeout` | Ограничение ожидания подключения и начального обмена. |
| `BatchMode yes` | Запрет интерактивных запросов аутентификации. |
| `ProxyJump` | Промежуточный SSH-сервер. |
| `Include` | Подключение других файлов конфигурации. |
| `AddKeysToAgent` | Автоматическое добавление ключа в агент. |

Для большинства настроек действует **первое полученное значение**. Поэтому конкретные `Host` обычно располагают раньше общего `Host *`. Некоторые параметры накапливаются, в частности `IdentityFile`. [Правила ssh_config](https://man.openbsd.org/ssh_config).

Проверить итоговую конфигурацию без сетевого подключения:

```bash
ssh -G lab
```

Так можно обнаружить неожиданный порт, пользователя или дополнительные ключи. Вывод содержит ваши реальные адреса и пути — перед публикацией его обезличьте.

Альтернативный файл:

```bash
ssh -F ~/.ssh/config-lab lab
```

Для конкретного диагностического запуска без обычных файлов конфигурации:

```bash
ssh -F none -p 2222 -i ~/.ssh/id_ed25519_server \
  -o IdentitiesOnly=yes -o IdentityAgent=none \
  alice@server.example.com
```

`-F none` не отключает проверку host key. Не помещайте секреты в конфигурацию: она должна содержать пути к ключам, а не их содержимое и не парольные фразы.

<a id="github"></a>
## 10. GitHub и несколько аккаунтов

### 10.1. Добавление открытого ключа

Покажите открытую часть:

```bash
cat ~/.ssh/id_ed25519_github.pub
```

На GitHub откройте **Settings → SSH and GPG keys → New SSH key**. Укажите понятное название устройства, тип **Authentication Key**, вставьте одну полную строку `.pub`. Комментарий после ключа не обязан совпадать с email аккаунта. [Добавление ключа](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/adding-a-new-ssh-key-to-your-github-account).

### 10.2. Псевдоним для аккаунта

```sshconfig
Host github-personal
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_github
    IdentitiesOnly yes
    ForwardAgent no
```

Проверка:

```bash
ssh -T git@github-personal
```

У GitHub SSH-пользователь — всегда `git`; аккаунт определяется предъявленным ключом. Успешный ответ приветствует ваш логин и сообщает об отсутствии shell-доступа. При таком успешном тесте GitHub использует код завершения `1`, что не следует путать с отказом аутентификации. [Проверка соединения](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/testing-your-ssh-connection).

Клонирование и настройка уже существующего репозитория:

```bash
git clone git@github-personal:OWNER/REPOSITORY.git
```

```bash
git remote set-url origin git@github-personal:OWNER/REPOSITORY.git
git ls-remote --heads origin
```

Последние команды выполняются внутри нужного локального репозитория. В SSH URL нет токена. `OWNER` может быть владельцем другого аккаунта или организацией: право доступа определяется настройками репозитория.

### 10.3. Два аккаунта

Создайте второй ключ с другим именем и добавьте его во второй аккаунт:

```bash
ssh-keygen -t ed25519 -a 100 \
  -f ~/.ssh/id_ed25519_github_work \
  -C "github-work-laptop"
```

```sshconfig
Host github-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_github_work
    IdentitiesOnly yes
    ForwardAgent no
```

```bash
ssh -T git@github-personal
ssh -T git@github-work
git clone git@github-work:WORK_OWNER/REPOSITORY.git
```

Проверьте логин в каждом приветствии. Не пытайтесь прикрепить одну и ту же личную SSH-пару к двум разным GitHub-аккаунтам — используйте независимые пары.

### 10.4. Автор коммита — отдельная настройка

SSH определяет доступ к репозиторию, но не автора коммита. Внутри каждого клона задайте имя и **свой точный GitHub noreply-адрес из Settings → Emails**:

```bash
git config user.name "YOUR_LOGIN"
git config user.email "YOUR_GITHUB_NOREPLY_ADDRESS"
```

Вторая строка содержит заполнитель: замените его настоящим noreply-адресом перед выполнением. Не подставляйте личную почту в публичные примеры. Обычно современный адрес имеет форму `ID+LOGIN@users.noreply.github.com`; его следует скопировать из настроек, а не угадывать. [Справка GitHub об email](https://docs.github.com/en/account-and-profile/reference/email-addresses-reference).

### 10.5. Если сеть блокирует порт 22

Для GitHub.com доступен специальный SSH endpoint на TCP 443:

```sshconfig
Host github-personal-443
    HostName ssh.github.com
    Port 443
    User git
    IdentityFile ~/.ssh/id_ed25519_github
    IdentitiesOnly yes
    ForwardAgent no
```

```bash
ssh -T git@github-personal-443
git clone git@github-personal-443:OWNER/REPOSITORY.git
```

Это SSH на порту 443, а не превращение протокола в HTTPS. HTTPS-прокси может его блокировать. Используется `ssh.github.com`, а не `github.com:443`; для Enterprise действуют отдельные ограничения. [Официальная инструкция](https://docs.github.com/en/authentication/troubleshooting-ssh/using-ssh-over-the-https-port).

<a id="agent"></a>
## 11. SSH-агент

Агент позволяет разблокировать программный ключ один раз и затем выполнять подписи без повторного ввода фразы. Он хранит доступную для использования идентичность, а не превращает серверный вход в парольный.

Проверить, доступен ли агент, и увидеть только отпечатки:

```bash
ssh-add -l
```

Если агента нет и его не предоставляет графическая сессия, запустите его для текущей оболочки:

```bash
eval "$(ssh-agent -s)"
```

Не добавляйте безусловный запуск в каждый shell startup-файл: иначе можно создавать множество ненужных агентов.

Загрузить ключ на один час:

```bash
ssh-add -t 1h ~/.ssh/id_ed25519_github
```

Показать открытые части, удалить одну идентичность или все загруженные идентичности:

```bash
ssh-add -L
ssh-add -d ~/.ssh/id_ed25519_github.pub
ssh-add -D
```

Удаление из агента не удаляет файлы и не отзывает ключ на GitHub. `-t` ограничивает доступность загруженного ключа, но не завершает уже открытые SSH-сессии. При необходимости используйте `ssh-add -c` для подтверждения операций: это требует работоспособного механизма `ssh-askpass`. [ssh-add](https://man.openbsd.org/ssh-add), [ssh-agent](https://man.openbsd.org/ssh-agent).

Чтобы запросить парольную фразу напрямую и обойти агент:

```bash
ssh -o IdentityAgent=none -i ~/.ssh/id_ed25519_github \
  -o IdentitiesOnly=yes -T git@github.com
```

`ForwardAgent no` и `IdentityAgent none` различаются: первое запрещает прокидывать агент на удалённую машину, второе отключает его использование самим клиентом. `ssh -A` не копирует закрытый ключ на сервер, но предоставляет возможность просить локальный агент выполнить подпись. Для доступа через промежуточную машину обычно достаточно `ProxyJump`.

<a id="fido"></a>
## 12. Аппаратный FIDO2-токен

### 12.1. Что требуется

Нужен аппаратный аутентификатор, поддерживающий используемый OpenSSH механизм FIDO и выбранный алгоритм. Наличие USB-разъёма или поддержки входа на сайты само по себе не гарантирует поддержку `ed25519-sk`. Клиентская сборка OpenSSH должна включать соответствующую поддержку; аппаратные SSH-ключи появились в OpenSSH 8.2.

Проверьте версию и доступные типы:

```bash
ssh -V
ssh -Q key
```

В списке ищите типы с `sk-`, например `sk-ssh-ed25519@openssh.com`. Это показывает возможности программы, но не подтверждает возможности конкретного токена.

Токен содержит неэкспортируемый секрет устройства; локальный файл содержит материал, необходимый для обращения к ключу. Для обычного, нерезидентного варианта нужны **и токен, и локальный файл**. Парольная фраза файла, PIN токена и касание выполняют разные задачи. [Поддержка аппаратных ключей GitHub](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent).

### 12.2. Создание с PIN и касанием

Сначала настройте FIDO2 PIN в официальной программе производителя. Если токен уже используется, учитывайте действующие настройки; сброс FIDO может удалить зарегистрированные учётные данные. Не выполняйте reset ради обычной смены PIN.

Подключите токен и выполните:

```bash
ssh-keygen -t ed25519-sk -a 100 -O verify-required \
  -f ~/.ssh/id_ed25519_sk_github \
  -C "github-fido-laptop"
```

Подтвердите операцию на токене и задайте парольную фразу локального файла. `verify-required` запрашивает проверку пользователя токеном, обычно PIN. Касание требуется по умолчанию. Поддержка конкретной проверки зависит от токена и программного обеспечения.

Если токен не поддерживает Ed25519-SK, совместимый вариант:

```bash
ssh-keygen -t ecdsa-sk -a 100 -O verify-required \
  -f ~/.ssh/id_ecdsa_sk_github \
  -C "github-fido-laptop"
```

Добавьте соответствующий `.pub` в GitHub как **Authentication Key**, как и для программного ключа.

```sshconfig
Host github-fido
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_sk_github
    IdentitiesOnly yes
    ForwardAgent no
    IdentityAgent none
```

Если создали `ecdsa-sk`, измените `IdentityFile`. Проверка и использование:

```bash
ssh -T git@github-fido
git clone git@github-fido:OWNER/REPOSITORY.git
```

Установка `IdentityAgent none` — строгий вариант без агента. При обычном агенте требования токена к пользовательскому подтверждению не следует считать отключёнными: агент не превращает аппаратный ключ в экспортируемый программный.

### 12.3. Резидентный ключ

Это отдельный вариант для переноса доступа между компьютерами. Дескриптор ключа хранится на самом токене:

```bash
ssh-keygen -t ed25519-sk -O resident -O verify-required \
  -O application=ssh:github-guide -O user=portable-key \
  -a 100 -f ~/.ssh/id_ed25519_sk_portable \
  -C "github-fido-portable"
```

Устройство должно поддерживать resident credentials. `application` начинается с `ssh:` и различает назначение, `user` задаёт метку резидентной записи. Эти строки не должны содержать личные данные.

На другом доверенном компьютере получить локальные файлы можно в **новом пустом защищённом каталоге**:

```bash
umask 077
mkdir ~/ssh-fido-import
cd ~/ssh-fido-import
ssh-keygen -K
```

Посмотрите созданные имена через `ls -la`, назначьте парольную фразу нужному файлу через `ssh-keygen -p -a 100 -f ПУТЬ` и аккуратно разместите его в `~/.ssh`. Не импортируйте поверх существующих файлов. `ssh-add -K` загружает резидентные ключи в агент; на системах с другим вариантом `ssh-add` сначала проверьте локальную справку.

Нерезидентный вариант лучше разделяет устройство и локальный файл. Резидентный удобнее переносить, но украденный токен содержит больше необходимой для доступа информации. PIN и правила подтверждения остаются важны. [Модель FIDO в OpenSSH](https://man.openbsd.org/ssh-keygen#FIDO_AUTHENTICATOR).

### 12.4. Дополнительные параметры FIDO

| Настройка | Применение |
| --- | --- |
| `-O verify-required` | Проверка пользователя при подписи. |
| `-O resident` | Хранение дескриптора на токене. |
| `-O application=ssh:...` | Разделение назначений. |
| `-O user=...` | Метка резидентной записи. |
| `-O device=...` | Выбор устройства; синтаксис зависит от платформы. |
| `-w ПУТЬ` | Внешний FIDO provider при специальной интеграции. |
| `-O no-touch-required` | Снятие требования касания; не включайте ради удобства личного доступа. |
| `-O write-attestation=ПУТЬ` | Сохранение аттестации; может раскрывать сведения об устройстве. |

Не каждый параметр поддерживается каждой версией. Пример `verify-required` относится к FIDO; добавление его к обычному `ed25519` не создаёт аппаратной защиты.

### 12.5. Резервный доступ

Создайте независимый ключ на втором токене и добавьте его в аккаунт заранее. Скопировать неэкспортируемый секрет первого токена на второй обычной командой нельзя. Для нерезидентного ключа защищённая копия локального файла также нужна; сам файл без рабочего токена не восстановит доступ.

Отдельно настройте восстановление веб-доступа к GitHub. Потеря SSH-токена не должна одновременно лишать вас всех способов войти в настройки аккаунта. Регистрация токена как passkey/2FA для сайта и создание SSH-SK ключа — разные операции.

<a id="pat"></a>
## 13. GitHub PAT: отдельный способ доступа

PAT нужен для определённых операций API или Git по HTTPS. Он **не передаётся** в `ssh -i`, не добавляется в `authorized_keys` и не заменяет PIN аппаратного токена. Успешный `git push` через SSH также не авторизует автоматически отдельный запрос к REST API.

Если нужен PAT, в GitHub откройте **Settings → Developer settings → Personal access tokens**. Предпочитайте fine-grained token с выбранным владельцем ресурсов, конкретными репозиториями, минимальными разрешениями и сроком действия. Для чтения содержимого нужен соответствующий доступ на чтение; для записи — на запись. Организация может требовать одобрения. Не выдавайте полномочия администратора ради обычного клонирования. [Управление PAT](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

Пример HTTPS URL без секрета:

```bash
git clone https://github.com/OWNER/REPOSITORY.git
```

При прямом интерактивном запросе Git для приватного репозитория имя пользователя — логин GitHub, а в поле пароля используется PAT. Если уже настроен credential manager, он может провести вход по собственному сценарию и не показывать этот запрос.

Для повседневной работы используйте Git Credential Manager с поддерживаемым защищённым хранилищем вашей Linux-сессии. Не считайте `credential.helper store` шифрованным хранилищем: он записывает секрет на диск открытым текстом. Не вставляйте PAT в URL, команды, `.git/config`, логи и README. [Хранение учётных данных GitHub](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git).

Для автоматизации секрет обычно передают процессу через предусмотренное защищённое хранилище CI. Переменная окружения не является абсолютной защитой: секрет нельзя печатать, сериализовать в отчёт, включать в отладочный `set -x` или передавать недоверенному процессу. Не используйте личный PAT с широкими правами, если задачу решает более узкий механизм.

| Задача | Подходящий способ |
| --- | --- |
| Личный Git через SSH | Обычный SSH-ключ или FIDO2 SSH-ключ. |
| Git через HTTPS | Credential manager или PAT с нужными правами. |
| REST API GitHub | Разрешённый API credential, например PAT или GitHub App. |
| Чтение одного репозитория сервером | Отдельный read-only deploy key либо иной узкий сервисный доступ. |
| Вход на сайт | Пароль/passkey и настроенная защита аккаунта; SSH-ключ не заменяет веб-вход. |

<a id="server"></a>
## 14. Настройка SSH-сервера Linux

### 14.1. Установка и проверка

Следующие команды выполняются **на сервере**, а не на компьютере-клиенте. Пример для Debian/Ubuntu с systemd:

```bash
sudo apt update
sudo apt install openssh-server
sudo systemctl status ssh.service
sudo ss -ltnp
```

В других дистрибутивах служба часто называется `sshd.service`; названия пакетов и средства управления firewall отличаются. Проверьте документацию своей системы. Некоторые Ubuntu используют `ssh.socket` для активации; при изменении порта нужно учитывать сокет, а не только конфигурацию демона.

```bash
systemctl status ssh.socket
systemctl cat ssh.service ssh.socket
```

Отсутствие socket unit в другой системе само по себе не ошибка. Открывать SSH всему интернету для использования GitHub не требуется.

### 14.2. Сначала обеспечить второй проверенный вход

Перед отключением паролей:

1. Убедитесь, что есть консоль провайдера или другой способ восстановить доступ.
2. Создайте обычного пользователя с нужными административными правами либо используйте существующего.
3. Добавьте его открытый ключ и проверьте `sudo` при необходимости.
4. Оставьте текущую SSH-сессию открытой.
5. Откройте **новое** соединение с принудительной аутентификацией по ключу из раздела 8.
6. Сохраните резервные копии изменяемых файлов конфигурации, включая используемые snippets.

Успешный вход root не доказывает, что после `PermitRootLogin no` получится войти обычным пользователем. Существующая сессия также не доказывает, что новая конфигурация разрешает новые подключения.

Если на новом Debian/Ubuntu-сервере ещё нет нужного пользователя, пример создания из административной сессии:

```bash
sudo adduser alice
sudo usermod -aG sudo alice
```

Замените `alice` выбранным именем; не создавайте повторно существующего пользователя. Вторая команда добавляет административные полномочия и нужна только тому, кто действительно должен администрировать сервер. Не убирайте `-a`: без него изменение дополнительных групп может лишить пользователя прежних членств. Затем войдите как новый пользователь, добавьте его `.pub` и проверьте необходимые действия через `sudo`.

### 14.3. Пример конфигурации только для ключей

После проверки доступа можно применить следующие настройки:

```sshconfig
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
AuthenticationMethods publickey
PermitRootLogin no
X11Forwarding no
AllowAgentForwarding no
```

| Настройка | Назначение |
| --- | --- |
| `PubkeyAuthentication` | Вход по открытым ключам. |
| `PasswordAuthentication` | Метод серверного пароля. |
| `KbdInteractiveAuthentication` | Интерактивные механизмы, включая некоторые PAM/MFA-сценарии. |
| `AuthenticationMethods` | Требуемый набор методов. |
| `PermitRootLogin` | Возможность прямого входа root. |
| `X11Forwarding` | Перенаправление X11. |
| `AllowAgentForwarding` | Перенаправление SSH-агента. |

Это профиль **только для publickey**, не шаблон для сервера с PAM/TOTP: отключение keyboard-interactive может нарушить нужную MFA-схему. Не отключайте `UsePAM` без понимания зависимых механизмов учётных записей и сессий.

Для ограничения списка пользователей существует `AllowUsers`, например `AllowUsers alice deploy`. Добавляйте его только после учёта всех законных пользователей и сервисов. Не копируйте вымышленные имена в рабочую конфигурацию.

Где разместить настройки, зависит от реального `Include`. В стандартной Ubuntu обычно используются `/etc/ssh/sshd_config.d/*.conf`, подключённые в начале основного файла. Имена файлов сортируются, а для большинства директив важно первое значение. Поэтому файл `99-hardening.conf` **не гарантирует**, что перекроет более ранние настройки. Проверьте существующий порядок и итог через `sshd -T`. [Ubuntu: конфигурация OpenSSH](https://ubuntu.com/server/docs/how-to/security/openssh-server/), [sshd_config](https://man.openbsd.org/sshd_config).

### 14.4. Проверка и применение

Сначала проверить синтаксис:

```bash
sudo sshd -t
```

Без ошибок команда обычно не выводит ничего. Проверить эффективные параметры:

```bash
sudo sshd -T
```

При использовании блоков `Match` проверяйте конкретный контекст входа, заменив заполнители:

```bash
sudo sshd -T -C user=alice,host=client.example.com,addr=192.0.2.50
```

`-t` проверяет конфигурацию и необходимые серверные файлы; `-T` показывает рассчитанные настройки; `-C` задаёт условия подключения для проверки `Match`. Дополнительные условия вроде локального адреса и порта также задаются при необходимости. [sshd(8)](https://man.openbsd.org/sshd).

Только после успешной проверки перечитайте конфигурацию соответствующей службы:

```bash
sudo sshd -t && sudo systemctl reload ssh.service
```

Если unit называется иначе, используйте его действительное имя. Не заменяйте ошибку проверки безусловным restart. После применения откройте новое соединение и подтвердите ожидаемый способ входа, прежде чем закрывать старое.

### 14.5. Сеть и порт

Доступ зависит одновременно от слушающего сокета, локального firewall, облачных правил и NAT. Замена порта с 22 на 2222 уменьшает часть шума сканирования, но не заменяет ключи, обновления и проверку host key.

Для системы, где **уже используется UFW**, можно посмотреть действующие правила:

```bash
sudo ufw status verbose
```

Пример разрешения SSH только с документального клиентского адреса:

```bash
sudo ufw allow from 192.0.2.50 to any port 22 proto tcp
```

Перед выполнением замените адрес своим доверенным источником и учтите IPv6. Это добавляет правило, но не удаляет ранее существовавшее более широкое разрешение. Не включайте и не сбрасывайте firewall удалённо без проверки всей политики и резервного доступа.

<a id="files-transfer"></a>
## 15. Передача файлов

### 15.1. scp

Отправить файл, получить файл и отправить каталог:

```bash
scp ./notes.txt lab:/home/alice/notes.txt
scp lab:/home/alice/report.txt ./report.txt
scp -r ./documents lab:/home/alice/incoming/
```

Если псевдоним не настроен:

```bash
scp -P 2222 -i ~/.ssh/id_ed25519_server -o IdentitiesOnly=yes \
  ./notes.txt alice@server.example.com:/home/alice/notes.txt
```

| Параметр scp | Значение |
| --- | --- |
| `-P 2222` | Порт; здесь заглавная буква. |
| `-p` | Сохранение времени и режима доступа. |
| `-r` | Рекурсивное копирование каталога. |
| `-i`, `-F`, `-o`, `-J` | Ключ, конфигурация, опция SSH, промежуточный сервер. |
| `-C` | Сжатие. |
| `-l ЧИСЛО` | Ограничение скорости в Kbit/s. |
| `-v`, `-q` | Диагностика или тихий режим. |
| `-O` | Старый протокол SCP; нужен только для конкретной совместимости. |

Современный OpenSSH `scp` по умолчанию использует SFTP. Старый режим имеет другие правила обработки путей и шаблонов. Не переключайте протокол без причины. [scp(1)](https://man.openbsd.org/scp).

Команда может перезаписать существующий файл назначения. Для больших деревьев и предварительного просмотра изменений удобнее `rsync`.

### 15.2. sftp

```bash
sftp lab
```

Внутри интерактивного клиента:

```text
pwd
lpwd
ls
lls
cd /home/alice/incoming
lcd ./documents
put notes.txt
get report.txt
bye
```

Команды с начальным `l` относятся к локальной машине. `put` отправляет, `get` скачивает. Для явного порта используется `sftp -P 2222`; параметры ключа и SSH-настроек доступны через `-i` и `-o`. Пакетный файл команд задаётся `-b`, но его операции могут менять и удалять данные — просмотрите содержимое заранее. [sftp(1)](https://man.openbsd.org/sftp).

### 15.3. rsync поверх SSH

Сначала просмотр без изменений:

```bash
rsync -av --dry-run ./documents/ lab:/home/alice/documents/
```

Затем выполнение:

```bash
rsync -av --progress ./documents/ lab:/home/alice/documents/
```

С явными SSH-параметрами:

```bash
rsync -av --dry-run \
  -e 'ssh -p 2222 -i ~/.ssh/id_ed25519_server -o IdentitiesOnly=yes' \
  ./documents/ alice@server.example.com:/home/alice/documents/
```

`-a` включает архивный режим, `-v` выводит ход работы, `--dry-run` показывает план, `-e` выбирает транспорт. Завершающий `/` у исходного каталога означает передачу **содержимого**. Без него структура назначения может отличаться. `--delete` удаляет лишние файлы на стороне назначения; в базовые примеры он намеренно не добавлен. Для стандартного rsync через SSH программа должна быть доступна на обеих машинах. [Руководство rsync](https://download.samba.org/pub/rsync/rsync.1).

<a id="commands"></a>
## 16. Команды, кавычки и интерактивный терминал

Одноразовая команда:

```bash
ssh lab 'uname -sr'
ssh lab 'df -h /'
```

Команда выполняется на сервере, а вывод возвращается в локальный терминал. Обычный `ssh` возвращает код удалённой команды; ошибка самого подключения часто обозначается кодом `255`. GitHub имеет отдельное поведение тестового `ssh -T`, описанное выше.

### Где раскрываются переменные

```bash
ssh lab 'printf "%s\n" "$HOME"'
```

Одинарные кавычки сохраняют `$HOME` до обработки на сервере. Вариант с двойными внешними кавычками может раскрыть переменную локально ещё до запуска SSH.

SSH передаёт удалённую команду для обработки удалённой оболочкой. Нельзя считать, что произвольные аргументы автоматически сохранят границы и будут безопасны. Не подставляйте в командную строку непроверенные имена файлов или пользовательский текст. Для файлов используйте SFTP; для сложной автоматизации — проверенный скрипт с определённым форматом входных данных.

Передать простой скрипт через stdin без локального раскрытия переменных:

```bash
ssh -T lab 'bash -s' <<'REMOTE_SCRIPT'
set -eu
printf 'Удалённый пользователь: %s\n' "$(id -un)"
uname -sr
REMOTE_SCRIPT
```

Кавычки вокруг `REMOTE_SCRIPT` важны: содержимое раскрывается удалённой Bash. Завершающая метка должна стоять отдельно. На сервере должен быть `bash`.

### Когда нужны -t и -T

Для интерактивного редактора или команды, которой нужен терминал:

```bash
ssh -t lab 'top'
```

`-t` запрашивает псевдотерминал; `-tt` принудительно запрашивает его даже без локального терминала. `-T` запрещает псевдотерминал и подходит для машинного вывода или потока данных. Не добавляйте `-t` к бинарной передаче: терминал может преобразовывать поток.

### Долгая работа

Для интерактивного задания используйте установленный на сервере `tmux`:

```bash
ssh lab
tmux new -s maintenance
```

Отсоединение: Ctrl+B, затем D. После повторного входа:

```bash
tmux attach -t maintenance
```

SSH keepalive помогает обнаруживать оборванное соединение, но не гарантирует сохранение процесса. `ssh -f` также не является менеджером удалённых задач. Для фонового сервиса используйте штатный менеджер служб и журналирование.

<a id="jump"></a>
## 17. Промежуточный сервер ProxyJump

Сценарий: внутренний сервер доступен только через bastion. Ключи остаются на клиентском компьютере; пересылка агента для обычного `ProxyJump` не требуется.

```sshconfig
Host bastion
    HostName bastion.example.com
    User gateway
    IdentityFile ~/.ssh/id_ed25519_bastion
    IdentitiesOnly yes
    ForwardAgent no

Host internal
    HostName internal.example.com
    User alice
    IdentityFile ~/.ssh/id_ed25519_internal
    IdentitiesOnly yes
    ForwardAgent no
    ProxyJump bastion
```

Для этих двух назначений предварительно создайте отдельные ключи и зарегистрируйте их на соответствующих серверах.

```bash
ssh internal
scp ./notes.txt internal:/home/alice/
```

Одноразовая запись:

```bash
ssh -J gateway@bastion.example.com alice@internal.example.com
```

С портом bastion:

```bash
ssh -J gateway@bastion.example.com:2222 alice@internal.example.com
```

Для двух переходов можно использовать `-J first-hop,second-hop`, если оба псевдонима настроены. Командный `-i` относится к целевому подключению и не является универсальной настройкой ключа каждого перехода: для разных ключей удобнее отдельные блоки `Host`.

Проверяются host keys и bastion, и конечного сервера. Посредник должен разрешать нужное TCP-перенаправление. `ProxyJump` и `ProxyCommand` не следует одновременно задавать для одного подключения без понимания порядка выбора.

<a id="tunnels"></a>
## 18. Туннели: -L, -R и -D

SSH-перенаправление используется только там, где у вас есть право доступа к обоим концам. Оно не отменяет аутентификацию приложения и правила firewall. Базовые примеры слушают только loopback, чтобы не открыть сервис всей сети.

### 18.1. Локальный туннель -L

Сценарий: на сервере веб-приложение слушает `127.0.0.1:8080`, нужно открыть его в локальном браузере:

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18080:127.0.0.1:8080 lab
```

Теперь на **своём компьютере** откройте `http://127.0.0.1:18080`.

```text
локальный браузер → локальный 127.0.0.1:18080
                 → SSH → сервер → серверный 127.0.0.1:8080
```

В `-L АДРЕС:ПОРТ:ЦЕЛЬ:ПОРТ_ЦЕЛИ` первая пара относится к клиенту; соединение с целью открывает сервер. Поэтому последние `127.0.0.1` здесь означают **сервер**, а не ноутбук.

Для базы данных, доступной серверу по имени:

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:15432:db.internal.example.com:5432 lab
```

Имя базы разрешается и соединение устанавливается с удалённой стороны. Шифрован участок клиент ↔ SSH-сервер; дальнейший участок до базы требует собственной защиты, если проходит по недоверенной сети.

### 18.2. Обратный туннель -R

Сценарий: на ноутбуке есть приложение `127.0.0.1:3000`; нужно временно сделать его доступным **на loopback сервера**:

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -R 127.0.0.1:13000:127.0.0.1:3000 lab
```

На сервере обращайтесь к `http://127.0.0.1:13000`. Здесь последняя пара `127.0.0.1:3000` относится к **клиентскому компьютеру**.

Поведение адреса прослушивания `-R` ограничивает серверная настройка `GatewayPorts`. Профиль `GatewayPorts no` сохраняет доступ через loopback. Не заменяйте адрес на `0.0.0.0` и не включайте `GatewayPorts yes`, если не планируете осознанно публиковать сервис и проверять его аутентификацию.

### 18.3. SOCKS-прокси -D

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -D 127.0.0.1:1080 lab
```

Приложение должно использовать SOCKS-прокси `127.0.0.1:1080`. Пример для установленного `curl`:

```bash
curl --socks5-hostname 127.0.0.1:1080 https://example.com/
```

`--socks5-hostname` передаёт разрешение имени через прокси. Настройка браузера, выполняющего DNS локально, может вести себя иначе. Этот прокси не перенаправляет автоматически весь трафик Linux и не является универсальным VPN для UDP.

### 18.4. Несколько туннелей в одном соединении

```bash
ssh -N -T \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 \
  -o ServerAliveCountMax=3 \
  -L 127.0.0.1:18080:127.0.0.1:8080 \
  -L 127.0.0.1:15432:db.internal.example.com:5432 \
  -D 127.0.0.1:1080 \
  lab
```

`-N` убирает удалённую команду, `-T` — терминал. `ExitOnForwardFailure` позволяет заметить невозможность **создать перенаправление**, но не доказывает, что конечный HTTP-сервис или база здоровы. Проверяйте приложение отдельным запросом. Ctrl+C закрывает foreground-туннель.

В конфигурации аналогичные настройки:

```sshconfig
Host lab-web
    HostName server.example.com
    User alice
    Port 2222
    IdentityFile ~/.ssh/id_ed25519_server
    IdentitiesOnly yes
    ForwardAgent no
    LocalForward 127.0.0.1:18080 127.0.0.1:8080
    ExitOnForwardFailure yes
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

```bash
ssh -N -T lab-web
```

Не путайте `LocalForward`/`RemoteForward` клиента с разрешениями `AllowTcpForwarding`, `PermitOpen`, `PermitListen` на сервере. Полный синтаксис TCP и Unix-сокетов описан в [ssh(1)](https://man.openbsd.org/ssh).

<a id="multiplexing"></a>
## 19. Повторное использование соединения

Multiplexing позволяет новым сеансам использовать уже открытое SSH-соединение. Это ускоряет серии команд, но новый сеанс может не выполнять новую аутентификацию и не просить парольную фразу или касание токена.

Создайте закрытый каталог сокетов:

```bash
mkdir -p ~/.ssh/control
chmod 700 ~/.ssh/control
```

В нужный существующий блок `Host` можно добавить:

```sshconfig
ControlMaster auto
ControlPath ~/.ssh/control/%C
ControlPersist 5m
```

`%C` формирует сокращённое имя на основе параметров соединения. Сокет нельзя размещать в каталоге, доступном другим пользователям для записи. `ControlPersist` оставляет master-соединение на заданное время после завершения последнего клиентского сеанса.

```bash
ssh lab 'uname -sr'
ssh -O check lab
ssh -O exit lab
```

`exit` завершает master и может оборвать использующие его сеансы. `stop` прекращает принимать новые multiplexed-сеансы, сохраняя существующие.

Для диагностики **новой аутентификации** отключите повторное использование:

```bash
ssh -S none -o ControlMaster=no lab
```

Для строгой проверки аппаратного токена дополнительно можно использовать `-o IdentityAgent=none`. Удаление ключа из агента само по себе не разрывает существующий master.

<a id="automation"></a>
## 20. Автоматизация и ограниченный доступ

### 20.1. Команда без интерактивных вопросов

Когда нужный host key уже проверен и сохранён, а ключ доступен процессу:

```bash
ssh -T -o BatchMode=yes \
  -o StrictHostKeyChecking=yes \
  -o ConnectTimeout=10 \
  lab 'uname -sr'
```

`BatchMode=yes` не разблокирует ключ и не обходит пароль. Если для ключа требуется интерактивная парольная фраза, команда завершится ошибкой. Ограничение `ConnectTimeout` не задаёт максимальное время выполнения удалённой команды. Для общего таймаута на Linux можно обернуть вызов в `timeout`, понимая, что разрыв клиента не гарантирует остановку всех удалённых процессов.

```bash
timeout 30s ssh -T -o BatchMode=yes -o ConnectTimeout=10 lab 'uname -sr'
```

Для заданий по расписанию нужны абсолютные пути, явно доступный агент или отдельный сервисный ключ, заранее проверенный `known_hosts` и минимальные права. Не делайте копию личного административного ключа на каждом CI runner. FIDO2 с обязательным касанием плохо подходит для полностью автоматического unattended-задания.

### 20.2. Ограничения одного ключа на Linux

В `authorized_keys` перед открытым ключом можно указать ограничения. Следующая строка — **шаблон**, а не готовый действительный ключ:

```text
from="192.0.2.50",restrict,command="/usr/bin/id" ssh-ed25519 PUBLIC_KEY_BODY monitoring-key
```

Вместо `PUBLIC_KEY_BODY` используется настоящая открытая часть, а документальный адрес заменяется разрешённым источником. `from` ограничивает адрес входа, `restrict` отключает ряд дополнительных возможностей, `command` заставляет выполнять фиксированную команду. Один `restrict` не равнозначен ограничению произвольных shell-команд: для этого нужен `command` или профиль сервиса. [Формат authorized_keys](https://man.openbsd.org/sshd#AUTHORIZED_KEYS_FILE_FORMAT).

Для ограниченного туннельного сервиса могут понадобиться `permitopen`, `permitlisten`, соответствующие настройки `AllowTcpForwarding` и отсутствие произвольной оболочки. Ограничение пересылки портов само по себе не изолирует пользователя, которому разрешено запускать любые программы на сервере.

### 20.3. Deploy key GitHub

Для одного репозитория можно создать отдельную SSH-пару и добавить её открытую часть в **Repository → Settings → Deploy keys**. По умолчанию сохраняйте доступ только для чтения; запись включайте только при необходимости. Такой ключ привязан к репозиторию и управляется отдельно от личных ключей аккаунта. [Deploy keys](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys).

SSH-ключ без парольной фразы иногда используется в изолированной автоматизации, но тогда защита файла и ограничение его прав становятся особенно важны. Это не рекомендуемый вариант для универсального личного ключа. Сам секрет выдаётся заданию через механизм CI, не через Git, Dockerfile или артефакт сборки.

<a id="rotation"></a>
## 21. Замена, резервирование и отзыв ключей

### 21.1. Плановая замена

1. Создайте новую пару с новым именем файла.
2. Добавьте новый `.pub` в GitHub и на нужные серверы.
3. Проверьте **новое соединение** с явно указанным новым ключом, без multiplexing.
4. Обновите `IdentityFile` и необходимые задания.
5. Удалите старую открытую часть из GitHub и каждого `authorized_keys`.
6. Уберите старую идентичность из агента и закройте старые master-соединения.
7. По принятой политике удалите ненужные локальные копии старого закрытого ключа.

Пример проверки нового ключа на Linux:

```bash
ssh -S none -F none -p 2222 \
  -i ~/.ssh/id_ed25519_server_new \
  -o IdentitiesOnly=yes -o IdentityAgent=none \
  -o PreferredAuthentications=publickey \
  alice@server.example.com
```

Удаление закрытого файла **не отзывает** украденные копии. Отзыв выполняется на стороне всех принимающих систем. Изменение парольной фразы вашего экземпляра также не меняет старую копию, уже оказавшуюся у другого человека.

### 21.2. Потеря или компрометация

При подтверждённой компрометации сначала отключайте подозрительный доступ, используя доверенное устройство и резервный канал. Проверьте журнал входов и действия аккаунта. Создайте новую пару, а не только новую фразу старого файла. Если украден FIDO2-токен, удалите соответствующие SSH-ключи и отдельно связанные веб-credentials; это разные регистрации.

Удаление ключа обычно запрещает **новую** аутентификацию. Оно не гарантирует остановку уже открытых сессий, токенов приложений или выполненных злоумышленником изменений — это нужно проверять отдельно.

### 21.3. Резервные копии

Для программного ключа резервируйте зашифрованный закрытый файл и сведения о его назначении в защищённом хранилище. Храните парольную фразу так, чтобы восстановление не зависело от одного потерянного устройства. Практически проверьте процедуру восстановления на доверенной машине, не публикуя закрытый материал.

Для нерезидентного FIDO2 нужны рабочий токен и локальный файл-дескриптор; резерв второго токена создаётся как независимый ключ. Не кладите архив `~/.ssh` в Git даже приватного репозитория. Удаление секретов следующим коммитом не удаляет их из истории.

Не обещайте себе «безвозвратное стирание» простым `rm` или `shred` на SSD, snapshot-файловой системе и облачном диске. Отзыв доступа важнее предположений об очистке каждой старой копии.

<a id="certificates"></a>
## 22. Сертификаты и подпись файлов

Эти примеры относятся к отдельной учебной Linux-инфраструктуре. Для обычного личного GitHub-доступа достаточно добавления открытого ключа; SSH-сертификат не следует считать автоматически принимаемым любым аккаунтом GitHub.

### 22.1. SSH CA и временный пользовательский сертификат

В новой учебной директории создайте CA и пользовательский ключ. Для обоих задайте парольные фразы:

```bash
umask 077
mkdir ~/ssh-ca-demo
ssh-keygen -t ed25519 -a 100 -f ~/ssh-ca-demo/ca -C "lab-ca"
ssh-keygen -t ed25519 -a 100 -f ~/ssh-ca-demo/user -C "lab-user"
```

Подписать открытую часть пользователя:

```bash
ssh-keygen -s ~/ssh-ca-demo/ca \
  -I demo-session-001 -n alice -V -5m:+8h -z 1 \
  ~/ssh-ca-demo/user.pub
```

Появится `user-cert.pub`. `-s` выбирает CA, `-I` — идентификатор сертификата, `-n` — разрешённый principal, `-V` — интервал действия, `-z` — серийный номер. В этом примере начало сдвинуто на пять минут назад, окончание — через восемь часов от текущего времени, чтобы небольшой рассинхрон часов не мешал входу.

Проверить содержимое сертификата:

```bash
ssh-keygen -L -f ~/ssh-ca-demo/user-cert.pub
```

Чтобы сервер принимал сертификат, администратор отдельно устанавливает **открытый** ключ CA и настраивает `TrustedUserCAKeys`, допустимые principals и правила входа. Закрытый CA-ключ на сервер не переносится. Без этого подпись файла сертификата сама по себе не даёт доступ.

После настройки доверия можно использовать пару ключ/сертификат:

```bash
ssh -i ~/ssh-ca-demo/user \
  -o CertificateFile=~/ssh-ca-demo/user-cert.pub \
  alice@server.example.com
```

Файл сертификата может автоматически подбираться по стандартному суффиксу `-cert.pub`. Разделение CA и пользовательских ключей удобно для большого числа серверов, но требует управления сроками, отзывом и защитой CA.

### 22.2. Список отзыва KRL

В новом файле можно создать список отзыва учебного открытого ключа:

```bash
ssh-keygen -k -f ~/ssh-ca-demo/revoked.krl ~/ssh-ca-demo/user.pub
ssh-keygen -Q -f ~/ssh-ca-demo/revoked.krl ~/ssh-ca-demo/user.pub
```

Для отозванного ключа проверка вернёт ненулевой статус. Чтобы отзыв реально применялся сервером, KRL нужно безопасно установить и подключить через `RevokedKeys`. Создание локального файла не уведомляет серверы автоматически. Для крупных инфраструктур существуют также отзыв сертификатов по серийным номерам и идентификаторам; см. [KRL в OpenSSH](https://man.openbsd.org/ssh-keygen#KEY_REVOCATION_LISTS).

### 22.3. Подпись файла

SSH-ключом можно подписать обычный файл без подключения к серверу:

```bash
ssh-keygen -Y sign -f ~/ssh-ca-demo/user -n file ./document.txt
```

Файл должен существовать; рядом создаётся `.sig`. `-n file` здесь задаёт пространство имён подписи, **не** пользователя сертификата. Для проверки нужны доверенный список подписантов, исходный файл и подпись:

```bash
ssh-keygen -Y verify -f ./allowed_signers \
  -I demo -n file -s ./document.txt.sig < ./document.txt
```

Пример формата `allowed_signers` с заполнителем:

```text
demo namespaces="file" ssh-ed25519 PUBLIC_KEY_BODY
```

Открытый ключ в этом файле должен быть получен по доверенному каналу. Подпись не шифрует документ.

### 22.4. Подпись Git-коммитов

Git может использовать SSH-ключ для подписания коммитов. В репозитории настройте отдельный ключ подписи или осознанно выбранную существующую пару:

```bash
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_signing -C "git-signing"
ssh-add -t 1h ~/.ssh/id_ed25519_signing
git config gpg.format ssh
git config user.signingkey ~/.ssh/id_ed25519_signing.pub
git config commit.gpgsign true
```

Агент должен быть запущен, как описано в разделе 11. Если ключ уже существует, не выполняйте его создание повторно. При использовании пути `.pub` закрытая часть доступна для подписи через агент. Открытую часть добавляют в GitHub как **Signing Key**; роль Authentication Key сама по себе не означает регистрацию для проверки подписей. Адрес автора коммита остаётся отдельной настройкой. [GitHub: настройка SSH-подписи](https://docs.github.com/en/authentication/managing-commit-signature-verification/telling-git-about-your-signing-key).

### Примеры менее частых параметров

Версия, категории запросов и поддерживаемые алгоритмы:

```bash
ssh -V
ssh -Q help
ssh -Q key
ssh -Q kex
ssh -Q cipher
ssh -Q mac
```

Поддержка алгоритма в `-Q` не означает, что он включён по умолчанию или разрешён удалённым сервером. Не заменяйте обновляемые безопасные настройки длинным устаревающим списком из интернета.

Проверка IPv4 и IPv6 — независимые варианты:

```bash
ssh -4 lab
ssh -6 lab
```

Исходящий адрес выбирают только из уже назначенных клиентской машине:

```bash
ssh -b 192.0.2.50 alice@server.example.com
```

Это не подмена сетевого адреса и не обход маршрутизации. `-B` требует реального имени локального интерфейса.

Порт в URI и обычной форме:

```bash
ssh ssh://alice@server.example.com:2222
ssh -p 2222 alice@server.example.com
```

Прямой поток через bastion, используемый в специальных транспортных схемах:

```bash
ssh -W internal.example.com:22 bastion
```

Этот вызов сам не открывает обычную оболочку конечной машины; в повседневной работе понятнее `ProxyJump`.

`-X` и особенно `-Y` требуют доверия удалённой стороне, могут давать доступ к возможностям локального X-сервера и не равнозначны безопасному полному удалённому рабочему столу. `-w` требует настройки TUN, прав и серверного разрешения; это не сокращённая замена обычному `-L`.

### Настройки через -o

Коротких флагов недостаточно для всех режимов. Через `-o` доступны директивы `ssh_config`:

```bash
ssh -o ConnectTimeout=10 \
  -o ConnectionAttempts=1 \
  -o ServerAliveInterval=30 \
  -o ServerAliveCountMax=3 \
  lab
```

Настройки, которые часто встречаются дополнительно:

| Директива | Когда нужна |
| --- | --- |
| `PreferredAuthentications` | Порядок допустимых методов клиента. |
| `PasswordAuthentication` | Разрешение клиенту попробовать серверный пароль. |
| `KbdInteractiveAuthentication` | Интерактивные запросы сервера. |
| `CertificateFile` | Пользовательский SSH-сертификат. |
| `UserKnownHostsFile` | Отдельная база доверенных host keys. |
| `HashKnownHosts` | Скрытие имён узлов в новых записях known_hosts. |
| `UpdateHostKeys` | Согласованное обновление доверенных host keys. |
| `HostKeyAlias` | Отдельное имя для проверки host key. |
| `HostKeyAlgorithms` | Алгоритмы идентичности сервера. |
| `PubkeyAcceptedAlgorithms` | Алгоритмы пользовательской подписи. |
| `KexAlgorithms` | Алгоритмы обмена ключами сеанса. |
| `Ciphers`, `MACs` | Шифры и контроль целостности транспорта. |
| `LocalForward`, `RemoteForward`, `DynamicForward` | Настройки туннелей. |
| `ExitOnForwardFailure` | Ошибка при невозможности создать forwarding. |

Полный набор директив существенно шире таблицы и меняется с версиями; официальная спецификация — [ssh_config(5)](https://man.openbsd.org/ssh_config). Передача `-o` клиенту не изменяет `sshd_config` сервера. Например, клиентское `PasswordAuthentication=no` защищает конкретное подключение от fallback, но не отключает парольные входы остальных клиентов.

## 24. Дополнительные режимы ssh-keygen

`ssh-keygen` объединяет несколько разных инструментов. Значение `-f`, `-O`, `-n` и других параметров определяется выбранным режимом. Нельзя собрать все параметры из таблицы в одну команду.

| Режим / параметры | Назначение |
| --- | --- |
| `-t`, `-b`, `-a`, `-C`, `-f` | Создание пары. |
| `-p`, `-P`, `-N` | Изменение парольной фразы. |
| `-c`, `-C` | Комментарий ключа. |
| `-l`, `-E`, `-v` | Отпечаток, хеш, визуальное представление. |
| `-B` | Представление отпечатка Bubble Babble. |
| `-y` | Получение открытой части. |
| `-e`, `-i`, `-m` | Экспорт, импорт, формат. |
| `-F` | Поиск known_hosts. |
| `-R` | Удаление записи known_hosts. |
| `-H` | Хеширование имён known_hosts. |
| `-r`, `-g` | DNS SSHFP. |
| `-A` | Создание отсутствующих host keys. |
| `-D` | Открытые ключи PKCS#11. |
| `-K` | Импорт резидентных FIDO credentials. |
| `-w`, `-O` | Provider и дополнительные настройки. |
| `-Z` | Шифр закрытого файла. |
| `-s`, `-I`, `-n`, `-V`, `-z` | Подпись сертификата, principal, срок, номер. |
| `-h` | Сертификат сервера. |
| `-U` | CA-ключ через агент. |
| `-L` | Просмотр сертификата. |
| `-k`, `-u`, `-Q` | Создание, обновление, проверка KRL. |
| `-M generate`, `-M screen` | Генерация и проверка DH moduli. |
| `-Y sign`, `-Y verify` | Подпись и проверка данных. |
| `-Y find-principals`, `-Y match-principals` | Работа с разрешёнными подписантами. |
| `-Y check-novalidate` | Проверка структуры подписи без установления доверия. |
| `-q`, `-v` | Управление диагностикой. |

Спецификация: [ssh-keygen(1)](https://man.openbsd.org/ssh-keygen). Справочник новых версий может перечислять алгоритмы, которых ещё нет в вашем Linux или GitHub. Не выбирайте экспериментально новый тип только из-за его присутствия на странице документации — нужна совместимость обеих сторон.

`ssh-keygen -A` создаёт **серверные** host keys, а не универсальный личный ключ. Удалять существующие host keys ради их обновления без плана ротации нельзя: клиенты увидят смену идентичности.

При `ssh-keygen -H` рядом может остаться `.old` с нехешированными именами серверов. Хеширование не превращает весь файл в зашифрованный секрет и не отменяет необходимость защиты резервных копий.

При импорте/экспорте некоторые режимы способны вывести закрытый материал. Не запускайте неизвестную комбинацию над личным ключом ради просмотра формата. Не используйте старый PEM-формат без требования конкретной системы.

Исторический параметр `ssh-keygen -o` встречается в старых инструкциях: он выбирал новый формат OpenSSH. В современных версиях этот формат используется по умолчанию, а наличие самого флага следует сверять с локальной справкой.

## 25. Сочетания параметров и типичные ошибки

### 25.1. Как собирать команду

Разделяйте задачу на четыре части:

1. Куда подключаться: пользователь, хост, `-p`, при необходимости `-J`.
2. Чем подтверждать доступ: `-i`, `IdentitiesOnly`, агент или FIDO2.
3. Какой сеанс нужен: оболочка, команда, `-t`, `-T` либо `-N`.
4. Как контролировать работу: проверка host key, таймаут, диагностика, forwarding.

Пример чтения состояния сервера через нестандартный порт:

```bash
ssh -p 2222 \
  -i ~/.ssh/id_ed25519_server \
  -o IdentitiesOnly=yes \
  -o StrictHostKeyChecking=yes \
  -o ConnectTimeout=10 \
  -T alice@server.example.com 'uptime'
```

Настроенные `Host` заменяют повторяющиеся параметры. Для сложных команд оставляйте флаги раздельными: `-N -T -v` читается понятнее, чем слитная запись.

### 25.2. Одинаковые буквы у разных программ

| Буква | ssh | ssh-keygen | scp / sftp |
| --- | --- | --- | --- |
| `-a` | Запрет forwarding агента. | Раунды KDF. | У sftp — попытка продолжить передачу. |
| `-C` | Сжатие. | Комментарий. | Сжатие. |
| `-f` | Фоновый режим. | Файл выбранной операции. | У sftp — запрос fsync после передачи. |
| `-i` | Файл идентичности. | Импорт. | Файл идентичности. |
| `-l` | Пользователь. | Отпечаток. | Лимит скорости. |
| `-N` | Без удалённой команды. | Новая парольная фраза. | Не переносите значение по аналогии. |
| `-p` | Порт. | Изменение парольной фразы. | Сохранение атрибутов. |
| `-P` | Метка конфигурации в новых версиях. | Старая парольная фраза. | Порт. |
| `-t` | Псевдотерминал. | Тип ключа. | Не имеет аналогичного общего смысла. |
| `-v` | Диагностика. | Диагностика / визуальный отпечаток с `-l`. | Диагностика. |

### 25.3. Комбинации, требующие внимания

| Комбинация | Что учитывать |
| --- | --- |
| `-N` и удалённая команда | Выберите туннель без команды либо выполнение команды. |
| `-T` и `-t` | Противоположные цели; задавайте одну политику явно. |
| `-n` и скрипт через stdin | `-n` лишает скрипт входных данных. |
| `-f` и stdin | Фоновый режим подразумевает прекращение чтения stdin. |
| `BatchMode=yes` и заблокированный ключ | Не будет интерактивного запроса фразы. |
| `IdentityAgent=none` и `ssh-add` | Для этого подключения загруженный агент не используется. |
| `IdentitiesOnly=yes` и несколько `IdentityFile` | Несколько настроенных ключей всё ещё могут предлагаться. |
| `-J` и `-A` | Forwarding агента обычно не нужен для перехода. |
| `-g` или bind `0.0.0.0` | Может открыть локальный туннель другим узлам сети. |
| `-R` и серверный `GatewayPorts` | Сервер ограничивает адрес прослушивания. |
| `-a 100` без passphrase | Нет ожидаемой защиты закрытого файла фразой. |
| FIDO2 и `ControlMaster` | Повторный сеанс может использовать уже авторизованный канал. |
| `-C` и уже сжатые данные | Дополнительное сжатие может только увеличить нагрузку. |

Параметры размещайте до имени узла. Текст после узла обычно относится к удалённой команде, а не является продолжением настройки клиента.

<a id="troubleshooting"></a>
## 26. Диагностика

### 26.1. Начинайте с фактов

```bash
ssh -V
ssh -G lab
ssh-add -l
ssh -vvv lab
```

Если необходимо исключить уже открытый master:

```bash
ssh -S none -o ControlMaster=no -vvv lab
```

В журнале последовательно проверяйте сетевой адрес, порт, host key, предлагаемый пользовательский ключ, ответ сервера и выбранный метод аутентификации.

Записать диагностику в отдельный файл:

```bash
umask 077
ssh -vvv -E ./ssh-debug.log lab
```

Лог может содержать реальные имена, IP, пути, отпечатки и команды. Перед передачей третьим лицам обезличьте его. Не прикладывайте закрытые ключи, файлы секретов и целиком каталог `~/.ssh`.

На сервере Debian/Ubuntu с соответствующей службой:

```bash
sudo journalctl -u ssh.service --since '15 minutes ago'
sudo sshd -t
sudo ss -ltnp
```

### 26.2. Таблица ошибок

| Сообщение / симптом | Проверка |
| --- | --- |
| `Could not resolve hostname` | Опечатка в имени, DNS, правильный `Host`/`HostName`, доступность сети. |
| `Connection timed out` | Маршрут, firewall, NAT, адрес и порт; это ещё не ошибка ключа. |
| `Connection refused` | Доступность слушателя, служба, порт, явный reject firewall. |
| `Permission denied (publickey)` | Пользователь, файл ключа, запись `.pub`, права, серверная политика. |
| `Too many authentication failures` | Лишние ключи агента; проверьте `IdentityFile` и `IdentitiesOnly`. |
| `UNPROTECTED PRIVATE KEY FILE` | Права и владелец закрытого файла; для личного ключа обычно `600`. |
| `Host key verification failed` | База доверия, непроверенный новый сервер или изменившийся ключ. |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | Сначала независимая сверка причины; не удаляйте запись автоматически. |
| `Could not open a connection to your authentication agent` | Доступен ли агент и корректен ли `SSH_AUTH_SOCK`. |
| `The agent has no identities` | Агент работает, но нужный ключ не загружен. |
| `sign_and_send_pubkey: signing failed` | Агент, доступ к токену, PIN, касание и выбранный ключ. |
| `No such file or directory` для `IdentityFile` | Путь, имя, домашний каталог и пользователь, от которого запускается SSH. |
| `invalid format` | Выбран не тот файл, повреждение переноса или неподдерживаемый формат. |
| `no matching host key type` | Совместимость host key; обновление старой стороны предпочтительнее глобального ослабления. |
| `no matching key exchange method` | Совместимость KEX; это не парольная фраза пользовательского ключа. |
| `Bad configuration option` | Опечатка или опция более новой/другой реализации OpenSSH. |
| `Address already in use` | Локальный порт туннеля занят; выберите другой или разберите владельца сокета. |
| `administratively prohibited` | Сервер запрещает forwarding или конкретное назначение. |
| Туннель поднялся, приложение не отвечает | Доступность цели с нужной стороны, адрес, DNS, порт и собственная авторизация приложения. |
| GitHub приветствует другой аккаунт | Предложен другой ключ; проверьте alias, агент и конфигурацию. |
| `Repository not found` после SSH-входа | Путь репозитория, права аккаунта, ограничения организации/SSO. |
| Git просит HTTPS credential | В репозитории настроен HTTPS transport; SSH-проверка к нему не относится. |

### 26.3. Аппаратный токен не работает

Проверьте по порядку:

1. Поддерживает ли клиент SK-типы (`ssh -Q key`).
2. Поддерживает ли сам токен выбранный алгоритм и `verify-required`.
3. Доступно ли устройство текущему пользователю Linux; нужны ли пакетные udev-правила производителя.
4. Не выполняется ли команда внутри контейнера или удалённой сессии без доступа к USB.
5. Выбран ли соответствующий локальный файл и добавлен ли именно его `.pub`.
6. Получено ли касание и корректно ли введён PIN.
7. Не перепутаны ли FIDO2 SSH, PIV/PKCS#11 и регистрация токена для веб-входа.

Не запускайте всё через root для обхода доступа к устройству и не делайте полный reset токена без понимания потери credentials. При неудачном PIN учитывайте ограничение попыток конкретного устройства.

### 26.4. Частые неверные выводы

- Отсутствие запроса парольной фразы может объясняться агентом или существующим master, а не отсутствием защиты файла.
- Успех `ssh -T` к GitHub подтверждает аккаунт, но не право записи в любой репозиторий.
- `chmod 600` не защищает украденную копию и не заменяет парольную фразу.
- Смена комментария `-C` не меняет владельца доступа на сервере.
- `-a 100` у `ssh-keygen` не задаёт серверный лимит попыток входа.
- Работа HTTPS на порту 443 не гарантирует, что сеть пропускает SSH на этом порту.
- Отпечаток пользовательского ключа и отпечаток сервера решают разные задачи.

## 27. Короткие рецепты

### Личный GitHub без аппаратного токена

```bash
umask 077
mkdir -p ~/.ssh
chmod 700 ~/.ssh
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_github -C "github-laptop"
cat ~/.ssh/id_ed25519_github.pub
```

Задать парольную фразу, добавить `.pub` как Authentication Key, настроить `github-personal`, сверить host fingerprint и проверить:

```bash
ssh -T git@github-personal
```

### GitHub с аппаратным FIDO2

Сначала задать PIN токена и проверить поддержку алгоритма:

```bash
ssh-keygen -t ed25519-sk -a 100 -O verify-required \
  -f ~/.ssh/id_ed25519_sk_github -C "github-fido-laptop"
```

Добавить `.pub`, настроить `github-fido`, подключить токен:

```bash
ssh -S none -o IdentityAgent=none -T git@github-fido
```

### Проверка Linux-входа по конкретному ключу

```bash
ssh -S none -F none -p 2222 \
  -i ~/.ssh/id_ed25519_server \
  -o IdentitiesOnly=yes \
  -o IdentityAgent=none \
  -o PreferredAuthentications=publickey \
  alice@server.example.com
```

### Локальный доступ к веб-сервису сервера

```bash
ssh -N -T -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18080:127.0.0.1:8080 lab
```

### Просмотр плана передачи каталога

```bash
rsync -av --dry-run ./documents/ lab:/home/alice/documents/
```

### Сменить парольную фразу, сохранив пару

```bash
ssh-keygen -p -a 100 -f ~/.ssh/id_ed25519_github
```

Эти рецепты предполагают подготовку, описанную в соответствующих разделах. Не создавайте повторно ключ поверх уже используемого файла.

## 28. Документация и границы применимости

Руководство содержит практические сценарии, справочник коротких параметров `ssh`, основные и специальные режимы `ssh-keygen`, а также объяснение всех настроек, использованных в примерах. У OpenSSH есть дополнительные директивы, платформенные возможности и параметры отдельных режимов; полный нормативный справочник следует читать для **своей версии**, а не предполагать одинаковое поведение всех выпусков.

Для поиска в Linux:

```bash
man ssh
man ssh-keygen
man ssh_config
man sshd
man sshd_config
man ssh-agent
man ssh-add
man scp
man sftp
```

В `man` клавиша `/` начинает поиск, `n` переходит к следующему совпадению, `q` выходит.

Основные первичные источники приведены рядом с соответствующими разделами. Дополнительно доступны [сайт OpenSSH](https://www.openssh.com/), [справочник OpenBSD](https://man.openbsd.org/) и [раздел GitHub об SSH](https://docs.github.com/en/authentication/connecting-to-github-with-ssh).

Конфигурации сервера, firewall, CA и ограничений доступа нужно адаптировать к существующей системе. Все перечисленные варианты не следует включать одновременно. Проверка синтаксиса примера не доказывает наличие вашего токена, сетевую доступность, работу конкретной версии ОС или правильность выбранных прав доступа.

Не сохраняйте в этом репозитории реальные SSH-ключи, токены, парольные фразы, резервные копии `~/.ssh`, сведения о личной инфраструктуре и необезличенные диагностические журналы.
